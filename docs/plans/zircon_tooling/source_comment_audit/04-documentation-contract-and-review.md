# 04 声明文档规范与补充审查

## 阶段状态

状态：进行中。依据用户 2026-10-05 更新的目标，函数声明、数据结构及接口说明须达到文档级深度，包含适用的 Markdown 摘要、参数、返回值和参考关系。全仓逐项审查、问题证据及最终哈希覆盖的完成条件继续有效。

本文件补充 [当前审查计划](03-evidence-recovery-and-current-source-review.md) 中的统一规则。逐对象记录、候选决定、源码增量和验证回执继续保存为独立账本与批次证据；本计划不承载逐项日志。正式账本目录尚未在当前会话获得可验证的写权限，待发布证据保存在已授权的私有审查目录。

## 注释形式

| 对象 | 形式 | 应说明的关系 |
|---|---|---|
| 模块 | `//!` | 模块职责、入口、所有权和边界，以及依赖哪些外部契约 |
| 类型、接口和函数声明 | `///` | 用途、调用时机、必要前提、结果与错误、状态变化和生命周期 |
| 私有语句块和不变量 | `//` | 非显然顺序、进入路径、状态转移、后续影响及设计理由 |
| 已证实缺陷或未闭合问题 | `BUG:` / `TODO:` | 审查编号、触发条件或具体问题、代码证据、证据缺口及下一步 |
| `unsafe` 安全前提 | `SAFETY:` | 调用路径实际保证的内存、别名、线程和生命周期约束 |

保留原有注释及其作者信息。用途已经清楚且现有说明足够的声明可记录“不需新增”；此决定仍须以定义、调用上下文和契约为依据。不得以逐行翻译、重复名称或填充空章节代替系统说明。

## 函数文档

首段是 Markdown 摘要，直接说明函数承担的责任及调用者使用它的目的。随后按实际契约组织章节：

- **参数**：使用真实参数名，解释取值域、身份或路径含义、所有权与借用、超时预算以及相关参数之间的关系。只有实现和调用证据支持的约束才能写成前提。
- **返回与错误**：说明成功结果代表什么，是否仅完成排队或内存变更，哪些条件返回错误；明确可重试性、部分状态变化以及失败后的责任边界。
- **调用时机与生命周期**：说明必须先完成的操作、后续操作、并发或重入要求、取消和释放的作用，以及异步工作是否会在调用结束后继续。
- **参考**：链接已读且直接相关的类型、方法或模块。Rust 使用能够在当前作用域解析的 rustdoc 链接；路径或测试证据可保留在批次账本，不将审查流水号和工具细节写入产品文档。

无参数的函数无需制造参数章节；无错误返回的函数无需制造错误类型。函数说明必须使调用者能判断何时使用、如何满足前提，以及返回结果能证明什么。

## 类型、接口和字段文档

类型摘要应解释它在调用关系中的角色。适用章节包括使用时机、字段或状态含义、不变量、所有权与生命周期、构造和验证边界，以及相关接口。

接口还须区分调用者的前提与实现者的责任。描述默认实现的合并、采样或持久化策略时，明确其适用范围；不得将单个实现的行为推断为所有实现的保证。

字段说明侧重单位、窗口、身份、允许状态和与其他字段的关系。对于指标快照、句柄和回执，必须说明其能证明的事实及时间边界。字段无需套用函数的参数、返回章节。

## 证据与补充流程

1. 以当前精确内容哈希划定互不重叠的文件范围，读取声明、直接调用、trait 实现、宏、动态注册、FFI、测试及契约。
2. 按以上规范逐个决定新增、补充或保留已有说明。无法确定的意图写为具体待验证问题，不使用猜测填充文档。
3. 早先已封存的批次保持原样。补充说明使用当前源码作为新起点，并另存新增片段、前后哈希和覆盖记录；不得把历史回执改写为新标准已通过。
4. 主审独立核对说明与代码路径，检查插入位置和 rustdoc 引用。按语言做范围内格式或解析检查，反向删除新增片段必须恢复起点的完整字节。
5. 记录源码最终哈希、调用证据及问题关系，正式发布后再进行范围内标签一致性核对。私有准备和未发布回执不等于全仓覆盖完成。

本阶段不修改行为或公共 API，不运行例行宽泛 Cargo 测试。旧本地协调器继续退役；验证与提交遵守当前仓库规则，并保留共享索引、其他任务的改动、历史归属及实际验收门槛。

## 完成条件

所有纳入的第一方源码均有匹配最终内容的逐项审查记录；声明文档符合本规范或有明确“不需新增”的依据；每批经过独立复核和语言检查；问题标签与问题账本一致；待处理文件为零。满足这些条件后才能报告全仓扫描完成。
