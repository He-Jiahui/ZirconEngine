# 01 · 跨报告 Owner、Schema、ABI 与 P0 依赖收敛审查

## 1. 结论

当前 `docs/plans/optimize` 已形成 223 篇直接归属七个产品/代码分类的专项报告，共 103,857 行、9,517,591 bytes。按每篇报告自己的“本轮登记/记录/确认”语义、明确的“没有新增 P0”声明，以及只在缺少自述时才使用的唯一 finding ID/表格 fallback，本轮可重建出 **661 项 P0、11,311 项 P1、2,620 项 P2**。这些数字是报告拥有的差距条目，不是源代码缺陷数、功能数、测试数或工作量估算。

这批报告已经足以否定“通过继续补局部按钮、DTO、布尔能力位、固定数字、空 executor 或成功字符串即可达到工程级引擎”的实施方式。当前最高层问题不是单一子系统少几个功能，而是以下共享合同尚未统一：

1. 产品能力、构建产物、运行时 provider 与可见 UI 之间没有 fail-closed 的 admission truth；
2. Build Set、schema、stable identity、source revision、compiled artifact、runtime generation 和 evidence 没有贯穿同一资格链；
3. 生命周期、异步 operation/job、事务、持久化、回滚、shutdown 和动态库卸载分别形成局部协议；
4. ABI/FFI、插件 package/native admission、foreign allocation、脚本权限、在线 principal 与文件系统边界仍存在可伪造、可越界或假成功面；
5. Runtime graphics、UI、asset、scene 和高层系统已经有不少可保留机制，但产品调用链、资源寿命、错误传播、预算、恢复和同语义性能证据没有闭合；
6. Editor 56 个专题的多数产品面仍把 fixture、descriptor、静态 Workbench 或孤立 helper 当作 authoring 能力；builtin catalog还会把无provider的functional view/window登记为可打开产品，Workbench shell声明没有product consumer，structured Copy/Cut/Paste/Duplicate也完全缺席，现有Delete撤销还会丢失`NodeRecord`之外的实体状态；Scene/Effect/Tags搜索入口未执行真实查询，Icon/Gameplay Tags还用固定Usage/Scan结果冒充检索；command/message/event/extension mount/project admission/activation/focus/layout/query generation/transaction/evidence receipt尚未形成同一因果链；
7. WOC 多角色产品把 identity report、项目manifest、协议DTO和golden fixture当作产品进度，但四个binary均立即退出、没有真实VM adapter，clean clone与world-state transaction又不能成立；
8. WOC Zr内部又把534公开字段、51阶段fixed tick、全量state codec、无despawn实体和带业务副作用的decode集中在68,730行world authority，代码规模没有形成可扩展kernel；
9. WOC combat目录虽然有197个文件，但109个非test-main模块仅54个从产品root可达；damage/death/threat/aura、Boss和词缀等55个候选owner断线，四套手写dispatch、分散HP/death写入与缺失parity owners尚未形成工程级战斗runtime；
10. WOC progression的55个非test-main模块仅15个进入普通fixed-tick图；item instance、bank/trade/market、通用quest/craft/talent commit等40个候选owner断线，scalar inventory和非事务经济路径不能承载完整持久实例；
11. WOC social的31个非test-main模块仅10个进入产品图，Catalog/client公开的SocialGraph/Dungeon Finder/Vale Cup/Duel能力大多无reducer；Chat静默丢合法消息，raw entity identity又没有presence/connection lifecycle；
12. WOC instance的57个非test-main模块普通产品只达4个；产品以X/Z坐标分带代替InstanceWorld，14个公开命令无reducer，Dungeon/Delve/lockpick/reset/Pet候选owner与artifact/parity证据均断线；
13. WOC world去重后的49个模块仍有14个候选owner断线；主移动按0.2步长对170个collider重复全表扫描，SpatialGrid/Pathfind未进产品，terrain/spawn又没有definition/partition/artifact generation；
14. WOC generated/content有104个非测试主体和81K行生成代码，但产品schema未聚合21份局部digest，M3/M4/M5/M8/current表没有唯一BuildSet，约58K个条件分支又把内容数据变成未限定成本的VM控制流；
15. WOC command protocol有165个command却只有157个typed payload contract，native FixedTick decode绕过已有validator，WorldState手工解析，movement允许旧sequence覆盖新输入，完整BuildIdentity与per-command outcome均缺失；
16. WOC parity把固定commit golden自洽、kernel fixture稳定和产品actual一致混成同一证据：native double-run复制expected，54个actual owner全缺失，四条M3 trace以常量模板生成，reference probe又执行可变工作树；
17. WOC native client的61个production文件均不在binary调用闭包，window/input/settings/UI/audio/network没有产品host；frame driver在timeline失败后仍消费输入，在线effect又没有secure transport/request identity并可Debug输出secret；
18. WOC native server的fixed-tick driver在VM commit前破坏性出队，fault batch没有可恢复journal且可被下一次空advance覆盖；authority queue没有principal/session/world绑定，commit又未统一outcome、replication和durability代际；
19. WOC World API catalog宣称28个facet/248个member，但只有1个owner文件存在且公开合同0/5匹配；validator不查signature/owner/artifact，projection又没有principal与publication generation隔离；
20. 39个首方plugin package虽然有结构一致的manifest，产品catalog却只路由14/30个runtime与2/25个editor package；standard profile的required Sound/Rendering又没有base catalog feature closure，required selection可被静默丢弃；
21. Vampire样例有173个tracked文件却不能从clean clone还原：7份模型源被根ignore规则排除，required provider依赖手工feature/test fixture，玩法按render update计速/伤害且不消费balance/behavior tree，脚本工件含绝对路径，测试/截图/性能证据又跨代漂移；
22. 唯一Renderable Empty项目模板没有version/content identity/compatibility与创建provenance，项目也不声明provider/BuildSet；Editor与Hub复制创建事务并给出不同成功语义，默认项目还暴露未达到发布资格的Windows release export；
23. `tests/acceptance`已被policy定义为历史归档，但100篇记录没有archive catalog/canonical evidence迁移，仍有两处required test直接读取Markdown字符串；6个serialization fixture虽有真实consumer，却没有历史writer来源、immutable digest或corpus manifest；
24. Tooling、Hub、App 与报告本身都缺少一份机器可校验的 owner/schema/ABI/finding manifest，导致“有报告”仍不能自动证明每条 finding 的唯一 owner、依赖和 currentness。
25. `zircon_runtime_host` 已统一六类JSON consumer policy和allocation release，但公开safe API仍可解引用Safe Rust伪造的raw output/status，`Copy` releaser不持有provider/session lease，protocol fuse又没有原子call admission；Runtime已发布的accessibility tree也没有host consumer/policy闭环。
26. Repo-local Codex控制面由tracked config授予danger-full-access且hook fail-open；agent工程规范与CI规范在Runtime错误、foreign-output ABI和Cargo政策上分叉，blocked aggregate固定exit 0，当前50项结构test有12项失败且未进入required CI。
27. Editor Workbench的270项DesignSpec/271张PNG被计划当作视觉权威，但标准verifier当前RED且未进CI；evidence把固定design未请求的fixture/icon纳入依赖、把legacy prototype真实依赖排除，又由同一导出操作自签candidate hash，192个editor-page也没有capability owner或真实产品验收映射。
28. MVP控制面从可变worktree构建且fingerprint吞入2,373个untracked文件/1.68 GB，ProductReceipt不绑定真实toolchain/runtime dependency；产品可用自报marker与任意非空PNG自认证，resource reporter又在没有产品observation producer时把caller JSON标为`measured`，F5与性能资格因此仍不成立。
29. capability/package/config/registration可以在没有provider instance、真实执行或qualification时投影`Complete/Available`，成功型no-op与fallback/degraded又未进入统一负向状态预算；“声明存在”仍可越级成为“产品完成”。
30. Git ignore事实进入MVP/Coordinator SourceSet信任边界，2,849个tracked-but-ignored path同目录的新required source可逃逸fingerprint；license/notice声明与Git/product artifact不闭合，1.335 GB混合tree又没有可验证SourceArchive。
31. 18个Rust executable target没有canonical TargetId/role/artifact/install/launch/CLI/qualification contract；6个target靠Cargo自动发现，build/spawn/exit 0不能证明正确产品代次进入Ready或执行目标能力。
32. PowerShell/Python/Shell/Node/workflow入口没有canonical CommandId、InterpreterSet、MutationScope、CLI/exit或OperationReceipt；path、npm alias和shell block仍可同时充当身份、权限与成功证明。

33. Zr real backend依赖未固定兄弟仓库和本机DLL，required CI不构建真实后端；`.zro`又缺signature/platform/width/endian/length/verifier admission，incremental/artifact发布非原子且类型/codegen/object/GC仍有跨层临时语义。
34. 11,758个production-like Rust文件中有1,791个policy-like命名定义分散在800文件，但Editor设置注册面只有6处Definition构造和13个公开key，Runtime配置仍是String到JSON；跨owner GPU/格式/容量合同重复，MAX又混用为unlimited、invalid、missing和admission bypass，没有可追溯的PolicyDefinition、分层override、ResolvedPolicySnapshot与性能资格证据。
35. 11,498个production-like Rust文件的失败词法inventory显示已有451个typed Error和74处catch_unwind基础，但panic/unreachable/expect、421处poison后继续与91处poison即终止、错误丢弃/default化和948个Result<_, String>候选没有共同FailureDomain、RecoveryDecision、TaskSupervisor或source/build-bound Failure/Crash Receipt。
36. 11,485个production-like Rust文件的并发词法inventory显示Runtime已有TaskPools/JobHandle、有界text/log/render queue等局部基础，但产品没有统一ExecutionDomain、ThreadTopology、LockGraph、AtomicInvariant、ChannelPolicy与TaskScope；资产change subscriber持锁wake且无界、World inspection分裂发布、network latency双Relaxed atomic发布协议均已形成具体反例，Loom/Shuttle/Miri/TSan又未进入直接验证配置。
37. 11,716个production-like Rust文件的memory inventory显示ECS/command/text/asset/render/foreign-output已有局部heap estimate、arena/pool和byte budget，但产品没有统一MemoryDomain/Tag、CPU/GPU/mapped/foreign预算、pressure/reclamation、OOM与heap snapshot；artifact cache-owned Arc bytes不能约束external lease实际驻留，InlineCommandArena保留峰值capacity，UiSurfaceNodePool又无界。
38. Runtime已有Real/Virtual/Fixed三时钟、稳定schedule与deterministic worker merge，但普通Update/PostUpdate直接消费raw real delta而绕过Virtual pause/scale/clamp；Fixed clock又在执行前预推进整批steps，导致每个子步读取相同最终tick/elapsed，失败时仍虚报全部时间已提交。AI、Particles与WOC的局部RNG也没有统一algorithm/stream/state/replay合同。
39. Runtime共享math alias、render precision seam和scene finite校验是真实基础，但CPU World仍是absolute f32，reflection/animation/sound/render DTO阻断局部f64切换；全产品没有Coordinate/Unit schema、typed Space、origin generation/rebase transaction或render-relative current/previous pipeline，scene又接受非单位quaternion与病态scale。
40. Runtime已有UUID、代际slot、HostRegistry、Render Graph generation和lease等局部基础，但Persistent/Live/Scoped/Sequence/Revision身份未统一；stable UUID依赖DefaultHasher，Scene载入可在MAX ID处panic/回绕，各owner又分裂为wrap、saturate、overwrite、retire和panic策略。
41. Runtime已有ProjectPaths物理身份、root admission、durable transaction、bounded watcher和generation publication，但ResourceIo无人实现或消费、AssetIoDriver为空、固定scheme没有source/mount lifecycle；lossy path/URI、check-open race、rename uncertainty和203文件的direct filesystem候选也没有统一治理。
42. ### 3.1 不能合并成同一 owner 的边界

- BuildSet identity 与 runtime generation相关但不等价：BuildSet 证明二进制/数据来自哪次构建，generation证明同一运行会话内哪个实例仍有效。
- Resource stable ID、Entity ID、Document ID、GPU handle、Network Object ID、Plugin handle不能统一成一个裸整数；它们共享 qualified-ID schema，但由不同 owner分配和验证。
- Editor transaction、Runtime world mutation、Hub database transaction、release installation transaction共享阶段协议，但不能共享一个跨产品全局锁或一个序列化实现。
- Capability descriptor只声明要求；admission decision必须由 product composer结合 provider、artifact、runtime status、permission和budget作出。
- Artifact cache不拥有 source truth；DDC/remote cache只能返回按完整 key验证的immutable artifact，miss/corruption必须回到 compiler，而不是重写source。
- Observability不能成为控制 authority；profile、health、dashboard与Workbench必须投影真实状态，不得反向用静态UI值决定runtime truth。
- Unity Graphics镜像只提供 SRP/Core/HDRenderPipeline 包级图形实现，不能被外推为Unity完整Editor、Hub、账号、包服务、协同或引擎生命周期证据。

## 8. 参考引擎给出的结构约束

| 参考 | 本轮使用的事实 | 对Zircon的约束 | 不外推的内容 |
|---|---|---|---|
| Unreal | ModuleManager显式load/unload与module owner；UObject identity/lifetime；RHI resource；Editor transaction/product分层 | owner、lifecycle、object/resource identity、render lifetime、authoring transaction必须是独立但可组合的系统 | 不因类型/文件数量相似就宣称功能或性能等价 |
| Godot | GDExtension manager、ResourceUID、Object、EditorUndoRedoManager职责分离 | extension、resource identity、object lifetime、undo/redo不能由一个通用字符串registry替代 | 不把Godot特定single-process/Object模型照搬为Zircon ABI |
| Bevy | Plugin/App、World、AssetServer、PipelineCache由不同资源/系统拥有 | ECS world、asset loading、pipeline compilation与product plugin组合必须分owner并通过typed state交接 | 不把ECS schedule或Rust monomorphization当作跨DLL稳定ABI |
| Fyrox | Plugin、ResourceManager、Editor Command分别负责runtime扩展、resource与可撤销编辑 | runtime plugin/resource与Editor command边界必须清楚，preview/command不能直接冒充runtime source truth | 不复制其具体scene graph或UI架构作为唯一方案 |
| Unity Graphics | CoreUtils及SRP package内图形utility与pipeline owner | 只用于具体render package/resource/command语义对照 | 本地镜像不含完整Unity Editor/Hub/Package Manager，不能为这些域提供完成证据 |

共同规律不是“参考引擎拥有更多类”，而是高风险对象均有明确owner、identity、状态机、失败路径、资源寿命和工具链资格。Zircon可以采用不同数据结构和更高性能实现，但不能删除语义、恢复、错误或证据来制造基准优势。

## 9. 重构里程碑

### M0 · 报告与产品 Truth Freeze

- 所有可见能力通过O00 admission；无provider/无artifact/无runtime reader全部fail-close；
- 给7篇旧报告补标准元数据、唯一finding ID与current-source复核策略；
- 实现FindingRecord生成/校验，不改变production行为；
- 恢复Hub、plugin lock和required test最小可达，保留失败基线。

### M1 · BuildSet、Identity、ABI、Budget 基础

- 冻结O01/O03/O06/O07/O15公共合同；
- 清除`usize`持久wire、裸路径输出、可伪造foreign ownership、无generation handle和pre-admission native load；
- 建立BuildSet/Schema/Artifact/ABI/Generation/Evidence六类不混淆identity。

### M2 · Lifecycle 与 Operation 收敛

- Runtime module/service/task、App host/session/window、Editor jobs/Play、Hub process/build、plugin unload接入O02；
- 建立cancel/drain/terminal/cleanup/DLL unload fault矩阵；
- 所有async product action返回typed receipt，不再用字符串或同步`Ok(())`代替。

### M3 · Source、Artifact、Persistence 与 Transaction

- O04/O05实现source→artifact→install和preflight→commit→rollback→reopen；
- 先修复已证明的数据擦除、partial mutation、path escape与无last-good路径；
- DDC/cook/package只消费完整artifact key，不拥有source。

### M4 · World 与 Runtime Systems

- Runtime05、08A-08G和26按O08恢复普通产品Scene、per-world owner、incremental sync、teardown与reader-gated debug；
- AI/Gameplay/Network等未存在产品先保持Unavailable，不用通用script host或fixture冒充domain；
- Editor domain只能在runtime gate通过后启用Apply/Playtest/Debug。

### M5 · Graphics 与 UI Correctness

- 09A-09H2与Runtime26/27 renderer/backend按O09依赖序硬切RHI/RenderScene/artifact/history/lighting/post/particle/AO路径；
- 11A-11C、Interface03和Editor01按O10实现同代publication、完整input effect、font/text/IME/security/a11y；
- 先过像素、时序、device loss、OOM、fault和scale gate，再做高级性能优化。

### M6 · Authoring Product 收敛

- Editor02建立共享document/save/transaction基础；Editor04/05建立asset/reflection adapter；Editor09建立operation projection；
- Editor14-45逐domain接入O13，删除静态第二authority和私有save/undo/compiler/preview；
- 每个domain完成create/open/edit/undo/save/reopen/cook/play/debug/error/recovery闭环。

### M7 · Online、Collaboration 与 Security

- O12/O15完成principal、credential、RBAC/audit、secure transport、ordering、CAS/conflict、reconnect/resync；
- Runtime multiplayer、Editor multi-user、Hub marketplace/cloud保持分层，不共享裸remote command或local Git identity；
- signed package/entitlement/trust在native code加载前完成。

### M8 · Evidence、Delivery 与 Competitive Gate

- O11/O14统一source/build-bound test/profile/crash/symbol/package/install/release evidence；
- 使用versioned workload corpus、明确oracle、同场景同画质同硬件统计协议；
- 只有correctness、failure、soak、memory、CPU/GPU/frame-time和artifact完整性同时达标后，才允许竞争性结论。
