## Problem

Parallel Codex Sessions validate independent source snapshots, but repeated Rust dependency builds and per-job target trees can consume hundreds of gigabytes. Serial validation avoids target locking but leaves available CPU idle and increases queue latency.

## Accepted Architecture

- Exact validation inputs are coalesced by the existing ticket dedupe key while they are queued or running.
- The validation worker advances at most two immutable workspace copies concurrently. FIFO claim order remains authoritative.
- Cargo keeps one retained warm target per compatibility key. A second retained target for the same key is forbidden.
- The existing resource-budget service may admit one disposable burst target for eligible scoped CPU validation. Burst output is deleted after release.
- `reuse` is the default validator storage mode: persistent Cargo fingerprints and compiled dependencies, dev/test debug disabled, package-level incremental compilation only for Runtime, Editor, and App, and a shared bounded `sccache`. `compact` disables incremental compilation for every package.
- `compact` keeps the same compiler cache but places Cargo build-script output in per-job scratch and deletes that scratch after the run.
- `diagnostic` is opt-in for symbolized investigation and enables full dev/test debug information.
- Validation refuses to start when the target drive cannot preserve a `35 GiB` reserve. It never automatically cleans a hot pool immediately before rebuilding it.

## Dynamic Dependency Boundary

- Native third-party libraries with a stable C ABI may remain external DLLs so multiple host/runtime artifacts can reuse one content identity. NativeDynamic export staging publishes immutable files into a shared SHA-256 content store, then materializes an ordinary private copy in every task stage; a task never receives a writable alias of the shared blob.
- The Runtime package defaults to `rlib`; the versioned product `zircon_runtime.dll` is produced only by the explicit `cargo rustc --lib --crate-type cdylib` product path. Development dynamic linking uses the non-published `zr_dev_deps_dylib` and `zr_runtime_dev_dylib` link carriers, with heavy dependencies enabled only by the development feature. Splitting arbitrary Rust crates into DLLs remains rejected because Rust ABI, enabled features, panic strategy, and toolchain identity are not a stable cross-build contract.
- Hosts communicate with `zircon_runtime.dll` only through the versioned runtime C ABI. A future artifact manifest must assign independent `RuntimeArtifactId` and `HostArtifactId` values so host-only changes do not invalidate an unchanged runtime DLL.
- The NativeDynamic store is bounded to 4 GiB by default. Oldest source blobs are reclaimed after a run without affecting already materialized task-private copies. Signing and notarization runs bypass the shared store entirely so mutable external tools operate only on private staged files.

## Sealed Ticket Sources And Writer-Lock Boundary

- The next milestone now seals every submitted overlay byte into the existing zlib-compressed, SHA-256-addressed coordinator object store. Null manifest entries remain deletion tombstones. An internal `validation-ticket-source:<ticket-id>` snapshot pins those objects while the ticket is queued, materializing, or running; terminal projection releases the pin and existing retention performs eventual deduplicated collection.
- Submit still replays an existing `request_id` before any mutable admission check. New requests validate Session/Plan, dependency roots, and current overlay ownership before reading source bytes, then repeat the mutable admission checks in the commit transaction. Source reading and hashing occur outside the global SQLite writer transaction; object registration, ticket insertion, source-pin insertion, and the sealed event commit atomically.
- A multi-file stale submission first reproduced an orphan-object leak: an earlier valid file could create a compressed object before a later stale file rolled back its database row. The corrected path validates every path and hash before writing any object. A separate deterministic concurrency RED held a source read open and showed an unrelated database writer blocked; after the transaction split, that writer completed within the 0.5-second assertion window while the source read remained blocked.
- Generic and Cargo validation copies now accept the immutable overlay manifest and materialize those paths from object bytes instead of the live worktree or current attribution. This covers changed files, newly created files, and deletion tombstones. Legacy tickets without a sealed event retain the prior fail-closed live ownership and drift checks.
- Cargo durable materialization requests persist the sealed overlay manifest so daemon recovery uses the same bytes. `PinnedCargoPlanner` constructs Cargo manifests, lockfiles, toolchain/config files, and zero-byte source topology from the ticket's baseline commit, then applies the sealed overlay and tombstones before invoking metadata inside the registered copy job. A submit-time manifest scan also records every sibling Git dependency's exact commit and package include roots in `coverage.externalSources`; the worker consumes that immutable descriptor after restart instead of reading a later sibling `HEAD`. Legacy tickets without the version marker retain live discovery only for compatibility.
- Each new ticket also records the submitting Session's `baseline_epoch` and `base_head` in its immutable submitted event. Both participate in the dedupe key, and the source-object snapshot references the same baseline epoch. A Session baseline change during source capture rejects the request before any ticket, request row, snapshot, or object is written.
- The validation worker passes the ticket's `base_head` into both generic and Cargo materialization. Generic dependency enumeration now uses `git ls-tree` against that commit rather than the live index; the durable Cargo JSON stores the same commit and recovery preserves it after HEAD advances. ## Native Dynamic Artifact CAS

- Managed Cargo environments expose one stable NativeDynamic CAS below the selected D/E/F storage root. A verified cache hit hashes the source and validates the existing blob under the digest lock before copying it into the task-owned stage.
