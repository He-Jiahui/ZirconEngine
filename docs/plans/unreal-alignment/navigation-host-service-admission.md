# Navigation plugin declares a Driver → Manager dependency before the scene can tick

**Draft — executed RED; no production change.** Source reviewed against ZE main `e89349ca51b4e9d024c194cd3bdf645bd25b6c37` and the local Unreal checkout. The rejection was measured using the unchanged production plugin. #146 constructed its Legacy manager directly and did not test host admission.

1. **Difference.** The ZE [production plugin descriptor](../../../zircon_plugins/navigation/runtime/src/plugin.rs#L199-L214) contributes [one implementation Driver](../../../zircon_plugins/navigation/runtime/src/lib.rs#L68-L95) that explicitly depends on `AssetModule.Manager.ProjectAssetManager`. Its scene Driver and public Manager both view that implementation. UE uses an instance attached to a world, and selects/configures it before initializing navigation for that same world; its navigation-data readiness follows the instance, not a service-kind edge equivalent to ZE's.
2. **Impact.** The real plugin catalog successfully contributed the module and the linked project plan selected it, but both Core registration and module composition returned the same `InvalidServiceDependencyKind`. This happens before plugin activation or the scheduled `navigation.agent_tick`. It is not a measured crash or a finding about every distribution: the linked production descriptor was explicitly selected, and an independent builtin navigation control remained functional.
3. **Cause and Unreal evidence.** ZE's [descriptor admission](../../../zircon_runtime/src/core/runtime/handle/registration/validation.rs#L17-L40) [requires Driver dependency targets to be Drivers](../../../zircon_runtime/src/core/runtime/handle/registration/validation.rs#L88-L102), independent of `Lazy`. In the local Unreal tree, `Engine/Source/Runtime/Engine/Private/AI/NavigationSystemBase.cpp:74–115` selects configuration, installs its instance in the world and optionally initializes it. `Engine/Source/Runtime/Engine/Private/World.cpp:2487–2499` may install without initializing; `Engine/Source/Runtime/Engine/Private/GameInstance.cpp:521–530` initializes PIE navigation after actor initialization. `Engine/Source/Runtime/NavigationSystem/Private/NavigationSystem.cpp:1355–1413` sets up the current world and registers its nav data. This references service availability, operation timing and ownership; UE does not expose ZE's Driver/Manager hierarchy.
4. **Rust feasibility.** Keep one authoritative navigation implementation and the existing Core dependency contract; deleting the descriptor edge while fetching the same Manager in the Driver factory would just hide the dependency. Baking requires project generation ownership: [geometry leases](../../../zircon_plugins/navigation/runtime/src/manager/bake/geometry_provider.rs#L17-L89), [preparation and generation capture](../../../zircon_plugins/navigation/runtime/src/manager/bake.rs#L388-L423), and both [direct](../../../zircon_plugins/navigation/runtime/src/manager/bake.rs#L508-L568) and [operation](../../../zircon_plugins/navigation/runtime/src/manager/bake.rs#L571-L629) publication fence the result against that project. The actual [AssetModule](../../../zircon_runtime/src/asset/module.rs#L46-L107) exposes Managers, not a lower-level Driver carrying the same project authority. [The audio module](../../../zircon_plugins/sound/runtime/src/module.rs#L24-L69) is a legitimate ZE precedent for an asset-dependent Manager above its Driver, but a move like that would affect navigation's existing scene bake contract, not just its descriptor. No legal one-line fix was established.
5. **Interface and ECS.** Preserve the public `NavigationManager` and `SceneNavigationRuntime` views, their shared loaded-mesh state, and project/world generation guards unless a separate, specifically justified change is approved. Neither UE's `UWorld` instance life cycle nor registry policy requires creating per-ECS-entity navigation owners. Do not change navmesh bake geometry, movement writeback, hierarchy, Prefab, or Core-wide service validation in this issue.
6. **Concrete ZE gate.** The [frozen target](../../../zircon_plugins/navigation/runtime/tests/host_service_admission.rs) reuses the three-entry and flat-quad assertions of the [existing registration](../../../zircon_plugins/navigation/runtime/src/tests/registration.rs#L25-L108) and [manager](../../../zircon_plugins/navigation/runtime/src/tests/manager.rs#L20-L43) tests. Register the real exported descriptor and its prerequisites before first activation; independently send the unmodified registration through the existing [module composition compiler](../../../zircon_runtime/src/builtin/runtime_modules/composition/compiler.rs#L59-L86). The local Unreal test `System.Navigation.NavMesh.Pathfinding.TwoPoints` (`Engine/Source/Developer/NavigationTestSuite/Private/NavMeshWorldCreationTest.cpp:29–57`) uses the world instance and real prepared data from `NavMeshTestWorld.cpp:146–221`. The availability→data→query assertions are adapted, without a new ZE harness. Keep this Draft tests-and-evidence only until the asset-aware bake portion has a legitimate owner and both service views still reach the same implementation. Then require both admission cases to pass and observe a typed report from a real Level `Update`; a built-in fallback or an empty schedule is not plugin acceptance.
