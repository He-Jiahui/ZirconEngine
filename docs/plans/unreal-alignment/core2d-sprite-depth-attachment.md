# Core2D sprite raster depth attachment is resolved through the wrong graph access

**Draft — independent real DX12 RED → GREEN.** Baseline `main@e89349ca51b4e9d024c194cd3bdf645bd25b6c37`. This is independent of sprite coordinate projection in #177: its original rigid frame first exposed the refusal. The frozen rigid fixture below reproduces it without hierarchy shear, with default Core2D selection and the real World journal identity.

1. **Difference.** UE uses a distinct depth-stencil attachment binding and derives graph access from that attachment contract. The ZE [opaque Sprite2D graph declaration](../../../zircon_runtime/src/graphics/feature/builtin/feature_descriptors/sprite.rs#L19-L37) declares a scene depth write; the [actual sprite recorder](../../../zircon_runtime/src/graphics/scene/renderer/execution/context/gpu/surface.rs#L151-L194) asks the same pass for a `Read` view of that name despite using it as the depth attachment.
2. **Impact.** Native `zircon_runtime` old `2c0465f5d0dadd199a48c8214b0d03e9c19d4b29` (main production, existing test-lifetime lens, and #177 test fixture only) reports `render graph pass opaque-sprite did not declare Read access for resource scene-depth`. The submit fails before the first *rigid* frame has any GPU pixels. This is not a shear result. An older snapshot-only product test with an orthographic camera but a Core3D pipeline instead failed its `pipeline 1 vs 3` assertion; that is not the same failure or a substitute for the live admitted Core2D witness.
3. **Cause and Unreal evidence.** The [ZE executor](../../../zircon_runtime/src/graphics/scene/renderer/execution/builtin_scene_executors.rs#L78-L94) already asks for the depth **write attachment** operations, and [actual WGPU binding](../../../zircon_runtime/src/graphics/scene/renderer/sprite/sprite_renderer.rs#L147-L173) passes them as raster depth ops, not sampled texture access. The [exact resolver](../../../zircon_runtime/src/graphics/scene/renderer/context/resource_resolver.rs#L130-L155) is right to distinguish accesses; making it allow undeclared reads would invalidate physical resource identity and graph checks. UE `Engine/Source/Runtime/Renderer/Private/SceneHitProxyRendering.cpp:356–374, 425–442` uses `EClear` then `ELoad` on the same DSV with `DepthWrite_StencilWrite`; `DepthRendering.cpp:318–327` also chooses `EClear` or `ELoad` while retaining the same access. `Engine/Source/Runtime/RenderCore/Private/RenderGraphBuilder.cpp:195–211` derives per-plane access from that binding, and `RenderGraphPass.cpp:74–105` encodes it separately from the load/store actions. These support attachment-based resource identity, not copying UE flags into WGPU. ZE's [Sprite PSO](../../../zircon_runtime/src/graphics/scene/renderer/sprite/sprite_renderer.rs#L82-L89) keeps fragment depth writes disabled; that does not turn its raster attachment operations into a graph texture read.
4. **Rust direction.** Bind the **declared writable attachment access** in the Sprite raster recorder if the frozen test confirms the refusal. In later phases the [exact Read key](../../../zircon_runtime/src/render_graph/graph/access_index.rs#L84-L114) addresses the prior contents, while the Write key addresses the successor; both currently use [the same physical scene depth target](../../../zircon_runtime/src/graphics/scene/core/render/bind_frame_graph_resources.rs#L46-L60). Do not add a false Read dependency, skip the pass, weaken admission or alter the shader/depth compare.
5. **Interface/ECS.** No change should be required to `World`, render frame DTOs, sprite data, camera selection or graph validation. ZE selects a versioned per-pass access; UE RDG extracts DSV access from pass parameters. Compile-time opaque `Clear/Store` and later `Load/Store` stay as declared. During production recording the [camera-stack policy](../../../zircon_runtime/src/graphics/types/viewport_camera_stack_attachment_policy.rs#L90-L108) converts first-target Clear to Load; [camera-region initialization](../../../zircon_runtime/src/graphics/core/render/execute_compiled_scene_graph_stages.rs#L100-L109) occurs before the graph. Leave both unchanged.
6. **Concrete gate.** Reuse the existing ZE product-submit suite for three rigid Ready sprites (opaque, mask, blend), a background patch, and the compiler's distinct depth successors; preserve the [strict physical resource gate](../../../zircon_runtime/src/graphics/scene/renderer/context/tests/resource_resolver.rs#L60-L117). Unreal's `Engine/Plugins/Tests/RHITests/Source/RHITests/Private/RHITests.spec.cpp:60–64` and `RHIClearTextureTests.cpp:1141–1158, 686–744` provide the real pass → staging → channel-comparison pattern for **color**. The DSV policy source is cited above; no identical UE depth automation or UE binary run is claimed. Require current-frame center/outside pixels and no graph/device fault; the pixels test raster admission, not Sprite fragment depth writes. After verified graph repair, use that identical fix in both local #177 comparisons; a graph refusal is not a shear pixel.

## Matched candidate

- The sole runtime change is [the Sprite depth view lookup](../../../zircon_runtime/src/graphics/scene/renderer/execution/context/gpu/surface.rs#L161-L172), `Read` → `Write`. It follows the same access row already used to obtain the attachment operations, matching the DSV binding and separate load/store decisions in UE `RenderGraphBuilder.cpp:195–211` and `RenderGraphPass.cpp:74–105`. No declaration, pass scheduling, strict resolver, camera clear, depth compare/write enable or ECS change.
- Windows candidate `9c07058e137d97a41948014b678acb32dea3e47b` differs from its baseline only by that line. Same fixture, arguments, DX12 RTX 3060 Laptop and strict resolver: **1/2 → 2/2 GPU tests**, `ready=3`, `fallback=0`, `vertices=18`, all three sprite executors and no device fault. Actual offscreen patches: opaque red **16/16**, masked green **16/16**, transparent blue **16/16**, background **16/16**. The exact CPU successor control stays green; the existing generic Overlay-order expectation still fails identically and is outside this change. No packaged editor or Unreal executable was run.
- This enables the independent #177 affine test to measure pixels without changing its geometry. The two production changes remain separate Drafts; local comparison prerequisites do not change either PR base or admission gates.
