# Core2D sprite raster depth attachment is resolved through the wrong graph access

**Problem-only Draft.** Baseline `main@e89349ca51b4e9d024c194cd3bdf645bd25b6c37`. No production or test change in this review yet. This is independent of sprite coordinate projection in #177: its old rigid frame (`scale_x=1`) reproduced the refusal before a textured sprite could rasterize, on the actual RTX 3060 Laptop DX12 backend with default Core2D selection and the real World journal identity.

1. **Difference.** UE uses a distinct depth-stencil attachment binding and derives graph access from that attachment contract. The ZE [opaque Sprite2D graph declaration](../../../zircon_runtime/src/graphics/feature/builtin/feature_descriptors/sprite.rs#L19-L37) declares a scene depth write; the [actual sprite recorder](../../../zircon_runtime/src/graphics/scene/renderer/execution/context/gpu/surface.rs#L151-L194) asks the same pass for a `Read` view of that name despite using it as the depth attachment.
2. **Impact.** Native `zircon_runtime` old `2c0465f5d0dadd199a48c8214b0d03e9c19d4b29` (main production, existing test-lifetime lens, and #177 test fixture only) reports `render graph pass opaque-sprite did not declare Read access for resource scene-depth`. The submit fails before the first *rigid* frame has any GPU pixels. This is not a shear result. An older snapshot-only product test with an orthographic camera but a Core3D pipeline instead failed its `pipeline 1 vs 3` assertion; that is not the same failure or a substitute for the live admitted Core2D witness.
3. **Cause and Unreal evidence.** The [ZE executor](../../../zircon_runtime/src/graphics/scene/renderer/execution/builtin_scene_executors.rs#L78-L94) already asks for the depth **write attachment** operations, and [actual WGPU binding](../../../zircon_runtime/src/graphics/scene/renderer/sprite/sprite_renderer.rs#L147-L173) passes them as raster depth ops, not sampled texture access. The [exact resolver](../../../zircon_runtime/src/graphics/scene/renderer/context/resource_resolver.rs#L130-L155) is right to distinguish accesses; making it allow undeclared reads would invalidate physical resource identity and graph checks. UE `Engine/Source/Runtime/Renderer/Private/SceneHitProxyRendering.cpp:356–365` declares `EClear` with `DepthWrite_StencilWrite`; `DepthRendering.cpp:318–327` chooses `EClear` or `ELoad` while retaining the same writable DSV contract. `Engine/Source/Runtime/RenderCore/Private/RenderGraphBuilder.cpp:195–211` derives the access for each depth/stencil plane from that binding. These support attachment-based resource identity, not copying UE flags into WGPU.
4. **Rust direction.** Verify a graph whose write depth version differs from a declared prior read where possible, and separately hold a real rigid default-Core2D hardware submission. After qualified old RED, evaluate selecting the matching **declared writable attachment version** in the sprite raster recorder. Do not add a fake input dependency to make an incorrect read lookup succeed, skip the graph pass, weaken admission or alter the pixel shader/depth compare. Verify both opaque write-only and load/store stages; don't claim the diagnosis certifies all other Core2D paths.
5. **Interface/ECS.** No change should be required to `World`, render frame DTOs, sprite data, camera selection or graph validation. ZE's graph selects an exact per-pass access; UE's RDG extracts the appropriate DSV access from pass parameters. Runtime World/journal alignment is a prerequisite, not a way around the resource error. Region clearing has its own existing camera-stack policy and must stay unchanged.
6. **Concrete gate.** Freeze a non-sheared World → Core2D witness in the existing product submit/renderer tests and preserve a normal Core3D or explicit resolver control. Adapt actual UE raster depth-clear and readback cases (`RHITests.spec.cpp:133–148`, `RHIClearTextureTests.cpp:686–744` for hardware output comparison); don't invent a parallel renderer. Require a real Ready texture, admitted world ID, Core2D, no undeclared-resource/device faults, and current-frame center/outside pixels. Reuse existing ZE [exact resource gate](../../../zircon_runtime/src/graphics/scene/renderer/context/tests/resource_resolver.rs#L86-L117), not an assertion that one string was replaced. After independently verified graph repair, put that exact fix in both local #177 comparison setups before the unchanged affine old/candidate GPU pair; no chart will claim an `opaque-sprite` error is a missing-shear pixel.
