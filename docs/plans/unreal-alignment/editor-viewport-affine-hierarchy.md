# Keep the authored affine hierarchy through the live editor viewport

**Draft — problem statement only.** This change depends on the existing affine draw/bounds path in [#135](https://github.com/He-Jiahui/ZirconEngine/pull/135). The reference for hierarchy behavior is Unity/Three.js, not Unreal's TRS limitation.

1. **Difference.** ZE already computes `parent_world * local_TRS_matrix` in [World propagation](../../../zircon_runtime/src/scene/world/derived_state.rs#L656-L682). The [live editor viewport](../../../zircon_editor/src/scene/viewport/controller/build_render_snapshot.rs#L24-L49) takes a compatibility packet and rebuilds a frame from TRS-only rows instead. [Three.js r180 Object3D](https://github.com/mrdoob/three.js/blob/r180/src/core/Object3D.js#L1116-L1157) carries the matrix through the child chain, and [WebGLRenderer](https://github.com/mrdoob/three.js/blob/r180/src/renderers/WebGLRenderer.js#L2004-L2009) consumes it directly. [Unity Entities LocalToWorld](https://docs.unity3d.com/Packages/com.unity.entities@1.3/manual/transforms-concepts.html) is a rendering matrix and can carry nonuniform scale and shear.
2. **Effect.** Nonuniform parent scale plus child rotation produces a valid, generally nonorthogonal basis. The compatibility extraction can change the displayed shape and give distinct world matrices the same mesh transform revision. These are source-derived symptoms until reproduced via the live editor frame and offscreen renderer.
3. **Cause and reference.** The [packet visitor](../../../zircon_runtime/src/scene/world/render.rs#L93-L126) does not collect the existing affine sideband, so [from_snapshot](../../../zircon_runtime/src/core/framework/render/frame_extract/frame.rs#L90-L106) cannot restore it. Unreal's ordinary attachment multiplies two `FTransform`s (`Engine/Source/Runtime/Engine/Private/Components/SceneComponent.cpp:727–748`); its quaternion/scale recomposition (`Engine/Source/Runtime/Core/Public/Math/TransformNonVectorized.h:1306–1345`) is the distinction, not a shear oracle for this change.
4. **Rust approach.** Carry `WorldMatrix` to the existing view's geometry frame and use the matrix-aware bounds/draw path from #135. First port the [Three.js `localToWorld` control](https://github.com/mrdoob/three.js/blob/r180/test/unit/src/core/Object3D.tests.js#L515-L543), and compare opposite-shear World edits whose TRS projections are equal. Freeze the CPU and actual offscreen observations before changing extraction.
5. **Interface/ECS boundary.** Keep node-authored local TRS, the single derived `WorldMatrix`, cache behavior and GPU layout. Do not promise arbitrary preserve-world reparenting with a TRS-only local authoring representation; [Three.js `attach`](https://github.com/mrdoob/three.js/blob/r180/src/core/Object3D.js#L837-L858) also limits nonuniformly scaled hierarchies. No Prefab, physics, navigation or mirror-UV morph changes.
6. **Concrete ZE change and gate.** Fix one editor viewport frame entry, leaving legacy packet APIs and unrelated rendering settings unchanged. Verify real editor-frame submission and a nonblank offscreen geometry witness with the existing harness, not only projected TRS. Keep #135's own scope separate, and upstream both only through the real required merge checks. Reflection/cubemap packets and full editor-window acceptance are separate.
