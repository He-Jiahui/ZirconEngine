# Rotating a newly created Directional Light does not aim it

Problem-only scope: **a new normal Directional Light**, then a rigid node or parent rotation. ZE publishes the transform, but the outgoing light/shadow direction and the Editor's direction arrow read a separate value. This is the bounded part of the existing [Scene Light authority finding `RSL-P1-013` / `RSL-P1-042`](../optimize/zircon_runtime/71-runtime-scene-light-directional-point-spot-rect-photometry-layer-shadow-cookie-ies-extract-authoring-product-integration-review.md#L219-L270), not a rewrite of lighting, optics, material passes, camera projection, renderer ABI, or Scene propagation. Source diagnosis—not a new behavioral RED or GPU capture.

## ZE route and the visible effect

- The [Editor command](../../../zircon_editor/src/core/editing/command.rs#L499-L517) calls normal `Scene::spawn_node(NodeKind::DirectionalLight)`. [Default node construction](../../../zircon_runtime/src/scene/world/bootstrap.rs#L131-L161) gives the entity a genuine `rotation = Rx(-45°)` and a [distinct nonzero normalized `DirectionalLight.direction`](../../../zircon_runtime/src/scene/components/scene/lighting.rs#L26-L52). The two are not encoded as one pose. A standard transform action updates local TRS and [the scheduled full affine WorldMatrix](../../../zircon_runtime/src/scene/world/derived_state.rs#L656-L681); it does not also edit a light property.
- [Scene extraction](../../../zircon_runtime/src/scene/world/render/lights.rs#L96-L133) uses `light.direction` verbatim. It selects the correct stable entity and layer but doesn't look at its current world orientation. The [Editor arrow](../../../zircon_editor/src/scene/viewport/render_packet.rs#L202-L246) places its origin at the node's world origin and normalizes the same component direction whenever it is nonzero; default lights do not take the fallback. [Packed GPU row](../../../zircon_runtime/src/graphics/scene/renderer/lighting/light_buffer.rs#L184-L195) and [actual deferred shading](../../../zircon_runtime/src/graphics/scene/deferred/shaders/deferred_lighting.wgsl#L163-L179) consume the extracted field, not the node. So dragging Rotate, or rotating a group containing the new sun, changes the pose and axes with no corresponding aim/illumination change. The [normal frame producer](../../../zircon_runtime/src/scene/world/render.rs#L152-L178) calls this collector on the scene. This remains the same on fresh extraction, so changing cache policy, rewriting `WorldMatrix` multiplication, or rotating only the arrow does not solve it.
- [Asset read](../../../zircon_runtime/src/scene/world/project_io/scene_asset.rs#L285-L312) and [save](../../../zircon_runtime/src/scene/world/project_io/scene_asset.rs#L518-L526) persist both the node transform and the direction; [public property enumeration](../../../zircon_runtime/src/scene/world/property_access/entries/lighting.rs#L43-L59) exposes the direction as animatable. Therefore don't reinterpret every old vector as local, discard it, or use a vector equality heuristic to decide legacy format. A legacy world-aim compatibility case must keep its look and its explicit authored field through save/reopen. A real product decision about direction authority and migration, not a component-specific editor workaround, is needed before a production patch. Spot's explicit direction, Point origin, and Rect's degraded renderer are separate coverage; leave their paths unchanged in this slice.

## Actual local Unreal source

[`ULightComponent::GetDirection`](<E:/Git/ZirconEngine/dev/UnrealEngine/Engine/Source/Runtime/Engine/Private/Components/LightComponent.cpp#L1449-L1453>) comes from the component transform's X unit axis; [`SendRenderTransform_Concurrent`](<E:/Git/ZirconEngine/dev/UnrealEngine/Engine/Source/Runtime/Engine/Private/Components/LightComponent.cpp#L997-L1002>) requests the render-side light transform update. [`FScene::UpdateLightTransform`](<E:/Git/ZirconEngine/dev/UnrealEngine/Engine/Source/Runtime/Renderer/Private/RendererScene.cpp#L3505-L3508>) sends the matrix **without scale** and position; [proxy](<E:/Git/ZirconEngine/dev/UnrealEngine/Engine/Source/Runtime/Engine/Private/LightSceneProxy.cpp#L169-L174>) stores light/world transforms, and [shader parameters](<E:/Git/ZirconEngine/dev/UnrealEngine/Engine/Source/Runtime/Engine/Private/Components/DirectionalLightComponent.cpp#L227-L241>) take the signed proxy direction. UE's [Spot visualizer](<E:/Git/ZirconEngine/dev/UnrealEngine/Engine/Source/Editor/ComponentVisualizers/Private/SpotLightComponentVisualizer.cpp#L21-L42>) also removes scale for an optical cone, not for scene geometry. The source distinguishes a rigid emitter orientation from a scene position, and connects one transform authority to render rather than dynamically editing a separate authored property. Do not copy X-axis/sign conventions or UE `FTransform` hierarchy math into ZE. A general sheared/reflected optical orientation needs an explicit policy; a rigid parent witness doesn't settle that policy.

## Smallest regression and acceptance boundary

1. Freeze the existing Runtime scene/extract harness on unchanged production. Create a normal Directional Light using the same Scene spawn entry as the Editor; compare the stable ID's actual pre-rotation direction and `WorldMatrix`. Rotate only the node by `Ry(90°)` with `q1=qDelta*q0` and observe a fresh scheduled matrix, then require direction `qDelta*d0` with the original magnitude. In an independent case rotate a unit-scale parent by the same `qDelta`, without changing child authored TRS or light data, and require the same relative direction change. Use the actual `RenderFrameExtract`, not a DTO constructed by the test. Require positive evidence the pose did change and the extract remained active; a missing light, failed setup, skipped case, or hand-built light buffer isn't RED.
2. Controls: translation-only plus unchanged-row case; an old authored explicit direction preserving its emitted result and unchanged field through load/save, even with nonidentity transform; the existing layer/photometry/property undo paths remain unchanged. Initial new-light appearance should not accidentally change because the default transform and existing direction presently differ. Only after observed genuine RED, compare a clearly owned opt-in/follow mode and narrow compatibility-preserving production change. Keep compiled/reflected direction and serialization contracts explicit, and keep derived `parent_world * local_matrix` intact. Optics may use a defined rigid display orientation; do not erase visible mesh shear or turn a nonsingular affine position into compact TRS.
3. Deliverable verification beyond CPU: a renderer capture from the same Scene-produced light, not a snapshot with a hand-entered direction. Using two diffuse receivers with a known direction contrast and a fixed camera/settings, assert once per selected path that changing parent/node orientation shifts the lit region and/or directional irradiance with the expected sign while translation does not. Preserve normal camera/material/light IDs and exact GPU provenance. Editor Rotate pointer acceptance should follow the same ECS and effect, not merely compare gizmo orientation. Existing directional shadow capture with injected directions is reusable only as a harness/control, not proof of this producer path.
