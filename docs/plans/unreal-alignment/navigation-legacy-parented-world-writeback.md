# Legacy navigation writes a world-space next position as a local transform

**Problem-only Draft.** The owning ZE source matches main `e89349ca51b4e9d024c194cd3bdf645bd25b6c37`. The direct movement path below is verified in source, not yet reproduced by running a test. Separate from physics #145; this Draft contains no engine code or test implementation.

1. **Difference.** The navigation runtime plugin's [registered Update system](../../../zircon_plugins/navigation/runtime/src/plugin.rs#L143-L158) calls the agent manager. With no navmesh loaded, it selects the [Legacy tick](../../../zircon_plugins/navigation/runtime/src/agent.rs#L44-L55). That tick starts from [world position](../../../zircon_plugins/navigation/runtime/src/manager/tick.rs#L51-L62), computes a [world displacement and next pose](../../../zircon_plugins/navigation/runtime/src/manager/tick.rs#L201-L235), and writes that pose through a [local-only ECS setter](../../../zircon_runtime/src/scene/world/hierarchy.rs#L132-L150). UE keeps path following and movement in world space until the component setter converts for the attachment.
2. **Impact.** For a stationary parent at X=10, child local X=1 (world X=11), and a direct +1 world step, the source predicts old child local X=12 and world X=22 rather than local X=2 and world X=12. A root agent masks the defect. Large overshoots can produce wrong stopping or repath decisions; those consequences and the numerical example are not runtime observations yet.
3. **Cause and Unreal evidence.** The adapter omitted the world-to-local boundary. In local UE, `Engine/Source/Runtime/AIModule/Private/Navigation/PathFollowingComponent.cpp:1117–1161` computes a path velocity as `(CurrentTarget - CurrentLocation) / DeltaTime` in the direct-move branch. `Engine/Source/Runtime/Engine/Private/Components/NavMovementComponent.cpp:132–135` stores that velocity; `Engine/Source/Runtime/Engine/Private/FloatingPawnMovement.cpp:37–64` turns it into a world delta. `Engine/Source/Runtime/Engine/Private/Components/MovementComponent.cpp:532–537,564–579` dispatches to `MoveComponent`; `PrimitiveComponent.cpp:3325,3502–3503` sends the resolved world position to the component setter. The attachment conversion happens before relative state is written in `Engine/Source/Runtime/Engine/Private/Components/SceneComponent.cpp:3293–3356`. This is a space/ownership reference, not a requirement to copy Pawn, sweeps, or UE `FTransform` algebra.
4. **Rust approach.** Keep the world-space navigation query/displacement. For position-only updates, convert the requested world point through the checked inverse of the actual parent world matrix; update just authored local translation. This preserves existing local rotation, scale and inherited shear. Use the existing scene/math APIs (the [gameplay-host world transform helper](../../../zircon_runtime/src/script/vm/gameplay_host/transform.rs#L308-L361) already illustrates the checked boundary). Treat requested world facing separately: if a relative orientation is not representable without changing the affine basis, do not silently rewrite authored scale or flatten shear. Freeze a rotation control before extending that behavior.
5. **Interface and ECS.** In UE a movement component owns the world move, with attached-relative values written by its scene component. In ZE a registered dynamic NavMeshAgent can be attached under the [checked hierarchy](../../../zircon_runtime/src/scene/world/hierarchy.rs#L96-L129). The agent manager should not write `WorldMatrix` or detach it. Preserve local authoring, full `parent_world * local`, root behavior and the current movement/reporting contracts; no new ECS component, movement service, or Prefab changes. Crowd, off-mesh traversal, the builtin bridge and DesiredVelocity must be individually qualified; this note makes no executed claim about any of them.
6. **Concrete ZE gate.** Extend the [existing Legacy manager test](../../../zircon_plugins/navigation/runtime/src/tests/manager.rs#L72-L101) with a translated parent plus a root control. Use an empty loaded-navmesh set, one world-space goal X=15, speed 2, `dt=0.5`, acceleration at least 4, no braking/avoidance/facing change; require one move, child local X=2/world X=12, and unchanged parent. The nearest source tests are UE `System.Navigation.NavMesh.Pathfinding.PathHasPoints` (`Engine/Source/Developer/NavigationTestSuite/Private/NavMeshPathfindingTest.cpp:94–126`, world path endpoints) and `System.Engine.Attachment` (`Engine/Source/Runtime/Engine/Private/Tests/EngineAutomationTests.cpp:2022–2085`, world/relative checks). Neither exercises the combined path. Borrow those assertions in the existing ZE harness; the older test currently passes `spawn_node` directly where [the API returns `SceneResult<EntityId>`](../../../zircon_runtime/src/scene/world/bootstrap.rs#L95-L100), a test-build prerequisite to distinguish from behavioral RED. Run the frozen old case first. If it reproduces, only then change the private Legacy writeback; no production or UE executable test has been run for this issue.
