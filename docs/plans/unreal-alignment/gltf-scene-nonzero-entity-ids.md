# glTF source index zero prevents a cooked Scene label from loading

A valid glTF source can put a root or a child at `nodes[0]`. The builtin importer writes source indices directly into Scene entity and parent fields, including the standalone `#Node0` label. `0` is reserved in a ZE World, so an asset can be fully cooked and Ready while a subsequent Level open fails. This blocks the actual hierarchy before any coordinate or render calculation.

## Observed on unmodified Windows r392 Runtime

A project with `default_scene = "res://input.gltf#Scene0"` goes through the actual V8 Headless `create_session` path with no Play scene override. Use two equivalent, valid local representations (explicit signed TRS or column-major local matrices), each with two three-deep hierarchies. Keep mesh data present in the source but remove the three per-node mesh bindings to isolate node identity from the asset-reference owner.

- Both representations cook all 15 assets Ready, then reject the first and cold starts: `entity 0 cannot advance the world identity allocator`. A standalone `#Node0` and a scene where node 0 is a root referenced by a child reproduce the same error. Those are six actual refusals with no session handle.
- Add an unselected dummy source node before the original array and consistently shift the scene/child indices. The same two hierarchies now load on first and cold starts, with the same local transform bits and parent relationship read from the corresponding cooked Scene and real V8 hierarchy. The shifted standalone Node and the shifted root control load as well. Unaffected `#Node4` and `#Scene1` controls also load. Total matrix: 16 native attempts, 8 live sessions, 123 successful query-output releases.
- `#Scene7` is a missing-label control; it does not silently select another scene. The original fixture with mesh references reaches a different error, a dangling `#Mesh0` UUID although the path is published. Keep that separate from this issue and from [#229](https://github.com/He-Jiahui/ZirconEngine/pull/229). Imported tangent handedness and [#141](https://github.com/He-Jiahui/ZirconEngine/pull/141) are separate. No claim that relabeling the fixture fixes either importer.

## Ownership and acceptance

- [Builtin traversal and Scene record creation](../../../zircon_runtime/src/asset/importer/ingest/gltf_labeled_subassets.rs#L167-L195) copy the source index into World-facing fields. [Stable traversal](../../../zircon_plugins/gltf_importer/runtime/src/subassets/scene_traversal.rs#L201-L220) and [its record creation](../../../zircon_plugins/gltf_importer/runtime/src/subassets.rs#L433-L446) have the analogous conversion; the packaged Stable runtime consumer has not been tested in this matrix.
- [The World identity allocator](../../../zircon_runtime/src/scene/world/entity_id_allocator.rs#L39-L60) is the correct guard. The fix belongs at the importer boundary, not in a general relaxation of World IDs or a hidden Level startup fallback. The emitted node IDs and all parent edges must use a consistent nonzero mapping. Keep source-facing labels such as `#Node0` and dependency targets in the source-index namespace. Select the smallest compatible mapping after checking the stability of already-loadable nonzero scene IDs; use an honest importer-version/cache migration if the persisted result changes.
- Freeze actual registered importer-to-Level regression cases for both producers on the same old source: node zero as a root, a child and standalone; nonzero, missing-label, and unaffected rigid controls. Require real Ready import, actual Level startup, label/UUID identity, exact authored TRS and a consistent parent chain for cold reopen. Do not mix this with asset-reference repair, full-affine propagation, Editor gizmos, or rendering. The r392 observation does not certify a current-source native test or a candidate fix.
