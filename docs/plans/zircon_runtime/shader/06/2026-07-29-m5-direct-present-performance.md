## Reason

Historical source measurements split the apparent 82--100 s HDRI load into cold/warm scene construction of about 95.54/87.60 s, with renderer initialization alone accounting for 90.55/86.48 s and an IBL cache restore only about 0.89 s. The current environment-only PBR profile has already removed the dominant DX12 deferred PSO startup cost: cache-reused scene construction is about 8.28 s and Ready is about 19.21 s. Split Ready-frame timing records about 9.87--9.99 s in the CPU wall-clock interval from renderer-frame entry through resource preparation, command encoding, and queue submission return, while `SceneRenderer::render` readback/completion is only 16--40 ms. That interval is not a GPU execution-duration measurement. The direct-surface form additionally includes surface acquisition, the GPU blit, and present before it returns, so its log names the interval `render_and_present_call`. The CPU RGBA readback followed by `SoftbufferViewportPresenter` upload is still an avoidable interactive-path round trip, but it is not the dominant cause of the long first frame. Direct present removes that round trip; GPU attribution remains a separate Render17 timestamp-query task.

Static tracing now identifies the actual first-frame CPU contributor for this viewer: `MeshPipelineCache::new` leaves its Base pipeline map empty, and `ensure_pipeline_for_variant` assembles Standard-PBR WGSL, creates a shader module, and creates a Base render pipeline for the first mesh variant. The environment-only viewer records `BaseScenePass`, not a GBuffer pass. That lazy mesh path is not included in the existing deferred `standard_pso` startup metric, so prewarming deferred lighting alone cannot eliminate it. The next capture must measure this Base-path hypothesis rather than treating it as accepted attribution.

The existing shader-prewarm workflow is not a runtime pipeline cache: it writes WGSL variants to disk and its WGPU pipeline mode creates disposable validation pipelines on a separate offscreen device. It therefore cannot populate this renderer's `MeshPipelineCache` or reuse the DX12 pipeline object that the first PBR frame creates. Any startup optimization must explicitly distinguish disk-source reuse from runtime/driver pipeline prewarming.

`wgpu` 29 does expose a persistent `PipelineCache`, but its documented backend support is currently Vulkan-only. The DX12 viewer therefore cannot use that API to persist the first Base PSO; the current Base descriptor's `cache: None` is not the missing Windows implementation. The practical next step is to measure and reduce the on-device lazy Base creation, or move that known work into an explicitly reported loading phase, rather than adding a cache that cannot serve the target backend.

The viewer must not prewarm by calling the CPU-image `SceneRenderer::render` and discarding its `ViewportFrame`: that would violate the contract which reserves this path for screenshots and image consumers. Shader06 now supplies `MeshPipelineCache::prewarm_environment_only_pbr_base_pipeline`, which resolves the current builtin PBR resource revision from that renderer's `ResourceStreamer` and creates the exact static, no-texture, no-shadow-receiver Standard-PBR Base pipeline in the renderer's own cache without encoding, submission, presentation, or readback. `EnvironmentOnlyPbrPreview` also defers its unused deferred-lighting foundation and PSO until a compiled-graph caller needs them; FullScene retains eager startup construction. Render17 invokes the Base prewarm after `ResourceStreamer` initialization and exposes its synchronous DX12 PSO cost in the startup report. A fresh direct-present run must still prove the first viewer frame reuses that entry; a Render17 generic no-readback offscreen warmup API remains the correct future route for scene-derived variants not covered by this known viewer pipeline.

### 2026-08-13 Structural PSO Identity Audit

The 82--100 s report remains a synchronous DX12 shader/PSO construction diagnosis, not an HDR, PMREM, or IBL-cache diagnosis. The retained decomposition measured the historical eager deferred phase at about 91.74 s while IBL restore was about 1.08 s. Constructor splitting then isolated Standard-PBR PSO construction at 21.80 s, and immediate same-cache process repeats still took 23.04 s and 23.82 s while IBL restore stayed below 846 ms. Later reduced profiles reached 11.65/11.16 s, the environment-only RenderDoc path reached 1.09 s, and a later current-source Debug capture reported 5.97 s. These are historical source-bound measurements; they do not claim that the present worktree has reproduced an 82 s load.

The current source has a separate structural scale risk. `PipelineKey` includes `has_base_color_texture`, `has_metallic_roughness_texture`, `has_occlusion_texture`, and `has_emissive_texture`, but `PipelineKey::shader_feature_bits` does not map those four values into the `ShaderVariantKey`. The fixed material bind-group layout and Standard-PBR material surface continue to provide/sample fallback resources, and render-pipeline state creation does not consume those four values. `MeshPipelineVariantKey`, however, hashes the complete `PipelineKey`, and the pipeline maps are indexed by the resulting variant id. A scene spanning every combination can therefore request as many as 2^4 = 16 registry variants and render-pipeline objects for the same shader variant and render state. This is a theoretical upper bound that must be instrumented before remediation; it is not the cause of the historical single-material 21--24 s Standard PSO measurement, but it can multiply cold compilation in representative multi-material scenes.

Reference-engine evidence argues for separating runtime resource values from compile-relevant shape without discarding real static material differences. Unreal's `FMaterialShaderMapId` owns quality, feature level, static switches/component masks, shader dependencies, and a texture-reference linkage hash (`dev/UnrealEngine/Engine/Source/Runtime/Engine/Public/MaterialShared.h:1345-1424`), while material instances retain mutable `TextureParameterValues` and apply overrides through the uniform-texture expression path (`dev/UnrealEngine/Engine/Source/Runtime/Engine/Private/Materials/MaterialInstance.cpp:6286-6383`). cmftStudio binds a fixed PBR texture set and gates albedo, reflectivity, emissive, surface, and AO sampling with runtime uniforms (`dev/cmftStudio/src/shaders/fs_mesh.shdr:9-22`, `:107-166`). `dev/cmft` remains the offline filter implementation and is not a material-PSO identity owner. Zircon should therefore keep alpha mode, double-sided state, geometry, pass, quality, static PBR features, and binding-layout compatibility in pipeline identity, while treating ordinary texture object presence as runtime material data unless profiling justifies a bounded sample-elision profile.

No identity rewrite is accepted from static inspection alone. The next performance slice must first add source-bound counters for requested `PipelineKey` values, normalized shader/state signatures, unique `ShaderVariantKey` values, shader-module creations, render-pipeline creations, async queue duration, and cache reuse. A deterministic corpus must exercise all 16 combinations with identical pass, geometry, alpha state, normal-map feature, and material layout, then compare three implementations on the same adapter: current runtime-fallback sampling with normalized PSO identity; all 16 sample-elision specializations; and a bounded textureless-versus-general profile. Cold-process DX12 runs must record median and spread across at least three launches, scene construction, Standard/Base PSO wall time, first Ready frame, steady-state GPU timestamp duration, RenderDoc texture-sample/draw evidence, and available process/GPU energy telemetry. Any unavailable power counter must be reported explicitly rather than inferred from frame time.

The first source-bound instrumentation layers are now implemented without changing pipeline identity. `ShaderVariantMissReport` exposes registered full pipeline variants, unique shader variants, variants normalized only across the four ordinary texture-presence booleans, and the resulting texture-presence-equivalent expansion. `MeshPipelineVariantRegistry` maintains those gauges only when it inserts a new key, rather than scanning registry storage per draw or per frame. `MeshPipelineCache` adds live shader-module/render-pipeline residency plus cumulative WGPU shader-module/render-pipeline creation calls and their CPU wall time. The creation timing boundary is the WGPU call only; source assembly, async queue wait, error-scope polling, and cache insertion are excluded. Background Base jobs separately publish the successful-admission-to-job-start wall-clock wait and sample count. Duplicate, full, unavailable-worker, and synchronous paths do not add wait samples. The worker publishes through a shared locked metric snapshot, while cache-hit draw paths do no metric work. Normal lazy paths and live-manifest prewarm both record calls before later validation-scope resolution, so failed creations are not hidden. `DiagnosticStore` publishes all twelve gauges under `render.shader_variant.*`. Pure regressions lock the 16 full / 1 normalized / 15 equivalent result, prove that TAA pipeline kind plus normal-map shader-feature differences survive normalization, verify saturating time conversion and coherent count/time snapshots, and require first synchronous/background/live-manifest creation to count while repeated cache hits leave counts and time unchanged. GPU timestamps, power telemetry, and the three-run cold-process corpus remain required before any identity optimization is selected.

The mandatory incremental review initially found that live-manifest prewarm bypassed the new creation metrics even though it performed real WGPU shader-module and render-pipeline calls. The forward repair now records ordinary, TAA companion, and OIT creations immediately after each call and before validation-scope resolution; a complete manifest cache hit returns before timing or metric locking. The repeated live-prewarm regression locks zero count/time growth. Renewed independent review reports `Critical 0 / Important 0`. This is static implementation/review evidence only and does not replace the outstanding managed WGPU, cold-process DX12, screenshot, or RenderDoc gates.

### 2026-08-13 Ready-Frame Evidence Checkpoint

The viewer now writes schema v12 metadata only after its Base pipeline is ready and the CPU-readback render for that same frame has completed. It reads the renderer-lifetime `ShaderVariantMissReport` after rendering, then carries all twelve PSO gauges into the sidecar: registered and shader variants, normalized and equivalent variants, render-pipeline and shader-module residency, creation counts and CPU microseconds, plus successful async-admission queue-wait counts and microseconds. The validator requires this v12 shape by default, retains v2--v11 only behind `--allow-legacy-schema`, and rejects inconsistent count, residency, normalization, and zero-wait invariants. Independent post-repair review reports `Critical 0 / Important 0`; it also confirms that EnvironmentOnly direct rendering does not call deferred lighting and that existing lazy profile gates avoid constructing unused deferred PSOs. This is implementation and static-review evidence only. M5 remains `in_progress` until a fresh managed DX12 run produces the required current-source screenshot sidecar, timing, and RenderDoc replay.

Implementation may start only after that comparison identifies the best total-cost option. The minimum acceptance bar is: resource-presence-only differences cannot create duplicate shader/state-equivalent PSOs; prewarm serialization keeps enough material metadata to recreate the intended runtime bindings; shader-module and PSO counts are reduced on the 16-combination corpus; no direct-light, AO, IBL, transparency, double-sided, or advanced-PBR behavior changes; and both cold-start CPU time and steady-state GPU/sample cost are reported so compile-time savings are not purchased by an unmeasured frame-time regression. A likely structural direction is a dedicated compile-relevant pipeline-shape key plus a bounded texture profile, but the measurement gate intentionally leaves the final choice open.

## Scope

- Expose a `SceneViewportSurface` owned by `SceneRenderer`, created only after the native window exists.
- Render the existing final sRGB offscreen texture through the backend's GPU surface blit and present it without `ViewportFrame` construction or texture readback.
- Preserve the CPU `SceneRenderer::render` contract exclusively for screenshot/image consumers.
- Invoke the Shader06-owned exact-cache Base prewarm after `ResourceStreamer` initialization for the known environment-only Standard-PBR viewer variant; keep its synchronous cost explicitly reported as startup work.
- Use a Render17-owned no-readback offscreen warmup API only for scene-derived variants beyond that known cache key; do not call the CPU-image `SceneRenderer::render` only to discard its output.
- Keep the PBR viewer fallback deterministic: if direct presentation cannot acquire or validate the native surface, detach it and request one CPU-present redraw.
- Record direct-present timing only when a one-shot RenderDoc capture requests it. Its readback interval must remain zero, while the log retains the separate `render_and_present_call` CPU wall-clock interval for follow-up diagnosis. GPU duration requires a Render17 timestamp-query report.
