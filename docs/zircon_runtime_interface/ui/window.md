# UI Window Input Contracts

`zircon_runtime_interface::ui::window` owns the neutral M1 window-event and input-pump DTO vocabulary. It is an interface-only subtree: runtime winit, editor native/Slint, and future app-host converters may emit these records, but platform event-loop behavior remains outside `zircon_runtime_interface`.

The 2026-06 host-editor UI foundation continuation extends this boundary with a Slate-style application intake contract. `UiWindowPlatformInputEvent` now normalizes pointer, keyboard, text, IME, navigation, analog, touch, drag/drop, popup, tooltip timer, and accessibility requests into the single shared `UiInputEvent` enum consumed by the runtime surface dispatcher. Window activation callbacks enter through `window_activation_changed(...)` with `UiWindowActivation::Activate`, `ActivateByMouse`, or `Deactivate`; application activation callbacks enter through `application_activation_changed(...)`. Both routes deliberately reuse the existing `Focused { focused }` window event so platform adapters can name the source callback without creating a second focus state model. Window action callbacks enter through `window_action(...)` with `UiWindowAction::ClickedNonClientArea`, `Maximize`, `Restore`, or `WindowMenu`; the event records the host action fact without deciding whether the platform should continue processing it or whether menu stacks should close. IME preedit and commit intake can preserve a platform-provided cursor byte range through `ime_with_cursor_range(...)`, while the older `ime(...)` helper remains the no-range convenience path. GenericApplication-style mouse move callbacks enter through `mouse_move(...)`, preserving the cursor point while mapping to Zircon's existing `Pointer/Move` dispatcher contract. Cursor-enter notifications can enter through `cursor_entered(...)`, which deliberately reuses `Pointer/Move` so hover-path recomputation stays in the runtime dispatcher instead of becoming a second platform-only route. Cursor-leave and capture-loss notifications enter through `cursor_left(...)` and `mouse_capture_lost(...)`, both mapping to `Pointer/Cancel` so the downstream route layer can clear hover, capture, drag, and tooltip state through the same cancellation vocabulary used by close/destroy cleanup. Mouse button callbacks enter through `mouse_button_down(...)` and `mouse_button_up(...)`, preserving the platform button and cursor point while mapping to Zircon's existing `Pointer/Down` and `Pointer/Up` dispatcher contract. Mouse-wheel callbacks can enter through `mouse_wheel(...)` for line-based scroll or `mouse_wheel_delta(...)` for precise x/y scroll units; both create a `Pointer/Scroll` input while preserving the scalar y delta for legacy consumers and the full precise-scroll payload for newer routing/render consumers. Double-click callbacks enter through `mouse_double_click(...)`, which preserves the button and cursor point while mapping to Zircon's existing `Pointer/Up` plus `click_count = 2` dispatcher contract. Keyboard callbacks can enter through `key_down(...)`, `key_up(...)`, and `key_char(...)`, preserving repeat state and routed character payloads in the existing shared keyboard DTO. Controller button callbacks enter through `controller_button_pressed(...)` and `controller_button_released(...)`, preserving the button name as both physical and logical key text so existing `Virtual_Accept`, `Virtual_Back`, and gamepad D-pad keyboard-route contracts remain the shared activation/navigation vocabulary. Controller analog callbacks enter through `controller_analog(...)`, preserving the control name and pressure value in the existing analog DTO used by runtime analog navigation. Touch callbacks enter through `touch_started(...)`, `touch_moved(...)`, `touch_ended(...)`, and `touch_canceled(...)`, preserving the platform touch id as `pointer_id` while mapping the phases onto Zircon's shared pointer Down, Move, Up, and Cancel contract. Slate-style touch force and first-move callbacks enter through `touch_force_changed(...)` and `touch_first_move(...)`; both accept the force argument for platform callback parity but intentionally normalize as `Pointer/Move` without retaining pressure until Zircon has a shared pointer-pressure DTO. External or retained drag callbacks can enter through `drag_enter(...)`, `drag_over(...)`, `drag_leave(...)`, `drag_drop_at(...)`, and `drag_end(...)`, preserving point, session id, and payload evidence while mapping to the existing shared drag/drop dispatcher kinds. This keeps platform adapters out of widget routing while making every input family enter through one dispatcher vocabulary.

## Reference Anchors

Unreal Slate is the primary reference for the 2026-06 input expansion. `dev/UnrealEngine/Engine/Source/Runtime/ApplicationCore/Public/GenericPlatform/GenericApplicationMessageHandler.h` exposes platform-facing key down/up/char, mouse move, mouse down/up, wheel, double-click, controller button, controller analog, touch started/moved/ended/force-changed/first-move, window activation, application activation, window action, size change, OS paint, resizing, moved-window, and window-close callbacks, and `dev/UnrealEngine/Engine/Source/Runtime/Slate/Private/Framework/Application/SlateApplication.cpp` centralizes pointer routing, window metrics, drag/drop enter-over-drop-leave, tooltip updates and close requests, menu dismissal, and accessibility message handling around `FSlateApplication` before widget handlers run. The same file routes key down/up and character input through `ProcessKeyDownEvent`, `ProcessKeyUpEvent`, and `ProcessKeyCharEvent` along the focus path, routes pointer movement through `ProcessMouseMoveEvent` and `RoutePointerMoveEvent`, routes touch callbacks through `ProcessTouchStartedEvent`, `ProcessTouchMovedEvent`, and `ProcessTouchEndedEvent` into the shared pointer path, treats touch force changes and first-move notifications as touch-move processing, translates `EWindowActivation::Activate`, `ActivateByMouse`, and `Deactivate` in `OnWindowActivationChanged`, routes process-level active/inactive changes through `OnApplicationActivationChanged`, forwards `EWindowAction::ClickedNonClientArea`, `Maximize`, `Restore`, and `WindowMenu` through `OnWindowAction`, updates cached window size/position from size and move callbacks, draws or flushes renderer state from OS paint/resizing callbacks, and converts window-close callbacks into destroy requests. Zircon translates that shape into Rust DTO normalization rather than copying Slate's C++ event loop, renderer flush calls, menu dismissal policy, OS action-consumption policy, or text input method objects.

Bevy remains the platform-neutral cross-check for the original window module. `dev/bevy/crates/bevy_window/src/event.rs` models window events as platform-neutral messages for cursor moved/entered/left, focus, resize, scale factor, redraw, close, lifecycle, file drag/drop, theme, mouse, keyboard, touch, and IME traffic. `dev/bevy/crates/bevy_winit/src/state.rs` converts winit cursor movement into logical coordinates plus optional delta, clears cached cursor position on cursor leave, emits focus/IME/resize/move events, and treats redraw requests as a separate event-loop concern.

Fyrox is the Rust-native editor/runtime cross-check. `dev/Fyrox/editor/src/lib.rs` handles resize, focus, move, scale factor, and redraw at the editor window boundary, then translates applicable winit events into UI OS events through `dev/Fyrox/fyrox-impl/src/utils/mod.rs`.

Godot is the UI/editor platform vocabulary cross-check. `dev/godot/servers/display/display_server.cpp` binds window event constants for mouse enter/exit, focus in/out, close request, DPI change, force close, and output color metadata. Zircon keeps Rust DTO names and does not mirror Godot's C++ enum names directly.

## Module Shape

`metadata.rs` defines `UiWindowEventMetadata`, which carries a shared `UiWindowId`, timestamp, sequence, and synthetic flag. It deliberately reuses the input metadata clock and sequence types so window events and `UiInputEvent` records can be ordered in one pump stream.

`metrics.rs` defines `UiWindowMetrics`, `UiWindowPixelSize`, and `UiWindowPixelPosition`. Logical size uses existing `UiSize`; physical size and position stay integer pixel DTOs. `scale_factor` defaults to `1.0` for old or partial payloads.

`event.rs` defines `UiWindowEvent`, `UiWindowEventKind`, `UiWindowActivation`, `UiWindowAction`, and `UiWindowRedrawReason`. Current M1 kinds cover created, close requested, closed, destroyed, cursor moved/entered/left, focus, occlusion, resize, scale-factor changes, backend scale-factor changes, move, window action, and redraw request. Host-facing helpers `window_focused(...)`, `window_activation_changed(...)`, `application_activation_changed(...)`, `window_action(...)`, `size_changed(...)`, `os_paint(...)`, `resizing_window(...)`, `moved_window(...)`, `window_close(...)`, and `request_redraw(...)` map common `GenericApplicationMessageHandler` window callbacks onto those existing DTOs without introducing a second platform event schema. `UiWindowActivation` preserves the source activation kind for adapter call sites, while `Activate` and `ActivateByMouse` both normalize to focused and `Deactivate` normalizes to unfocused. `UiWindowAction` preserves non-client click, maximize, restore, and window-menu action kinds as clean window events because the interface layer records the platform callback fact and leaves OS continuation plus menu-stack policy to runtime/editor hosts. `os_paint(...)` and `resizing_window(...)` deliberately become `RequestRedraw { reason: Paint }`; renderer flush/draw policy stays in the runtime/editor host, not in the interface crate. IME and text remain represented by the existing shared `UiInputEvent` families instead of duplicating text-input payloads in the window module.

`input.rs` defines `UiWindowInputContext`, `UiWindowPlatformInputEvent`, and `UiWindowPlatformInputEventKind`. The context attaches stable timestamp, sequence, window, user, device, surface, pointer, source, modifier, and synthetic metadata before normalization. The platform event kind is deliberately a thin adapter envelope: it preserves family-specific fields such as precise scroll deltas, IME cursor ranges, drag session and payload, popup owner/anchor, tooltip owner, and accessibility action request, then emits the matching `UiInputEvent` variant. `mouse_move(...)`, `cursor_entered(...)`, `cursor_left(...)`, `mouse_capture_lost(...)`, `mouse_button_down(...)`, and `mouse_button_up(...)` are host-facing helpers for GenericApplication-style pointer callbacks that already know the cursor point; hosts that need unusual pointer payloads still use the generic `pointer(...)` envelope. Cursor enter intentionally behaves like a move and cursor leave or capture loss intentionally behaves like cancel because the runtime surface, not the platform adapter, owns hover-path diffing and cancellation side effects. `mouse_wheel(...)` is the simple line-wheel helper, while `mouse_wheel_delta(...)` accepts an explicit `UiPreciseScrollDelta` so hosts can preserve pixel scroll and horizontal scroll without inventing a separate input event family. `mouse_double_click(...)` does not create a new pointer kind, and instead feeds the shared pointer dispatcher the already-tested button-release double-click representation. `key_down(...)` maps repeat callbacks to `UiKeyboardInputState::Repeated` and normal key-down callbacks to `Pressed`; `key_up(...)` maps to `Released`; and `key_char(...)` keeps Slate-style character intake in the keyboard family by attaching the character to `text` while preserving repeat state. `controller_button_pressed(...)` and `controller_button_released(...)` map host controller buttons into the same keyboard DTO instead of introducing a parallel gamepad-button route; runtime navigation and default action layers already interpret `Gamepad_DPad_*`, `Virtual_Accept`, and `Virtual_Back` from that vocabulary. `controller_analog(...)` is the named GenericApplication-style controller axis helper over the existing analog envelope, preserving the platform control name and value for runtime analog navigation thresholds and repeat timing. `ime(...)` creates a no-range IME payload for simple hosts, while `ime_with_cursor_range(...)` keeps preedit caret/selection range evidence from the platform. `touch_started(...)`, `touch_moved(...)`, `touch_force_changed(...)`, `touch_first_move(...)`, `touch_ended(...)`, and `touch_canceled(...)` are named GenericApplication-style helpers over the generic `touch(...)` envelope; they normalize into pointer events with touch source metadata and stable pointer id, while the force-specific helpers use the move phase until pointer pressure becomes a shared dispatcher field. `drag_enter(...)`, `drag_over(...)`, `drag_leave(...)`, `drag_drop_at(...)`, and `drag_end(...)` are named GenericApplication-style drag/drop helpers over the generic `drag_drop(...)` envelope; they do not add a second external-drag schema, and instead preserve Zircon's existing `UiDragPayload` plus drag session id contract for the runtime route layer.

`impact.rs` defines `UiWindowEventImpact`, a declarative dirty/consequence summary. It encodes the M1 acceptance semantics directly: cursor leave clears hover and requests redraw, scale-factor changes mark layout metrics dirty without mutating input state or forcing redraw by themselves, resize marks layout metrics dirty and redraws, and close requests are distinguishable from closed/destroyed cleanup events.

`pump.rs` defines `UiWindowInputPumpEvent` and `UiWindowInputPumpBatch`. A pump event is either a window event or an existing shared `UiInputEvent`; this prevents runtime/editor hosts from inventing a second input vocabulary. `push_platform_input(...)` normalizes a `UiWindowPlatformInputEvent` before adding it to the same batch, keeping the host-facing event intake on one path. `push_coalesced(...)` drops only consecutive redraw requests so repeated redraw notifications do not flood later M1 consumers, while preserving cursor/input ordering around redraws.

## Boundary

This module does not translate winit, Slint, Godot, or Fyrox events. It does not clear hover, dirty layout, request platform redraw, close windows, or mutate runtime/editor state. Those behaviors belong to later runtime and editor M1 slices after active platform/window/input sessions settle.

The contract tests in `zircon_runtime_interface/src/tests/window_input_contracts.rs` prove the DTOs are constructible, serializable, and carry the intended impact/coalescing semantics. They also pin that every shared dispatcher input family currently covered by `UiWindowPlatformInputEvent` preserves window metadata during normalization. The 2026-06-06 focused checks additionally prove that IME normalization preserves an optional preedit cursor byte range, mouse move and cursor-enter callbacks normalize into `Pointer/Move`, cursor-leave and mouse-capture-loss callbacks normalize into `Pointer/Cancel`, mouse button callbacks normalize into `Pointer/Down` and `Pointer/Up`, mouse-wheel callbacks normalize into scroll pointer events with line-based or explicit precise deltas, mouse double-click callbacks normalize into `Pointer/Up` with `click_count = 2`, key down/up/char callbacks normalize into the existing keyboard dispatcher contract with repeat and character payload state, controller buttons normalize into the same keyboard contract used by gamepad D-pad and virtual Accept/Back routing, controller analog callbacks normalize into the existing analog dispatcher contract, touch started/moved/force-changed/first-move/ended/canceled callbacks normalize into the existing pointer dispatcher contract with touch source and pointer id metadata, drag enter/over/leave/drop/end callbacks normalize into the existing drag/drop dispatcher contract with point, session id, and optional payload evidence, and platform envelopes can enter the input pump through `push_platform_input(...)`. The 2026-06-07 window event checks additionally prove that platform focus, window activation, application activation, window action, size-change, OS-paint, resizing, moved-window, and window-close helpers preserve the existing focus/action/resize/redraw/move/close impact semantics and JSON round-tripping. These interface checks do not claim workspace-wide validation or runtime/editor host conversion.
