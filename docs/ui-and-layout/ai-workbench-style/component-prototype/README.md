# Workbench Component Prototype

This prototype rebuilds `E:/Git/ZirconEngine/docs/ui-and-layout/workbench.png` as a component stack inside the normalized `ai-workbench-style` design workspace instead of wrapping the reference PNG.

## Build Order

1. `tokens.css` extracts the fixed dark editor palette, 1672x941 reference dimensions, compact 30 px controls, 1 px separators, low radii, and teal active states.
2. `layout.js` and `layout.css` provide reusable box, stack, cluster, and grid primitives for direction, wrapping, columns, shared gaps, left/center/right placement, and cross-axis alignment.
3. `icons.js` defines local inline SVG icons, so buttons and tree/list rows are not dependent on an icon package.
4. `atoms.js` and `atoms.css` provide buttons, icon buttons, inputs, checkboxes, radio buttons, switches, tabs, segmented controls, selects, number fields, and sliders.
5. `collections.js` and `collections.css` compose tree view, table view, list view, popup menu, alerts, tooltip, and toast. List, table, and menu rows are real buttons with stable action identities, so the same collection grammar can be used inside fixed side menus, data tables, and transient popup menus.
6. `surfaces.js` and `surfaces.css` compose the top toolbar, left rail, legacy scene drawer/viewport, inspector window, UI component drawer, and status bar through explicit `workbenchWindow` and drawer/window surface helpers; Scene, Inspector, and Showcase tabs consume the shared `panelGroup` primitive instead of duplicating local tab/view markup.
7. `module-components.js` contains the shared module surface primitives: left/main/right/bottom regions, cards, panel groups, panel tabs, right detail panels, bottom output drawers, generated bottom drawer panels, settings rows, list/tree/table rows, graph nodes, timelines, preview tiles, and tags. Module table rows derive their `data-action` and `aria-label` from the first readable content cell instead of a row index, so response hashes and accessible names stay meaningful across repeated tables.
8. `core-modules.js` owns the 11 native-synced core module registry entries: module IDs, labels, icons, status text, toolbar actions, and the left/center/right/bottom renderer wiring. The default Gameplay Effect module follows the approved shell direction from `ai-gameplay-effect-layout.png`; Scene, Gameplay Ability, Gameplay Tags, AI Perception, Material, Behavior Tree, Render Pipeline, Asset Browser, VFX, and HUD Editor reuse the same left/main/right/bottom workbench regions while borrowing only the core function grouping from their AI reference images.
9. `core-module-lefts.js` owns the 11 native-synced core module left panel bodies: tool palettes, trees, filters, asset browsers, debug toggles, and embedded Tags/HUD card panel groups. It keeps the registry file free of page-local drawer composition while still using the same shared panel, list, tree, settings, action, and panel-group primitives.
10. `core-module-centers.js` owns the 11 native-synced core module center workspaces and their specialized Perception map / HUD canvas helpers. It keeps graph boards, timelines, asset strips, stats, and fill-canvas compositions out of the registry file while still composing them from the shared module primitives. The module main, left, and right regions use shell-bound stretch constraints at desktop widths, while HUD and Perception editor grids make their primary canvas card a fill container instead of a fixed-height preview.
11. `core-module-details.js` owns the 11 native-synced core module right-detail panel groups. It keeps routeable Inspector/Details/Resources/etc. panels on the shared `panelGroup` primitive while `modules.js` stays focused on top tabs, rail entries, toolbar actions, and workspace assembly.
12. `core-module-bottoms.js` owns the 11 native-synced core module primary bottom output bodies. It keeps compile logs, validation tables, timelines, import progress, alerts, and bottom output settings out of the registry file while `bottomOutput()` still wraps them in the shared `panelGroup` drawer and generated secondary tabs.
13. `modules.js` and `modules.css` aggregate the core registry, More Editors library, and prototype-only extension modules into top tabs, rail entries, module toolbar, and the left/main/right/bottom workspace assembly.
14. `reference-samples.js` classifies the 59 PNG samples in the parent AI reference directory: 11 native-synced core module references, 44 prototype-only extension references, and 4 supplemental workbench/style references.
15. `extension-blueprints.js` owns the reference-specific function data for all 44 prototype-only More Editors panels: toolbar actions, left tools/assets, center primary table/graph/queue/timeline panels, right detail tabs, settings, metrics, and output rows.
16. `extension-configs.js` combines the reference manifest, reference-specific blueprints, and category fallback recipes into 44 extension module configs. It owns layout-kind selection, generated fallback tools/settings/assets/tables, hydrated controls, and title casing so the surface generator does not also carry recipe policy.
17. `extension-library.js` owns the More Editors library module: category groups, extension cards, coverage/routing right panel, bottom coverage output, and a Reference Blueprint Drilldown panel that exposes representative source images, layout grammars, component families, and route response behavior through the shared `panelGroup`, tables, settings, asset strips, and buttons.
18. `extension-surfaces.js` renders the 44 prototype-only More Editors module surfaces from prepared configs: left Reference/Tools/Assets drawers, center blueprint workspaces, right detail `panelGroup`s, bottom Output/Validation/References/Handoff drawers, and the reference-specific table/graph/queue/timeline helpers. It keeps shared `panelGroup`, table, settings, alert, asset-strip, tree, graph, timeline, preview, and button composition out of the module factory.
19. `extension-modules.js` generates the 44 prototype-only More Editors module records from the prepared extension configs. It wires module metadata, toolbar actions, left/center/right/bottom renderer callbacks, and the More Editors library into the shared workbench shell while leaving config generation and surface rendering to their focused files.
20. `extension-handoff.js` owns the visible web-to-native checklist for prototype-only extension modules. It keeps pending `.zui` workspace, retained route, preview action, and matrix-review states in a shared table/settings/alert composition instead of burying that migration status in page-specific prose.
21. `routes.js` maps prototype commands to module and panel destinations. Global commands can still jump across modules, while generic toolbar labels such as Compile, Preview, Build, Validate, Play, and Debug first resolve through the active module so repeated controls land on the matching output/details panel. Prototype-only extension commands route by command verb to their own Output, Validation, References, or Handoff bottom panel.
22. `app.js` mounts the window helper and wires small interactions for module navigation, URL hash deep links for modules, panels, and the latest command response, browser history restore, command routing, command feedback, tab switching, panel view switching, tree/list/table selection, keyboard activation for non-native button rows, toggles, dropdown popup placement, and popup menu selection/close feedback.

## Component Families

The prototype follows the same bottom-up grouping used by mature component libraries such as Material UI, but keeps the implementation local and dependency-free:

- Foundation and layout: tokens, box, stack, cluster, grid, window shell, drawers, panels, tab strips, toolbars, and status regions.
- Inputs: buttons, icon buttons, fields, selects, number fields, checkboxes, radios, switches, tabs, segmented controls, and sliders.
- Data display: scene tree rows, inspector property rows, table rows, list rows, and menu rows.
- Feedback: alerts, tooltip, toast, focused/selected/checked/disabled states, and popup placement.
- Surface chrome: top bar, activity rail, module tabs, module toolbar, module left drawer, module main editor, module right details window, module bottom output drawer, popup layer, and status bar.

Layout corrections should start by choosing the right foundation primitive and shared token. Per-control pixel adjustments are a late polish step, not the primary way to make repeated controls consistent.

## Fidelity Rules

- UI chrome and controls are HTML/CSS/SVG components.
- The whole `workbench.png` is not embedded as a screenshot.
- The central scene viewport is also HTML/CSS: it uses layered DOM elements for hangar bands, side walls, left stair/rack detail, rear-wall detail lines, an octagonal door, floor grid, floor grate, floor seam, floor reflection, lightwash overlays, shadow overlays, handrails, wall columns, amber beacons, selected prop, transform axes, cargo silhouettes with inner frames, lights, and the orientation gizmo instead of a cropped raster reference.
- The 1672x941 viewport is the strict reference size for visual QA. Smaller viewports use responsive media queries while preserving the same component hierarchy.

Each module has a shareable hash route such as `index.html#module=gameplay-effect`, `index.html#module=editor-library`, `index.html#module=shader-editor`, or `index.html#module=weather-editor`; unknown module hashes normalize back to `gameplay-effect`. Module tabs, rail items, extension cards, and routed commands update the hash, so browser Back/Forward restores the visible module state.

Panel tabs and routed commands can also store a panel target through `panel=<data-panel-tab>`, for example `index.html#module=gameplay-effect&panel=module-bottom-gameplay-effect%3Acompile-log`, `index.html#module=asset-browser&panel=asset-right%3Ametadata`, and `index.html#module=shader-editor&panel=shader-editor-right%3Aresources`. Invalid panel hashes are removed instead of forcing an unrelated panel open.

Ordinary control responses also store the latest response through `command=<id>` without changing the layout, for example `index.html#module=gameplay-effect&command=save`, `index.html#module=gameplay-effect&command=tree-ge-healthregen`, `index.html#module=gameplay-effect&command=row-healthregen`, or `index.html#module=gameplay-effect&command=edit-search-assets`. Loading one of these URLs restores the visible module and records the last prototype response in browser history; it does not execute engine behavior.
