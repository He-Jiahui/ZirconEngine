# Cargo 构建产物生命周期可视化设计

日期：2026-07-12  
所属计划：`docs/plans/zircon_tooling/session_coordinator/01-workflow-control-center-and-tray.md`  
所属里程碑：M6  
状态：已获用户确认并完成实现；随 M6 等待 24 小时稳定性门禁与里程碑提交

## 目标

让操作人员在现有 Jenkins 式“验证”页面直接判断 Cargo 构建产物是否可复用、何时清理以及是否发生清理失败。页面只投影协调服务已经持久化的生命周期状态，不创建第二套存储治理逻辑，也不提供绕过服务的手工删除入口。

## 采用方案

在现有验证页面增加紧凑摘要和扩展后的 Cargo 作业表，不新建导航页面：

- 摘要卡显示可复用池、临时产物、待清理和清理失败数量。
- Cargo 表新增 Session、产物策略、兼容键、复用来源、清理状态和清理错误。
- 兼容键和复用来源使用短标识显示，完整值保留为原生标题文本，便于审计且避免撑宽表格。
- 状态同时使用中文文本和现有 `StatusText` 视觉语义，不能只依赖颜色。
- 清理错误按普通文本渲染，不解释 HTML；没有错误时显示 `—`。

这一方案比只增加列更容易快速识别磁盘风险，又比新增独立存储页面更少导航、状态和维护成本。

## 数据边界

后端快照已经从 `cargo_jobs` 返回完整行，前端只需把下列既有字段纳入严格运行时契约：

- `reuse_key`
- `compatibility_key`
- `reuse_profile`
- `reused_from_job_id`
- `cleanup_policy`: `retained | delete_on_release`
- `cleanup_status`: `retained | pending | deleted | failed`
- `cleanup_error`

页面不得推导新的服务真相。摘要完全由当前有界快照中的 `cargoJobs` 计算，因此表示“当前页面快照内的作业记录”，不声称是磁盘目录扫描结果。物理删除、失败重试、LRU 回收和路径安全验证仍只由协调服务执行。

## 显示规则

- `retained` 策略显示“可复用”；`delete_on_release` 显示“用后即删”。
- `retained/pending/deleted/failed` 清理状态分别显示“保留中/待清理/已清理/清理失败”。
- 可复用池摘要按唯一非空 `compatibility_key` 去重，避免同一池的历史作业重复计数。
- 临时产物、待清理和清理失败摘要按作业记录计数。
- 缺失兼容键的可复用记录仍显示 `—`；Schema v23 会在服务迁移时把这类历史记录降级为用后即删，页面不自行改写状态。
- 表格继续有界渲染，并保持键盘可访问和非颜色状态文本。

## 错误处理

- 严格契约拒绝缺失生命周期字段或未知枚举值，触发现有安全刷新/错误边界，不静默猜测。
- `cleanup_error` 只作为服务端已清洗文本显示；浏览器不得执行其中的标记。
- 页面不显示凭据、环境变量、原始命令输出或任意文件内容。

## 验证

- 契约测试覆盖完整字段、未知策略和未知清理状态拒绝。
- 组件测试覆盖唯一池计数、临时/待清理/失败摘要、中文状态、短兼容键、复用来源和纯文本错误。
- 现有生产前端 `npm run check` 必须继续通过类型检查、全部组件测试、生产构建和递归产物图审计。
- 现有 Python 快照测试确认生命周期字段来自 `cargo_jobs`，不新增数据库或 API。

## 非目标

- 不增加浏览器手工删除、强制清理或更改保留策略动作。
- 不扫描磁盘目录，不估算目录大小，不创建第二套 cleanup 状态。
- 不修改 Cargo 生命周期、Schema v23、LRU 或守护进程清理算法。
- 不新增页面、路由、数据库表、托盘菜单或 Zircon Hub 入口。
