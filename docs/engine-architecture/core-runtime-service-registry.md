# Core Runtime Service Registry

## Purpose

这份文档记录 `zircon_runtime::core::runtime` 目录化后的当前边界。目标不是改变 `CoreRuntime` 的公开契约，而是把 descriptor、上下文、handle 行为和内部状态拆成可扩展子树，并明确 plugin 构造链现在已经从普通 `ServiceFactory` 分流为显式 `PluginFactory + PluginContext`。

## Core Spine Ownership Decisions

`docs/plans/zircon_runtime/runtime/02-core-spine-and-root-surface.md` 在 2026-06-12 定稿了 `core/` 根散件的后续归属。执行迁移前，以本节为同步口径；不要把这些散件继续扩展在 `core/` 根下。

| Former/current root item | Target owner | Facade decision | Reason |
|---|---|---|---|
| `config_store.rs` (moved 2026-06-12) | `core::runtime::config_store` | root `ConfigStore` export removed | `ConfigStore` is the `CoreRuntime` backing store; `core::manager` only exposes handles. |
| `frame_clock.rs` (moved 2026-06-12) | `core::runtime::frame_clock` | curated facade still exposed through `core::runtime::FrameClock` and root `core::FrameClock` | Frame delta is driven by the runtime tick path. |
| `channel_util.rs` | split: `core::framework::channel` and `core::runtime::tasks` | remove the three root helper exports | Channel wait helpers are neutral; named thread spawning belongs to runtime task execution. |
| `types.rs` | split: `core::framework::channel` and `core::runtime::descriptors` | remove root `ServiceObject` export | Channel aliases are neutral contracts; service object storage is runtime registry internals. |
| `error.rs` (moved 2026-06-12) | `core::framework::error` | keep `CoreError` / `ZirconError` facade through the curated `core` root | Errors cross framework traits, manager handles, and runtime services. |
| `event_bus.rs` + `event_bus/` (moved 2026-06-12) | split: `EngineEvent` to `core::framework::events`, `EventBus` implementation to `core::runtime::events` | keep `EngineEvent` / `EventBus` through root `core` facades, but remove the old `core::event_bus` namespace | Event DTOs are neutral; subscriber storage and delivery locks are runtime behavior. |
| `time.rs` | `core::runtime::time` | keep `RuntimeTime*` and diagnostics constants facade | Runtime time advances the neutral real/virtual/fixed clock contracts. |
| `job_scheduler.rs` | `core::runtime::tasks::job_scheduler` | keep `JobScheduler` through `core::runtime` and root `core` facades until the task slice settles | It is a compute facade over runtime task pools. |
| `tasks/` (moved 2026-06-12) | `core::runtime::tasks` | keep individual task-pool type facades through root `core`, but remove the old `core::tasks` namespace | Task pools are runtime execution infrastructure; descriptors already live in `framework::tasks`. |
| `state/` (moved 2026-06-12) | `core::framework::state` | keep individual state contract facades through root `core`, but remove the old `core::state` namespace | State contracts are Bevy-style neutral scheduling contracts. |
| `modules/` (moved 2026-06-12) | `core::runtime::modules` | keep individual descriptor/constant facades through root `core`, but remove the old `core::modules` namespace | Core modules are runtime module assembly. |
| `lifecycle.rs` (moved 2026-06-12) | `core::runtime::lifecycle` | keep lifecycle public facade through `core::runtime` and root `core` | Lifecycle and service kind vocabulary belongs to the runtime kernel. |
| `diagnostics/` (moved 2026-06-12) | `core::runtime::diagnostics` | keep `core::diagnostics` as a curated facade through the runtime owner; do not create a sixth long-term root spine seat | Diagnostics are runtime observability owned by `CoreRuntime` and runtime services. |

`foundation/runtime/config_manager.rs` and `foundation/runtime/event_manager.rs` remain wrappers over `CoreHandle`; they do not own the underlying config store or event bus behavior. M2 migration should update their `use` paths only.

## Registry Name Contract

`ModuleDescriptor::name` 是 module registry 的 canonical key。`CoreRuntime::register_module(...)` 在拿到 module lock 之前先拒绝空 module name 和首尾包含空白的 module name；这类输入返回 `CoreError::InvalidModuleName`，不会进入 module table，也不会继续注册服务。插件扩展 registry 可以继续用空名 fixture 测自己的无效输入报告，但 runtime 主链不再把空 module name 当成可注册实体。

`RegistryName` 是 runtime service table 的 canonical key，形状固定为 `Module.Kind.Service`，并且每一段都必须非空。`Module` 和 `Service` 段不能带首尾空白；`Kind` 段必须是 `ServiceKind::{Driver, Manager, Plugin}` 对应的 canonical 字符串，不能写成临时的 `Service`、小写别名或旧式分类名。`RegistryName::new(...)` 先用一次 byte scan 找到两个 separator offset，并在发现第三个 separator、少于两个 separator、空段、module/service 首尾空白或未知 kind 段时拒绝输入，避免旧式分层名字被悄悄注册进同一张服务表。`RegistryName::from_parts(...)` 现在先校验 module/service 段，再按已知长度预分配 canonical 字符串并直接写入缓存的 module/service offset 与 `ServiceKind`；这让 descriptor 构造不用在拼接后再次解析同一个 registry string，同时保持无效 segment 直接失败的开发期反馈。`module_name()`、`service_kind()`、`service_name()` 是读取三段 registry key 的唯一 owner API；注册、依赖校验和后续性能切片应通过这些 accessor 工作，不再散落手写 `split('.')` 逻辑。

M5 后续切片把 `RegistryName` 从裸 newtype 收紧为“字符串 + 已验证段元数据”。构造期一次性记录 module 段结束位置、service 段起始位置和 canonical `ServiceKind`；accessor 只做切片或返回缓存 kind，不再在注册、依赖校验、activation/deactivation 或 resolution 热路径重复拆分同一个 registry string。为了保持 descriptor、manifest 和测试 fixture 的开发者友好形态，`RegistryName` 的 serde 仍然是单个 canonical 字符串，不序列化内部偏移。`Hash` 也显式按 `as_str()` 计算，保证 `HashMap<RegistryName, ServiceEntry>` 的 `Borrow<str>` 查找与插入时的 key hash 一致。

2026-06-07 M5 后续把 `RegistryName::new(...)` 的 separator discovery 收敛到 `registry_separator_offsets(...)`。该 helper 用一次 `value.bytes().enumerate()` 记录 first/second separator offset，发现第三个 separator 立即拒绝；`new(...)` 不再先 `find('.')`、再对 kind tail `find('.')`、再对 service segment `contains('.')`。这样保持 `Module.Kind.Service` 字符串/serde/hash contract 不变，同时把构造期 separator scan 固定为一次。

2026-06-11 M5 后续把 `registry_separator_offsets(...)` 内部状态进一步收敛为 `value.as_bytes()` 加 indexed `while` loop。helper 现在用 `separator_count` 和两个 plain offset slot 记录第一、第二个 `.`，第三个 separator 仍立即返回 `None`，scan 结束后只在 count 恰好为 2 时返回 offset pair。外部 `RegistryName::new(...)` 的 exact-three-segment 行为、后续 module/kind/service validation、serde/hash/accessor contract 不变，但 separator scan 不再构造 `Option<usize>` 状态或通过 `first_separator?` / `second_separator?` 做尾部传播。

2026-06-11 M5 后续也把 `RegistryName` 的 serde decode 错误投影收敛为 direct match。`Deserialize` 仍先读取单个 canonical string，再调用 `RegistryName::new(...)` 保持同一 exact-three-segment 验证；成功路径直接返回解析后的 key，失败路径把原 `CoreError::InvalidRegistryName(...)` 交给 `serde::de::Error::custom(...)`，不再通过 `.map_err(...)` adapter 包一层闭包。

2026-06-07 M5 后续把 `RegistryName` 的 segment validation 从 `trim()`/post-check dot scan 收敛到本地 char-boundary helpers。`is_canonical_segment(...)` 只验证非空和首尾 whitespace，供 `new(...)` 在 separator offset 已验证后校验 module/service slice；`is_canonical_dot_free_segment(...)` 只用于 `from_parts(...)` 的 raw module/service 输入，并在同一 char pass 中拒绝首尾 whitespace 与任意 `.`。这样 `from_parts(...)` 不再用 `contains('.')` 或 `trim()` 做额外扫描，`new(...)` 也不再在 separator discovery 后再次执行 trim 分配/扫描形态，同时保持原有无效输入拒绝语义。

2026-06-11 M5 后续把 `is_canonical_segment(...)` 的尾字符读取也改成 direct match：多字符 segment 使用 `chars.next_back()` 返回的最后一个字符，单字符 segment 直接回到 `first`，再统一做 whitespace 判断。这保持单字符合法 segment 与尾部 whitespace 拒绝语义不变，同时移除校验路径里的 `.unwrap_or(...)` adapter。

`resolve_named_service_inner(...)` 的初始化路径也保持失败可恢复：服务进入 `Initializing` 前会在第二次拿到 service lock 后再次读取 cached instance；如果其它路径已经完成初始化，当前 frame 直接返回已缓存实例，不会把 `Running` service 重新标成 `Initializing` 或重复执行 factory。真正进入 `Initializing` 后，如果 module activation、依赖解析或 factory 构造返回错误，runtime 会在返回错误前把还没有实例的 entry 恢复为 `Registered`，并弹出当前 recursion stack。这样 lazy service 的一次失败不会把内部状态永久卡在 `Initializing`，后续 resolve 可以按相同 descriptor/factory 路径重试；成功路径仍然只在实例写入 service table 后标记为 `Running`。这个复位契约同时覆盖当前服务自身 factory 失败和依赖链中下游 service 初始化失败：依赖 service 会在自己的 resolve frame 中恢复，依赖它的父 service 也会在错误向上传播时恢复，避免重试前出现半初始化的 manager 或 driver。

`activate_module(...)` 也遵循同一条失败恢复边界：module 先进入 `Initializing` 并克隆 registration-time cached `startup_service_names`；空列表跳过 startup service resolution loop，非空列表才初始化 immediate services。如果任一 immediate service 或最终 module 状态写入返回错误，仍处于 `Initializing` 的 module 会恢复为 `Registered`。成功完成 module lifecycle transition 后，runtime 会尝试把该 module name 反查为已安装 plugin bridge lifecycle state 里的 provider package id；匹配到 linked runtime plugin module 时，CoreRuntime 会应用 provider activation，并从最终 `RuntimeExtensionRegistry` 恢复 deactivation 清掉的 bridge provider。这样 immediate service 的瞬时失败不会留下半激活 module；同一 module 可以通过原 descriptor 再次 `activate_module(...)`，并且 service-level reset 继续由 resolution frame 负责。

2026-06-11 M5 后续把 activation/deactivation 的 missing-module lookup 也收敛成 direct `let Some(entry) = modules.get_mut(module_name) else` 分支。`activate_module(...)`、`deactivate_module(...)`、`finish_module_activation(...)` 和 `finish_module_deactivation(...)` 保持相同 `CoreError::MissingModule(module_name.to_string())` 载荷，但不再通过 `ok_or_else(...)` closure 构造错误路径。single-service blocked-unload 结果也改为 direct `let Some(dependents) = blocked_dependents else { return None; }`，避免最后一段 `Option::map(...)` projection while preserving the same blocked-service payload.

同一轮 M5 follow-up 也收紧了 single-service blocked-dependency matcher 的 six-or-more fallback。`dependency_slice_contains_service(...)` 仍先对空 slice 和 exact one-through-five dependency slices 做固定比较；只有六个及以上 dependency 时才进入直接 `for dependency in dependencies` loop，找到首个匹配立即 `return true`，扫描结束返回 `false`。这样保留单 shutdown service blocked-deactivation 的依赖判定语义，但不再通过 iterator `.any(...)` adapter 构造 fallback predicate。

M5 的 canonical-key follow-up 把 registration-time service-key cache 继续贯穿到初始化路径。`activate_module(...)` 对空 `ModuleEntry.startup_service_names` 使用 first-lock module lifecycle fast path；非空列表交给 `resolve_startup_services(...)`，一个 startup service 直接调用 crate-local `resolve_registered_service(...)`，exact two startup services 直接解析两项 cached key，exact three startup services 直接解析三项 cached key，exact four startup services 直接解析四项 cached key，exact five startup services 直接解析五项 cached key，只有 six-or-more startup service list 才遍历 cached typed list，不再把已经 canonical 的 `RegistryName` 降回 `&str` 再走一次 service table key recovery。依赖链解析同样使用 `resolve_registered_service_inner(...)` 递归处理 `Arc<[RegistryName]>` dependency slice，保留当前 recursion stack 并避免 dependency walk 中的 `RegistryName -> str -> RegistryName` 往返。direct-key resolver 内部访问 service table 时也保持 typed key：已经持有 `&RegistryName` 或 owned `RegistryName` 的路径走 `HashMap<RegistryName, ServiceEntry>::get/get_mut`，只有公开 `resolve_driver(...)` / `resolve_manager(...)` / `resolve_plugin(...)` 字符串入口通过 `get_key_value(...)` 从 `&str` 找回 canonical key。公开字符串入口保留，因为上层调用者和 host/plugin boundary 需要这个开发者友好的 contract；runtime 内部已经拥有 canonical key 的启动和依赖路径不再做 `service_key.as_str()` 查表绕行。

`deactivate_module(...)` 的卸载路径现在也是事务式的。module 进入 `Stopping` 前会记录原生命周期，然后使用 registration-time cached typed unload order 决定卸载工作。shutdown list 为空时跳过 service-table blocked-unload precheck 和 unload mutation；非空 shutdown list 会先预检所有待卸载 service 的外部 running dependents。只有没有 service 阻塞时，runtime 才尝试把该 module name 反查为已安装 plugin bridge lifecycle state 里的 provider package id，并在服务卸载前应用 provider deactivation。强 bridge dependent 会返回 `CoreError::PluginBridgeLifecycleBlocked(...)`，恢复 module 原生命周期，并且不会清空同 module 的 services。只有一个 shutdown service 时，预检直接用该 `RegistryName` 比较 running external dependency slices，并跳过 unload-order index allocation；exact two shutdown services 走 `first_blocked_two_service_unload(...)` 直接比较两项 cached key，先收集第一项 service 的阻塞 dependents，只有第一项未被阻塞时才返回第二项结果；exact three shutdown services 走 `first_blocked_three_service_unload(...)` 直接比较三项 cached key；exact four shutdown services 走 `first_blocked_four_service_unload(...)` 直接比较四项 cached key；exact five shutdown services 走 `first_blocked_five_service_unload(...)` 直接比较五项 cached key；这些 small-slice helpers 都按 cached shutdown key 的 stop-order precedence 返回最早被外部 running service 阻塞的项。只有 six-or-more shutdown list 才按 unload order 长度预分配 unload-order index，再单次扫描 running external services 的 dependency slices。同一份 index 既定位依赖落在哪个待卸载 service，也判断被扫描的 service 自身是否正在卸载，避免额外构建 typed unloading set。预检和 bridge lifecycle deactivation 都通过后，实际卸载也通过 typed helper 访问 service table：一个 shutdown service 直接对该 `RegistryName` 做单项 `get_mut(...)`，exact two/three/four/five shutdown services 直接执行对应次数的 typed mutation helper，只有 six-or-more shutdown list 才遍历 cached unload order 并复用同一单项 mutation helper，不再把 shutdown key 降回 `service_name.as_str()`。预检只保留当前最早被阻塞的 unload-order index 和对应 dependents；dependent list 也只在第一次发现阻塞项时按本地初始容量创建，遇到更早阻塞项时复用并清空旧 dependent list，遇到更晚阻塞项时忽略，同时保持按原 stop order 返回第一个阻塞项。如果任一 service 或 bridge dependent 阻塞，runtime 会把仍处于 `Stopping` 的 module 恢复到原生命周期，并且不会提前卸载同 module 内排在前面的 manager/plugin/service，避免失败后留下半停止或半卸载状态。

direct resolve 一个未激活 module 的 immediate service 时，resolution frame 会先触发 owner module activation。activation 可能已经初始化并缓存了当前 service；因此 `resolve_named_service_inner(...)` 在 activation 返回后会重新读取 service table，若实例已经存在就直接返回该实例，而不是继续执行当前 frame 的 factory。这个规则保持 service table 是唯一实例权威，避免 direct resolve immediate service 走出两次 factory 调用和两份实例。

## Folder Boundary

当前 `runtime` 子树固定成四层：

- `contexts/`
  - 只放 `ModuleContext`、`PluginContext` 这种纯声明类型。
- `descriptors/`
  - 每个 registry 声明各占一个文件，`ServiceFactory`、`PluginFactory` 与 `ServiceObject` 分文件持有，不再和 runtime 逻辑混写。
- `handle/`
  - `CoreHandle` 自身只保留声明和极小 accessor。
  - 注册、激活/停用、解析、事件/配置 分别拆到独立行为文件。
- `state/`
  - `CoreRuntimeInner`、`ModuleEntry`、`ServiceEntry` 都被压到内部状态层，不再和公开 descriptor 混在一起。

这样之后继续增加新的 service kind、生命周期规则、配置桥或调度行为时，不需要再回到一个巨型 `core.rs` 里追加段落。

## Behavior Split

`CoreHandle` 现在按行为族拆分：

- `registration/`
  - `mod.rs` 只保留 child module declarations，不承载 `CoreHandle` implementation。
  - `register_module.rs` 拥有 `CoreHandle::register_module(...)` orchestration、empty/single/two/three/four/five service registration paths、six-or-more pending registration path, and final transactional commit。
  - `descriptor_entries*.rs` 只准备 descriptor-backed service entries。
  - `service_lists.rs` 只构造 owner/startup/shutdown `Arc<[RegistryName]>` lifecycle caches。
  - `validation.rs` 和 `duplicates.rs` 分别拥有 registration-time descriptor validation 与 final duplicate lookup。
  - `duplicates.rs` keeps the six-or-more pending-service duplicate check as an explicit first-match scan over canonical `RegistryName` keys, returning the first existing service-table key directly and falling through to `None` without `find_map(...then_some(...))` adapter projection.
- `activation.rs`
  - module activate / deactivate
  - unload blocking 检查
  - `activation/blocked_dependencies/` owns blocked-dependency matchers by exact shutdown-service count: `single.rs`, `two_service.rs`, `three_service.rs`, `four_service.rs`, and `five_service.rs`; its `mod.rs` stays wiring-only.
- `resolution.rs`
  - driver / manager / plugin 解析
  - dependency chain 递归初始化
  - plugin 解析显式构造 `PluginContext`
  - 初始化失败后的 lifecycle reset / retry
  - kind mismatch / cycle / initialization error 收口
- `events.rs`
  - event bus publish / subscribe
  - config store load / store

runtime resolution 测试现在同样是 folder-backed：`resolution/mod.rs` 只声明 `behavior` 和 `structure`；`resolution/behavior.rs` 拥有 lazy resolve、failed initialization retry、exact four dependency 和 four-frame cycle 行为覆盖；`resolution/structure.rs` 拥有 source-shape guard、deeper `../../handle/resolution.rs` / `../../../diagnostics/devtools.rs` include paths，以及 behavior ownership assertions。生产 `resolution.rs` behavior 不变，这只是把 548-line mixed flat test file 拆成 ownership 更清楚的 behavior/structure children。

activation deactivation 行为测试现在也继续 folder-backed：`activation/behavior/deactivation.rs` 只声明 `blocked` 和 `clean`；`deactivation/blocked.rs` 拥有外部 running dependent 阻塞、shutdown-order first-blocked precedence、exact three/four blocked-unload fast-path 行为覆盖；`deactivation/clean.rs` 拥有空 shutdown list 和 exact three/four/five clean unload mutation 覆盖。`activation/structure/` 现在也是 folder-backed guard tree：`mod.rs` 只声明 child guards，`fixture.rs` owns source aggregation, and `root_contract.rs`, `service_lists.rs`, `startup.rs`, `blocked_dependencies.rs`, `blocked_unload.rs`, and `unload_mutation.rs` split the source-shape assertions by behavior family so exact-count hot-path assertions no longer regrow one mixed test file.

2026-06-07 M5 后续把 blocked-dependency matcher owner 从 former flat owner 切到 folder-backed `activation/blocked_dependencies/`。根 `mod.rs` 只声明并 re-export child matchers；`single.rs` owns single-service dependency presence, while `two_service.rs` through `five_service.rs` own exact-count classifier enums and dependency-slice matching for each shutdown-service count. This preserves the existing activation/deactivation API while making the next exact-count matcher a new child-file change instead of regrowing the activation root.

同一轮 activation hard-cutover 也把 startup resolution、blocked-unload precheck、clean unload mutation 从 `activation.rs` root 中下沉到 child owners。`activation/startup.rs` owns `resolve_startup_services(...)` and its one-through-five cached startup-key fast paths; `activation/blocked_unload.rs` owns `first_blocked_unload(...)`, exact one-through-five blocked-deactivation service scans, and the six-or-more indexed fallback; `activation/unload_mutation.rs` owns `unload_services(...)`, the single-service `unload_service(...)` mutation helper, and one-through-five cached shutdown-key mutation fast paths. ## Internal State Discipline

`state/` 目录现在只承载运行时内部权威状态：

- `CoreRuntimeInner`
  - modules registry
  - services registry
  - event bus
  - config store
  - scheduler
- `ModuleEntry`
  - module descriptor + owner service-key list + immediate startup service-key list + shutdown service-key list + lifecycle
- `ServiceEntry`
  - startup / canonical dependency names / factory / lifecycle / cached instance
  - service identity, owner module, and kind are derived from the `HashMap<RegistryName, ServiceEntry>` key, not duplicated in the value
  - factory 进一步细分为普通 `ServiceFactory` 与 plugin 专用 `PluginFactory`

这些结构不是公开 API，不允许再被重新暴露到 `mod.rs`。外部应继续通过 `CoreRuntime` / `CoreHandle` 工作。

## Extension Rule

后续继续扩展 `zircon_runtime::core::runtime` 时，保持以下规则：

- 新的公开声明放到 `descriptors/` 或 `contexts/`，每个顶层声明一个文件。
- runtime service-table object storage 使用 `descriptors/service_object.rs` 的 `ServiceObject`；不要从 `core` root 恢复 `ServiceObject` re-export。
- 新的 `CoreHandle` 行为先判断属于哪个行为族；如果已经跨出当前文件职责，就新增行为文件。
- `runtime/mod.rs` 只做 `mod` 和 `pub use`。
- 不再恢复单文件 `core.rs` 式混合实现。
