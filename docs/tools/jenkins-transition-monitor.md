## 每日编译增量归因与纠正（2026-10-18 授权）

现有 Codex 任务 `automation` 每次执行必须读取本节及
[编译存储规则](jenkins-build-storage-policy.md)。保持北京时间 09:00 的原任务，
不新建 Windows 任务，不直接修改 Codex 任务数据库或注册文件。正式任务接口
不可用时，通过任务原本就要求读取的本文交付审查步骤，不能声称改过调度器。

完整只读审查仍用项目根的原命令：

```powershell
& '.jenkins/runtime/python/python.exe' -B -X utf8 tools/dev/jenkins_transition_monitor.py --repo E:/Git/ZirconEngine --deep
```

`buildStorage` 使用本轮已有目录遍历的互不重叠 `outputItems`，分别记录共享池、
普通 target/build、incremental、调试符号的逻辑字节，与上一份有效基线比较。
第一次观察只建立基线。扫描不完整、读取失败或只做快速检查时，保留上一有效
计数、未结异常和证据；不能将低于上次的扫描下界记为已释放或已解决。
目录遍历共用 900 秒预算，并记录当前正在扫描的根目录。预算耗尽时所有未遍历
部分都标为不完整；这是遍历预算，不保证 Windows 的单次文件 I/O 能被强制中断。
优先扫描编译输出根，直接复用该次遍历建立池基线；控制目录后续超时不能抹掉
此前已完整观察的编译池，也不能将重叠统计相加。
逻辑大小读取目录枚举数据；进入子目录前重新核对 reparse 属性。Windows 枚举
没有逐文件硬链接计数时，明确记录 `hardlinkCountComplete=false`，不能把零个
已确认硬链接解释为不存在共享文件；清理仍需 Jenkins 的精确文件身份核验。
Full Access 下仍使用保留的 `zircon-strict.filesystem` 表作为审查范围，报告
实际配置仍是 Full Access；不改权限，也不据此声称启用了沙箱。

对新增占用先核对 artifacts 清单、Jenkins 原 request/operation、实际执行回执、
session、ownerThreadId、源码工作树/分支、提交及文件哈希。目录时间、名称、
最后一个请求或单一清单都不能证明共享池全部字节由该会话产生。清单归因只是
候选线索，实际执行与资源引用仍须核验；记录无法归属、多写入者和证据缺口。
至少 1 GiB 的无归属增长标为待核查，不直接判为浪费。重复池只有在完整兼容性
身份相同、原生 writer 已终结且引用条件成立后才可交给 Jenkins 回收。

检查已记录 Cargo 命令及各就绪工作树的 dev/test profile 是否违反存储规则。
确认违规后，核对原任务是否已经修复，按精确候选路径和当前哈希向原 Jenkins
流程递交有界纠正：默认 features/测试范围、incremental、符号配置或重复输出
选择的修复。用户已授权此类纠正与强制规则维护，不再要求逐会话提交许可。
源码、提交、集成、生成及清理仍由 Jenkins 负责；审查脚本本身只写审查元数据。
归属不清、外部暂存、未知锁、活动 writer 或原请求 UNKNOWN 时保留现场和阻塞，
不另建源码副本、私有 target 或替代构建。失败时写原会话收件记录，明确区分
已保存交接、Codex 已确认送达和对方已读取；没有消息接口不能声称已唤醒对方。

每条异常保留责任候选、证据、实际修复请求和验收状态。只有 Jenkins 实际回执
证明纠正完成才关闭；提交到任务分支不等于主干已生效。状态未发生可行动变化
时只存报告；新增明确违规、失败、修复完成或需要用户决策时才提醒。
普通范围提交继续遵循较新的先提交任务分支、再经统一定时 PR 集成流程，
不使用下方历史人工 main 提交步骤代替它。

## 健康判定与移交条件

先验证当前 `driver.json` 指定的不可变实现及完整文件集合，再用该实现只读
检查。控制器与 agent 需有匹配的 PID、创建时间、可执行文件和命令摘要；端口
需属于该控制器。只有端口归属核对通过，才向本机 API 发送认证 GET。运行代次
需与 selector、host 和 operation 一致，实际健康及运行状态需同时通过。
报告不保存凭据或原始命令行。

恢复启动时，项目 Python 的临时辅助进程仍计入潜在占用者；不得因其来自
Codex 或声称只读就忽略。恢复入口允许最多 60 秒的只读观测等待，占用消失后
重新核验完整的原计划。持续占用、身份不可读、Boot 或生命周期变化仍阻止
启动；这不是命令重试或历史队列重放。辅助审查应使用独立的现有解释器，
避免审查自身占用待恢复的运行时。每日深度巡检继续使用规定的 Jenkins Python，
不在恢复事务内启动。

`tools/dev/prepare_jenkins_runtime_contention_recovery.py` 是针对原请求的 Jenkins
离线部署修复入口。它只安装经过实际针对性回归验证的不可变支撑驱动，复用
已审查计划与请求，保留原证据；不准备产品源码、操作 Git、构建或启动服务。
启动仍由 `tools/dev/start-jenkins-coordinator.ps1` 的严格权限宿主执行。

`Ready`、fixture 成功和历史支持层测试只证明各自范围。它们不证明当前源码、
多工作树合并、版本提交、生成、复用或定时清理已验收。移交须同时具备：

- 当前部署实现与真实服务身份匹配，原请求的源码及覆盖验收成立。
- Git 集成和多工作树流程有真实目标提交、路径、依赖、冲突及结果回执。
- 生成、产物复用、任务结束清理和定时维护均有当前代次的实施及运行证据。
- 保留对象、未知归属、历史锁与其他会话的活动资源完成原状态对账。

移交记录需指向上述证据，然后停用本次临时任务；不能只见到 `Ready` 就自动
切换写入主体，也不能删除旧证据或历史 State 来模拟验收。

## 人工合并操作

每日任务负责巡检和提醒。由临时接管会话处理已审查的候选批次，不让计划任务
根据“dirty”“目录旧”或“有分支”直接提交。当前共享 main 的异会话改动须保留。
每个批次按以下顺序执行，记录到上述报告根的 `integration` 目录：

1. 明确原会话/作者、候选路径、父提交、文件和依赖哈希；收集当前源码所需的
   检查证据。未声明归属或行为验收不成立的候选保持待验收。
2. 检查前一次人工交付、当前 HEAD、共享 index、未完成合并、活动 Git 进程和
   Jenkins 所有权。存在外部暂存、占用或身份不明的锁时停止该批次 Git 写入。
3. 仅暂存批准的路径，检查暂存后的内容、路径集合、哈希与父提交。
   忽略的新技能/测试须单独明确选择，不能使用 `git add -A`。
4. 用正常 Git 提交交付当前 main 上的候选，不复制源码、不创建额外工作树，
   不 reset/stash 别人的改动。真正的分支合并须先确认源 ref、目标 ref、共同
   基线和验收；已经包含于 main 的旧分支不得为了“清积压”制造合并。
5. 对账实际 commit 的 parent、tree、路径和内容；保存结果与仍阻塞项。
   本次授权不包含 push、发布、外部通知、解除 Jenkins 历史保留或清理未知文件。

锁恢复必须有当前占用/身份证据、精确路径及原字节记录；不能仅凭零字节或年龄
删除锁。其他会话恢复操作已经完成时，不恢复其历史锁或重复接管其提交。
