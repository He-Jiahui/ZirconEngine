# Postprocess Pass Graph Contracts

## Purpose

`zircon_runtime::core::framework::render::post_process` owns the neutral M4B postprocess product contract. It describes the per-camera stack as data on `RenderFrameExtract` and keeps effect ordering, resource names, and validation independent from WGPU pipelines.

Concrete rendering stays in `zircon_runtime::graphics`. The renderer consumes the frame's validated graph for execution evidence and treats actual renderer history availability as a final resource gate: when history is not available, it derives a frame-local graph by removing only the history resource/node from the submitted stack. It still uses the existing shader-backed postprocess stack for pixels until later milestones replace individual passes with graph-native implementations.

## Bevy Evidence

The Bevy reference surface is `bevy_post_process`, not a single monolithic effect pass. `dev/bevy/crates/bevy_post_process/src/lib.rs:9-36` splits the crate into `auto_exposure`, `bloom`, `dof`, `effect_stack`, `motion_blur`, and `msaa_writeback`, then wires `MsaaWritebackPlugin`, `BloomPlugin`, `MotionBlurPlugin`, `DepthOfFieldPlugin`, and `EffectStackPlugin` into `PostProcessPlugin`.

`dev/bevy/crates/bevy_post_process/src/bloom/mod.rs:44-83` shows bloom as a real Core2d/Core3d post-process system with extracted component data, prepared textures/bind groups, and scheduling before tonemapping. `dev/bevy/crates/bevy_post_process/src/effect_stack/mod.rs:3-6` names the built-in effect-stack features as chromatic aberration and vignette, while `effect_stack/mod.rs:141-165` extracts those camera components and schedules the combined pass before tonemapping.

The heavier Bevy effects have additional prerequisites. `dev/bevy/crates/bevy_post_process/src/motion_blur/mod.rs:75-173` requires depth and motion-vector prepasses and runs in the Core3d post-process set before bloom, while `dev/bevy/crates/bevy_post_process/src/motion_blur/motion_blur.wgsl` samples motion vectors plus depth to gather along a shutter-scaled screen-space vector. `dev/bevy/crates/bevy_core_pipeline/src/prepass/background_motion_vectors.rs` and `background_motion_vectors.wgsl` show that background/camera motion is a prepass product, not something inferred inside final composition. `dev/bevy/crates/bevy_post_process/src/dof/mod.rs:69-241` defines depth-of-field camera state, prepares depth/focus resources, and schedules after bloom and before tonemapping. `dev/bevy/crates/bevy_post_process/src/dof/mod.rs:69-139` also keeps DoF physical enough to expose focal distance, sensor height, aperture f-stops, max circle-of-confusion diameter, and Gaussian-vs-bokeh mode while acknowledging the implementation is speed-oriented. `dev/bevy/crates/bevy_camera/src/camera.rs:253-287` keeps the shared physical camera defaults that feed exposure and DoF. `dev/bevy/crates/bevy_post_process/src/msaa_writeback.rs:21-33` registers MSAA writeback before the Core2d/Core3d main pass, and `msaa_writeback.rs:110-126` only inserts the blit pipeline when camera writeback policy and MSAA sample count require it.

The user-facing Bevy example `dev/bevy/examples/3d/post_processing.rs` demonstrates the effect-stack authoring model by attaching chromatic aberration and vignette components to a 3D camera. Zircon does not yet expose equivalent camera components for those effects.

## Unity Volume Evidence

The volume-stack side of M7 follows Unity SRP more closely than Bevy. `dev/Graphics/Packages/com.unity.render-pipelines.core/Runtime/Volume/Volume.cs`, `VolumeProfile.cs`, `VolumeManager.cs`, and `VolumeStack.cs` establish the same product concepts Zircon now mirrors in neutral form: profiles contain optional effect overrides, volumes can be global or local, priority and blend weight decide ordering and influence, and camera layer masks decide which authored volumes are relevant to the current view.

Zircon keeps spatial volume evaluation out of renderer submit. Scene extract now computes the first runtime local influence path by comparing the selected camera position against a volume entity's `ColliderComponent` box, sphere, or capsule shape, then writes the resulting fade into `RenderPostProcessVolume.local_blend`. Local volumes without a same-entity collider are excluded from the stack instead of receiving an authored fallback influence. The render submit path only performs deterministic filtering, ordering, and parameter blending before the graph is built.

Scene extract now provides that authoring source for runtime worlds. `PostProcessVolumeComponent` stores global/local volume state plus a `RenderPostProcessVolumeProfile` in fixed scene component storage; `World::build_prepared_render_frame_extract_for_request(...)` filters those components by active hierarchy, component active flag, and effective camera render layers, then writes a `RenderPostProcessVolumeStack` into `PostProcessExtract.volume_stack`. Global volumes use authored weight directly. Local volumes require a collider on the same entity; scene extract evaluates the camera's distance from the transformed box, sphere, or capsule surface, applies `blend_distance`, and excludes the volume when the influence reaches zero. Submit remains the resolver by calling the existing layer-aware settings path before the postprocess graph is built. The component is intentionally skipped by world serialization in this slice, so serialized project/editor authoring remains future work.

Unity also sets the practical LUT import boundary for this M7 slice. `CubeLutAssetImporter.cs` parses `.cube` headers into a square 3D LUT, rejects sizes outside 2-256, and creates a clamped bilinear `Texture3D`; `CubeLutAssetFactory.cs` uses 33 as the default authoring size. Zircon mirrors that as neutral metadata in `RenderColorLookupTextureLayout` instead of binding a WGPU type at the framework boundary. `Texture2dStrip { size }` remains the 2D-strip layout for authored LUTs that arrive as atlas-style texture assets, while `Texture3d { size }` now routes through renderer-private WGPU `texture_3d` upload and final post-process shader sampling with a clamp/linear sampler. Bevy's `tonemapping/lut_bindings.wgsl` is the reference for the renderer-private 3D texture plus sampler binding shape, not something `app`, `editor`, or `framework` may import directly. The basic `.cube` asset ingress now lives in `zircon_runtime::asset`: `.cube` text imports become linear RGBA8 `TextureAsset` payloads with a neutral D3 descriptor, then renderer preparation consumes them through the same authored 3D LUT path as any decoded texture asset.

Unity's older screen-space reflection pass is the reference for the temporal reuse boundary. `dev/Graphics/com.unity.postprocessing/PostProcessing/Shaders/Builtins/ScreenSpaceReflections.hlsl` samples both history and camera motion vectors, reprojects history with current-minus-previous velocity, clamps reused history against the current color neighborhood, and blends it into the current reflection. Zircon now mirrors that as explicit graph-visible postprocess products: `ScreenSpaceReflectionDepthPyramid` writes first-level half-resolution min/max linear view depth into `postprocess.screen-space-reflection.depth-pyramid`; `ScreenSpaceReflectionSpecularOcclusion` writes `postprocess.screen-space-reflection.specular-occlusion` from scene depth, G-buffer material, and ambient occlusion; then `ScreenSpaceReflectionResolve` reads both products with scene color/depth, G-buffer normal/material, reconstructed motion vectors, and optional previous SSR history before writing the current-frame `postprocess.screen-space-reflection.history` target. Binding 20 remains the previous-frame feedback texture (`history.previous.screen-space-reflection`) for reprojection, binding 21 is the resolved current SSR target consumed by final `post.stack` composition, binding 22 carries the split specular-occlusion product into the resolve shader, and binding 23 carries the first-level depth-pyramid range target. The current frame target is copied into per-viewport history after the pass, then imported next frame as previous SSR history. This is deliberately not a full reflection pyramid, hierarchical multi-level SSR depth pyramid, new material ABI, or object/skinned/particle velocity path.

The postprocess shader source is assembled by `resources/shader_sources.rs`. The base `post_process.wgsl` owns the fullscreen vertex entry, final composition entry point, split SSR depth-pyramid and resolve entry points, and shared effect-stack sampling, while `post_process_screen_space_reflection.wgsl` owns the SSR helper family, including depth/normal/material/AO sampling, first-level depth-pyramid construction and range gating, bounded ray march/refinement, temporal history reprojection, and resolve-time specular attenuation. Production pipeline creation and the GL/WebGL/ANGLE fallback-depth source rewrite both consume the assembled `POST_PROCESS_SHADER`, so the split changes concrete pass ownership while preserving one assembled source contract.

The 2026-06-05 SSR coarse-pyramid follow-up extends that live contract to a fixed two-level hierarchy. `ScreenSpaceReflectionDepthPyramidCoarse` writes `postprocess.screen-space-reflection.depth-pyramid.coarse` from the first-level depth range target, and `ScreenSpaceReflectionReflectionPyramidCoarse` writes `postprocess.screen-space-reflection.reflection-pyramid.coarse` from the first-level color target. The pyramid products are graph-owned `Rgba16Float` transient textures materialized from compiled graph descriptors at half or quarter resolution; `import_frame_targets(...)` keeps scene, final, previous-history, and swapchain-style targets external. Resolve now depends on and reads first-level plus coarse depth/reflection products. Binding 24 carries first-level reflection color, binding 25 carries coarse depth range, and binding 26 carries coarse reflection color. The shader gates ray visibility with both depth-range levels and blends rougher hits toward the first-level then coarse color pyramid. This is still a fixed two-level SSR handoff, not the final dynamic multi-mip hierarchy, new material ABI, or object/skinned/particle velocity path.

Unity's older post-processing DoF remains the reference for the lens/bokeh authoring shape. `dev/Graphics/com.unity.postprocessing/PostProcessing/Runtime/Effects/DepthOfField.cs:48-70` exposes focus distance, f-stop aperture, focal length, and bokeh kernel size. `DepthOfField.cs:176-183` turns focal length, focus distance, aperture, and film height into a lens coefficient, and `DepthOfField.cs:217-226` runs downsample, bokeh simulation, postfilter, and combine passes. `DepthOfField.hlsl:150-205` uses disk-shaped bokeh kernels and separate near/far accumulation. Zircon now mirrors the neutral control vocabulary, reserves graph-visible CoC/bokeh resource names, materializes those scratch targets as graph-owned transients, and records a graph-visible `depth-of-field-prepare` pass that writes signed near/far CoC into the CoC scratch target and writes a CoC-weighted center-plus-four-neighbor bokeh prefilter seed into the bokeh scratch target. The final post-process shader now samples the CoC scratch target at binding 17 and bokeh scratch target at binding 18, treating center-plus-four-neighbor prepared CoC as an additional blur-radius signal and sampling the prepared bokeh prefilter seed with center/sample CoC far/near layer weighting inside the bounded final-pass bokeh kernel. This is still a final-pass seed/prefilter approximation until half-resolution bokeh simulation/gather, temporal CoC history, dedicated near/far combine passes, and postfilter/combine stages are introduced.

Unity's older motion blur sets the same split between authoring parameters, velocity input, and final reconstruction. `dev/Graphics/com.unity.postprocessing/PostProcessing/Runtime/Effects/MotionBlur.cs` requests depth plus motion-vector textures and scales velocity by shutter angle, while `MotionBlur.shader` samples the camera motion-vector texture before running its reconstruction passes. Zircon now mirrors a camera/background velocity producer plus a fixed graph-owned reconstruction handoff: `motion-vector-camera` writes camera/background UV velocity into raw graph `scene-motion-vector`, `motion-vector-tile-max` writes half-resolution `postprocess.motion-vector.tile-max`, `motion-vector-tile-max-coarse` writes quarter-resolution `postprocess.motion-vector.tile-max.coarse`, `motion-vector-neighbor-max` reads that coarse tile target and writes full-resolution `postprocess.motion-vector.neighbor-max`, `PostProcessParams.effect_motion_blur` uploads shutter/sample controls, binding 19 exposes the reconstructed motion-vector texture to a bounded vector gather, and the final shader attenuates foreground-depth samples during the gather. Object/skinned/particle velocity writers, a full dynamic multi-level tile-max/neighbor-max pyramid, and richer temporal/camera-cut policy remain future renderer work.

The current camera/background velocity producer also treats implausible previous-camera history as a cut: projection mode, target, viewport, dynamic-resolution, large FOV/orthographic-size/clip-plane jumps, large translation, and large rotation incompatibilities leave `scene-motion-vector` at the neutral clear value instead of reprojecting stale history. The tile-max, coarse tile-max, and neighbor-max passes then reconstruct from that neutral/raw chain, but richer temporal policy, object velocity ownership, and a full dynamic tile/neighbor pyramid remain future work.

Invalid or non-finite camera projection data uses the same neutral path. `MotionVectorCameraParams` validates current/previous FOV and clip ranges before projection matrix generation, scans the generated current/previous matrices for finite values, disables `post.motion-vector-camera` on invalid input, and uploads identity clip matrices in the disabled uniform so bad camera data cannot leak NaNs into the motion-vector shader.

## Data Model

`PostProcessEffectKind` currently names the first product nodes: bloom, color grading, history resolve, effect stack, screen-space reflection depth pyramid, screen-space reflection specular occlusion, screen-space reflection resolve, final composite, and FXAA. These names are intentionally product-level, not tied to a specific shader or render-pass asset.

`PostProcessEffectSettings` is the authored node descriptor. It carries the effect kind, enabled flag, required input resource names, produced output resource names, and `after` ordering dependencies.

`PostProcessStackDescriptor` stores the initial resource set and ordered authored effects. `from_extract_settings(...)` derives the default stack from `RenderBloomSettings`, `RenderColorGradingSettings`, history-resolve enablement, and history availability. History resolve requires both an enabled profile feature and a compatible previous history texture; the first compatible frame keeps the history node skipped until renderer history is actually available. Disabled effects remain visible in the descriptor but are elided from executable graph nodes.

`RenderPostProcessEffectStackSettings` is the M7 typed parameter bundle for effect-stack style postprocess. It currently carries neutral settings for tonemap, color lookup table, blur, motion blur, depth of field, screen-space reflection, vignette, film grain, dither, chromatic aberration, and fog. `RenderMotionBlurSettings` mirrors the Bevy camera-facing shape with a disabled-by-default shutter angle and sample count; positive shutter angle plus non-zero samples enables the family, and renderer upload will clamp samples to the current local policy limit. The DoF settings include focus distance, focus range, aperture strength, focal length in millimeters, max blur radius, bokeh blade count, and bokeh rotation; the renderer sanitizes focal length, focus range, and blade count before uploading them. `RenderColorLookupSettings` includes `RenderColorLookupTextureLayout`, giving authored LUTs an API-level shape contract before WGPU resources are selected. Positive LUT intensity is the authored request signal even when no texture handle is present; missing handles and invalid explicit LUT sizes are reported by the effect-stack report. A default bundle is treated as absent so existing default graphs do not grow a disabled placeholder node. When any setting is active, `PostProcessStackDescriptor::from_extract_settings_with_effect_stack_and_anti_alias(...)` inserts an `EffectStack` product node after bloom/color-grading/history inputs and before final composite, producing `postprocess.effect-stacked`. When SSR is active, the descriptor also inserts `ScreenSpaceReflectionDepthPyramid`, `ScreenSpaceReflectionSpecularOcclusion`, and `ScreenSpaceReflectionResolve` before final composite. The depth-pyramid node requires `scene-depth` and produces `postprocess.screen-space-reflection.depth-pyramid`; the specular-occlusion node requires `scene-depth`, `gbuffer-material`, and `ambient-occlusion`; the resolve node requires scene color/depth, G-buffer normal/material, the split depth-pyramid and specular-occlusion products, and `postprocess.motion-vector.neighbor-max`, adds `history.previous.screen-space-reflection` when temporal history is enabled, and produces graph-owned current-frame `postprocess.screen-space-reflection.history`. Final composite then declares the resolved SSR target as an input and depends on the resolve node. The built-in `post_process` render feature adds a 3D `motion-vector-clear` pass in `DepthPrepass` that clear-stores raw graph-owned `scene-motion-vector` to neutral zero. A later `motion-vector-camera` pass load/stores that raw target from graph `scene-depth` and previous compatible camera state, `motion-vector-tile-max` downsamples that raw target into graph-owned `postprocess.motion-vector.tile-max`, `motion-vector-tile-max-coarse` downsamples that tile target into graph-owned `postprocess.motion-vector.tile-max.coarse`, and `motion-vector-neighbor-max` reads the coarse tile target to write graph-owned `postprocess.motion-vector.neighbor-max` for final-stack consumption. Camera/background velocity exists while object/skinned/particle velocity remains open. When DoF is active, the effect-stack node also produces graph-owned `postprocess.depth-of-field.coc` and `postprocess.depth-of-field.bokeh` product resources.

For the current fixed two-level SSR pyramid, the active descriptor also inserts `ScreenSpaceReflectionReflectionPyramid`, `ScreenSpaceReflectionDepthPyramidCoarse`, and `ScreenSpaceReflectionReflectionPyramidCoarse`. The coarse depth node depends on the first-level depth node, the coarse reflection node depends on the first-level reflection node, and `ScreenSpaceReflectionResolve` depends on all four pyramid products plus split specular occlusion before writing `postprocess.screen-space-reflection.history`.

This parameter bundle is still a render-chain contract, not full shader parity. The renderer now encodes effect-stack fields plus camera depth/projection/view-basis parameters into `PostProcessParams`, and `post_process.wgsl` consumes those uniforms for baseline tonemap/exposure, authored-or-fallback LUT texture sampling, blur, camera-linearized scene-depth DoF-radius sampling with focal-length scaling and a rotated blade-shaped bokeh kernel, prepared CoC scratch sampling with center-plus-four-neighbor dilation as an additional DoF radius candidate, prepared bokeh prefilter seed sampling with true center/sample CoC far/near layer weighting through the final-pass bokeh kernel, bounded motion-vector gather from graph-reconstructed `postprocess.motion-vector.neighbor-max` with scene-depth foreground-sample attenuation, resolved SSR sampling from binding 21 in final composition, vignette, grain, dither, chromatic aberration, and view-depth-weighted fog. Motion blur now uploads `PostProcessParams.effect_motion_blur`, samples the motion-vector neighbor-max target at binding 19, depth-weights foreground sample rejection, and can consume camera/background velocity from `motion-vector-camera`; object/skinned/particle velocity remains absent. `motion-vector-camera` disables itself and preserves the clear value when previous camera history fails projection/target/viewport/dynamic-resolution checks, large FOV/orthographic-size/clip-plane jump checks, or the large translation/rotation cut gate. `motion-vector-tile-max` is a half-resolution 2x2 dominant-vector pass, `motion-vector-tile-max-coarse` reuses that 2x2 downsample to write a fixed quarter-resolution coarse tile target, and `motion-vector-neighbor-max` expands the center-plus-eight coarse-tile neighborhood back to full resolution using the 4x4 source-to-coarse mapping; this is a fixed two-level pyramid, not the final dynamic multi-level tile-max/neighbor-max pyramid. `RenderColorLookupSettings::is_enabled()` treats positive intensity as the LUT request signal; the optional texture handle decides whether the WGPU postprocess bind group selects a prepared 2D/2D-strip LUT at binding 10, a prepared 3D LUT at binding 12, or renderer-owned fallbacks. Binding 10 keeps the 64x1 S-curve fallback for 1D/2D-style LUT use, binding 12 keeps a 2x2x2 identity cube fallback for `Texture3d`, binding 13 carries the clamp/linear sampler used by the 3D path, and `PostProcessParams.effect_flags.y` records the actual shader binding mode selected for the frame: disabled, 2D, 2D strip, or 3D. The 3D shader path samples normalized texel-center coordinates with `textureSampleLevel(...)`, preserving endpoint colors while allowing interpolation between LUT cells. The renderer inspects the neutral `RenderImageDescriptor` before upload, so unsupported array/non-LUT shapes are diagnosed and kept on fallback instead of being forced through the wrong WGPU slot. Binding 11 carries graph-owned `scene-depth` on backends that can compile the raw depth shader path, while `PostProcessDepthSamplingMode` switches GL/WebGL/ANGLE backends to a viewport-depth fallback shader and a regular float fallback texture because Naga's GLSL path translates raw depth sampling into a shadow-sampler shape. Binding 14 carries graph-owned `gbuffer-normal`, binding 16 carries `gbuffer-material` only when the active compiled graph has an unculled writer, binding 17 carries `postprocess.depth-of-field.coc`, binding 18 carries `postprocess.depth-of-field.bokeh`, binding 19 carries `postprocess.motion-vector.neighbor-max`, binding 20 carries `history.previous.screen-space-reflection` for the split SSR resolve pass, binding 21 carries the current resolved `postprocess.screen-space-reflection.history` target for final composition, binding 22 carries `postprocess.screen-space-reflection.specular-occlusion`, and binding 23 carries `postprocess.screen-space-reflection.depth-pyramid`. Otherwise the material slot binds the renderer-owned black fallback and the shader treats material roughness as fully rough. The SSR resolve path reconstructs a view-space origin from the sampled depth, transforms the decoded world normal through the camera view-basis rows before reflecting the view vector, projects marched view-space candidates back to pixels using `PostProcessParams.effect_projection`, refines the first depth/thickness hit with a small bounded interval search, reprojects the previous SSR history texture through current-minus-previous motion vectors when `feature_flags.z` marks history valid, clamps reused history RGB to the current scene-color neighborhood while preserving history alpha as feedback confidence, writes current-frame `postprocess.screen-space-reflection.history`, suppresses reflection contribution as roughness approaches 1.0, multiplies final visibility by split specular occlusion sampled from binding 22, and dampens coarse depth mismatch using the first-level min/max range sampled from binding 23; binding 1 ambient occlusion feeds the separate specular-occlusion pass and keeps its white fallback neutral. `PostProcessParams.effect_depth` carries clamped near/far planes, inverse range, and projection-mode flag so perspective and orthographic cameras interpret sampled or fallback depth consistently, `effect_projection` carries perspective focal scales and orthographic half extents for the final-pass projection math, `effect_dof_lens` carries sanitized focal length, focus range, bokeh blade count, and bokeh rotation, `effect_view_x/y/z` carries the world-to-view camera basis used only by the post-process normal conversion, and `effect_motion_blur` carries the enabled shutter fraction plus bounded sample count. Basic text `.cube` import is now asset-pipeline work that feeds this 3D path; object/skinned/particle velocity output, a full dynamic multi-level tile-max/neighbor-max motion-blur pyramid, half-float LUTs, 1D shaper LUTs, editor baking, physical half-resolution bokeh simulation/combines, a full hierarchical SSR depth pyramid/reflection pyramid, a linear-depth color resource for GL fallback quality, and deeper split per-effect passes remain future renderer or authoring work.

The same SSR coarse-pyramid continuation extends the binding list above: binding 24 carries `postprocess.screen-space-reflection.reflection-pyramid`, binding 25 carries `postprocess.screen-space-reflection.depth-pyramid.coarse`, and binding 26 carries `postprocess.screen-space-reflection.reflection-pyramid.coarse`. Resolve samples binding 23 plus 25 for fixed two-level depth-range visibility and binding 24 plus 26 for roughness-weighted color fallback.

`RenderPostProcessEffectStackReport` is the public diagnostic companion for that intentionally partial state. It is derived from the effective settings after direct extract and volume resolution, records active effect families, records which active families are still approximation-backed (`depth-of-field`, `motion-blur`, `screen-space-reflection`), and exposes missing authored or renderer-prerequisite labels such as `effect-stack.lut.texture`, `effect-stack.lut.texture-layout`, `effect-stack.ssr.normal`, `effect-stack.ssr.temporal-history`, `effect-stack.motion-blur.motion-vector`, and `effect-stack.motion-blur.velocity-prepass`. The LUT label now means intensity was authored without a LUT handle; once a handle is present, LUT is considered renderer-bound and no longer counted as approximation-backed. Renderer-private upload failure still falls back to the S-curve or identity-cube texture at bind time rather than changing the neutral report, while renderer-side `RenderStats.last_post_process_lut_*` counters expose whether the enabled LUT family requested a texture, prepared it, used fallback, matched the current 2D-strip contract, requested and prepared a 3D layout, or had an unsupported shape. DoF/SSR/motion-blur depth is no longer reported as missing because `post.stack` now binds graph `scene-depth`. SSR normal readiness is graph-resource-driven: when the effective effect-stack node declares `gbuffer-normal`, submit stats pass `RenderPostProcessEffectStackResourceStatus { ssr_normal_available: true }` and the old `effect-stack.ssr.normal` missing label is cleared. Temporal SSR readiness is also graph-resource-driven: when `history.previous.screen-space-reflection` is absent, the report records `effect-stack.ssr.temporal-history`; when previous SSR history is declared but the reconstructed motion-vector input or its producer chain is incomplete, the report records `effect-stack.ssr.temporal-motion-vector`, `effect-stack.ssr.temporal-velocity-prepass`, the `.camera`, `.tile-max`, `.tile-max-coarse`, and `.neighbor-max` stage suffixes, plus `.camera-history` or `.camera-cut-or-invalid` when camera-vector status explains the neutral velocity path. Motion-vector target readiness remains available to motion blur: when the motion-blur effect-stack node declares `postprocess.motion-vector.neighbor-max`, submit stats pass `motion_vector_available: true` and clear the `effect-stack.motion-blur.motion-vector` label, while `motion_vector_prepass_available` becomes true only when `post.motion-vector-camera`, `post.motion-vector-tile-max`, `post.motion-vector-tile-max-coarse`, and `post.motion-vector-neighbor-max` executed for the frame. SSR material roughness is renderer-resource consumption rather than an authored-resource label: the graph declares `gbuffer-material` for SSR, but the concrete postprocess bind group only uses it when the active compiled graph has an unculled material G-buffer writer. The report uses only count and string fields so `RenderStats` remains cloneable and equality-friendly for focused bridge tests.

The motion-blur report keeps the aggregate `effect-stack.motion-blur.velocity-prepass` label for compatibility and now adds stage-level labels while that aggregate is missing: `effect-stack.motion-blur.velocity-prepass.camera`, `.tile-max`, `.tile-max-coarse`, and `.neighbor-max`. Tools can therefore identify which graph executor did not run without parsing the executed-node string list.

Camera-vector readiness is now separate from camera executor presence. `MotionVectorCameraStatus` records whether the camera producer was not requested, lacked a previous camera, rejected the previous camera as a cut or invalid projection, or uploaded usable camera/background vectors. The effect-stack report keeps `effect-stack.motion-blur.velocity-prepass` active unless the camera status is `ready` and the tile-max, coarse tile-max, and neighbor-max stages executed; when the camera executor preserved neutral velocity, the report adds `effect-stack.motion-blur.velocity-prepass.camera-history` or `effect-stack.motion-blur.velocity-prepass.camera-cut-or-invalid`.

`RenderPostProcessVolumeProfile`, `RenderPostProcessVolume`, and `RenderPostProcessVolumeStack` are the M7 volume authoring DTOs carried by `PostProcessExtract`. A profile can override bloom, color grading, and the effect-stack settings independently. A volume records active/global state, priority, weight, render-layer mask, local blend influence, and the profile payload. `RenderPostProcessVolumeStack::resolve(...)` filters volumes by active state, camera layer intersection, and positive influence, then blends them in ascending priority order with insertion-order tie breaking. Global volumes use only `weight`; local volumes use `weight * local_blend`, where `local_blend` is precomputed by scene extract from the camera/volume/collider relationship rather than calculated in the renderer.

`RenderResolvedPostProcessSettings` is the resolved per-camera output of that stack. It is not stored as authored scene state; it exists to feed the submit-time graph compiler and history-validation key with the final bloom, color-grading, and effect-stack settings for the current camera.

History scene-color is deliberately split into previous, current, and output names. The previous slot is the only graph input imported from the last accepted frame. The current slot names the renderer-owned texture that `HistoryCopy` updates at the end of a valid frame. The output slot is the postprocess result produced by the history-resolve pass for later composition. A pass must not use one shared resource name for both previous input and current output, because that hides temporal overwrite bugs from graph validation.

`PostProcessPassGraph` is the validated graph summary carried by `PostProcessExtract`. It contains executable nodes, skipped nodes, and the final composite node name for stats and tests.

Object/skinned/particle velocity writers still do not exist. `postprocess.color-graded`, `postprocess.effect-stacked`, `postprocess.history-resolved`, and `postprocess.final-composited` remain imported aliases for graph-resource consistency while concrete shader execution still writes through the existing postprocess target set. The DoF targets are allocated and graph-imported scratch resources; `depth-of-field-prepare` now populates CoC with a signed near/far fullscreen shader and writes a CoC-weighted bokeh prefilter seed, while final postprocess samples both scratch targets with CoC-aware bokeh weighting and a four-neighbor CoC dilation for the final radius/mix decision. Separate half-resolution bokeh simulation, dedicated near/far combine, and postfilter/combine passes do not exist yet. `history.previous.scene-color` is imported only when `prepare_history_textures(...)` reports a compatible previous history texture, so execution evidence cannot claim history resolve on the first frame after allocation or rotation. `history.current.scene-color` is the label of the renderer history texture written by `HistoryCopy`; it is not the graph input consumed by history resolve.

## Validation

`PostProcessPassGraph::validate_stack(...)` enforces the graph invariants before execution evidence is recorded:

- enabled nodes must have all required inputs available before they run,
- produced outputs must not duplicate initial resources or another enabled node output,
- `after` dependencies must target an enabled node in the graph,
- dependency cycles reject the stack before renderer execution.

Disabled effects are not errors. They are converted into `skipped_nodes` so stats and diagnostics can distinguish an authored but disabled effect from a node that never existed.

## Runtime Submit Integration

`build_frame_submission_context(...)` derives the effective stack from the compiled feature set, extract settings, compatible frame history, resolved volume stack, and resolved anti-alias settings. It first calls `PostProcessExtract::resolved_settings_for_layers(...)` with the current camera render layers, then applies feature gates. Profile-disabled bloom or color grading is converted back to default settings before graph validation, history resolve only enters the graph when the compiled pipeline enables the history feature and the viewport already has compatible frame history, and FXAA enters the graph only when `AntiAliasSettings` resolves to `Fxaa`.

`FrameSubmissionContext` carries the effective bloom settings, color-grading settings, effect-stack settings, `PostProcessStackDescriptor`, and `PostProcessPassGraph`. Extract-submit, present-submit, and direct runtime-frame submit replace the frame's stack and graph with those effective values and clear the raw `volume_stack` before calling the renderer, so renderer execution starts from the active pipeline rather than raw authored settings.

The compiled-scene renderer is the final authority for execution evidence. The submitted effective graph remains the source graph for the frame, but after `prepare_history_textures(...)` reports actual renderer history availability, the renderer records a frame-local `PostProcessExtract` graph through `RenderGraphStageExecution::record_post_process_graph(...)`. If history is unavailable, that frame-local graph is derived from the submitted validated stack by dropping the history resource and disabling only the history-resolve node. `RenderStats` reads node counts/final-composite metadata from the renderer graph when available. This keeps stats and executed-node evidence aligned when viewport metadata says history is compatible but the concrete history texture was just allocated, released, or resized. The compiled-scene root does not directly pair post-process graph resources with the execution record; that ownership stays inside the graph-stage execution context.

The concrete built-in graph executors now split preparation and final composition by declared pass. `post.motion-vector-clear` clear-stores `scene-motion-vector` to neutral zero in the depth-prepass stage, `post.motion-vector-camera` reconstructs camera/background screen-space velocity from current depth plus the previous submitted camera when that previous camera passes projection/target/viewport/dynamic-resolution, FOV/orthographic-size/clip-plane, and translation/rotation cut checks, `post.motion-vector-tile-max` writes the half-resolution tile target, `post.motion-vector-tile-max-coarse` writes the quarter-resolution coarse tile target, `post.motion-vector-neighbor-max` writes the full-resolution reconstructed target, `ao.ssao-evaluate` records SSAO into `ambient-occlusion`, `lighting.clustered-cull` fills `light-list`, and `post.bloom-extract` records bloom into `bloom-texture`. `post.stack` no longer dispatches those preparation passes; it consumes graph-bound `scene-depth`, `gbuffer-normal`, scene color, motion vector, AO, bloom, final color, GI target, and light-list resources for the final post-process composite. Missing post-process stack context is a hard executor error rather than a silent no-op.

The product-node executors for `post.bloom`, `post.color-grading`, `post.history-resolve`, `post.effect-stack`, `post.final-composite`, and `post.fxaa` still validate the submitted product post-process node resources through `RenderGraphExecutionResources`. They remain evidence/metadata executors for the neutral product graph, while the WGPU pixel work is owned by the pass executors above. When DoF is active, `post.effect-stack` validates the graph-visible CoC and bokeh target resources in addition to `postprocess.effect-stacked`; the pixels still run through the final post-process shader's uniform block rather than separate graph-native passes per effect family.

`RenderStats` reports `last_post_process_graph_node_count`, `last_post_process_graph_skipped_node_count`, `last_post_process_final_composite_node`, `last_post_process_graph_executed_nodes`, `last_post_process_effect_stack_report`, `last_post_process_lut_{request,ready,fallback}_count`, `last_post_process_lut_2d_strip_ready_count`, `last_post_process_lut_3d_request_count`, and `last_post_process_lut_unsupported_shape_count`. The executed-node list is separate from normal render graph passes, so product postprocess evidence does not change existing pass-order expectations such as overlay staying the last compiled graph pass. The effect-stack report is derived from the same effective settings as the graph, so direct extract and volume-authored stacks produce comparable active-family and missing-resource diagnostics. `collect_runtime_diagnostics(...)` mirrors the report's enabled state, active-family count, approximation-backed count, and missing-resource count into `DiagnosticStore` under `render.post_process.effect_stack.*` paths, and mirrors LUT resource readiness and shape status under `render.post_process.lut.request_count`, `ready_count`, `fallback_count`, `texture_2d_strip_ready_count`, `texture_3d_request_count`, and `unsupported_shape_count` for runtime/editor tooling.

## Bevy Gap Classification

Zircon currently covers the neutral product graph, bloom/color-grading/history/effect-stack/final-composite node vocabulary, graph validation, renderer execution evidence, and the FXAA node that is shared with the anti-alias surface. That is enough for DefaultRender diagnostics and pass-order accountability.

Zircon is not yet Bevy-complete for post-processing. Motion blur now has authored settings, a graph-visible raw motion-vector target, a neutral clear pass, a camera/background velocity producer, a graph-owned half-resolution tile-max pass, a graph-owned quarter-resolution coarse tile-max pass, a graph-owned full-resolution neighbor-max reconstruction pass, and a bounded final-stack shader consumer with depth-aware foreground sample attenuation, but it is still not complete because object, skinned, and particle velocity writers plus the full dynamic multi-level tile-max/neighbor-max pyramid are not implemented. Depth of field now has neutral focus/lens/bokeh controls plus graph-visible CoC and bokeh product-resource names backed by renderer-owned scratch targets, a shader-backed CoC/bokeh-prefilter prepare pass, final-pass CoC-aware bokeh sampling, and a small prepared-CoC dilation for radius/mix coverage, but it still lacks graph-native half-resolution bokeh simulation/prefilter passes, temporal CoC history, a dedicated near/far combine pass, and a resolved half-resolution bokeh policy. Chromatic aberration and vignette now have a neutral effect-stack DTO, graph/stat node, and baseline shader consumption, but they are not yet camera components or dedicated WGPU passes. MSAA writeback is represented only indirectly through camera MSAA settings and anti-alias fallback reporting; there is no Bevy-style sorted-camera MSAA writeback blit path yet.

The next Bevy-parity implementation milestone should add typed post-process authoring descriptors before adding more shader passes. The safe order is: camera-facing post-process settings, neutral graph nodes/resources, validation and stats, then concrete WGPU execution. This keeps advanced effects from bypassing the basic DefaultRender product contract.
