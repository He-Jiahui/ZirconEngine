# Plugin Bridge

The plugin bridge is the runtime-owned interface table for typed plugin-to-plugin calls. It is the 11-M1 slice of the `zircon_plugins` architecture plan: plugins can export a typed interface during extension registration, consumers can resolve strong or weak handles during finish, and the runtime keeps owner information for later unload or hot-reload work.

The bridge is intentionally separate from managers. Managers remain engine-owned global services; plugin-to-plugin synchronous calls go through bridge interfaces so dependencies, optional providers, and future hot reload behavior stay observable to the plugin system.

## Contract Layer

`zircon_runtime::core::framework::bridge::PluginInterface` is the neutral marker trait. Interface traits are defined as framework contracts and implement `PluginInterface` on the trait object, for example `impl PluginInterface for dyn PhysicsQueryInterface`.

Each interface has a stable `INTERFACE_ID` such as `physics.query.v1`. Breaking changes must use a new id. Implementations must be `Send + Sync + 'static` and must not access `World` directly; world mutation belongs in scheduled systems where `SystemParamAccess` can participate in conflict detection.

`BridgeError::Absent` is the weak-call runtime status for an interface that was not installed in the frozen bridge table. `BridgeError::NotEnabled` is reserved for an installed provider that is disabled or temporarily between generations.

## Runtime Table

`RuntimeExtensionRegistry::export_interface::<T>(owner, Arc<T>)` registers one owner-tracked export per interface id. Duplicate exports return `DuplicatePluginInterface`. `RuntimeExtensionRegistry::frozen_bridge_table()` materializes a `FrozenBridgeTable` snapshot with dense `InterfaceSlot` entries.

`FrozenBridgeTable` owns bridge entries behind shared `Arc` state, so weak bridges can keep a stable table snapshot after finish-time resolution. Each entry stores the interface id, owner module, erased provider, and generation counter. Even generations are enabled, odd generations are disabled. `interface_status(...)` reports `Absent`, `Enabled`, or `Disabled` for single-interface diagnostics, and `interface_snapshot(slot)` / `interface_snapshot_by_id(interface_id)` return one stable bridge-matrix row when the target exists. `interface_snapshots()` returns all rows: dense slot, interface id, owner module id, generation, provider-installed flag, status, and diagnostics snapshot. Snapshot status is derived from one captured generation/provider-installed pair so a row does not independently recompute its status fields. `interface_snapshots_owned_by(owner)` filters the same row model to one runtime module owner, which lets lifecycle code and editor diagnostics preview exactly which bridge exports a module owns without reading table internals. `diagnostics_summary()` aggregates the current rows into `BridgeTableDiagnosticsSummary`: total interfaces, enabled/disabled row counts, installed/missing provider counts, and debug call counters. `diagnostics_summary_owned_by(owner)` applies the same aggregate model to one runtime module owner, and `BridgeTableDiagnosticsSummary::diagnostic()` renders stable `bridge.table_summary` text for lifecycle logs or future editor diagnostics. `diagnostics_matrix()` and `diagnostics_matrix_owned_by(owner)` bundle the deterministic row set plus summary into `BridgeDiagnosticsMatrix`; `diagnostic_lines()` emits one `bridge.table_summary` row followed by stable `bridge.interface` rows for editor/log consumers. `set_enabled(...)`, `set_owner_enabled(...)`, `activate_owner(...)`, `deactivate_owner(...)`, `restore_owner_exports_with_report(...)`, `reload_owner_exports_with_report(...)`, `replace_provider(...)`, and `reload_provider(...)` are the current hooks for activate/deactivate/hot-reload wiring. Owner-level flips let lifecycle code toggle every interface exported by one runtime module in a single bridge-table operation, while `deactivate_owner(...)` also clears provider references. `restore_owner_exports_with_report(...)` reinstalls erased providers for an owner from final-registry `InterfaceExport` rows, so linked runtime module activation can recover bridge calls after a prior deactivation cleared the provider. `reload_owner_exports_with_report(...)` replaces those erased providers from replacement-registry `InterfaceExport` rows without disabling enabled entries, so a hot-reloaded runtime module can publish new provider trait objects through the same stable frozen table. The `*_with_report(...)` owner-level variants return `BridgeOwnerTransitionReport`, carrying a `BridgeOwnerTransitionMode` (`Activate`, `Disable`, `Deactivate`, or `Reload`), affected slots, and post-operation snapshots for lifecycle diagnostics. `BridgeOwnerTransitionReport::diagnostic()` renders a stable bridge.owner_transition text row that includes the owner slot, mode, affected count, interface ids, slot ids, generation, provider-installed state, and final status. The provider-installed flag lets diagnostics distinguish disabled-but-still-installed entries from deactivated entries whose provider reference has been cleared. Reloading a provider while enabled advances the generation by two so weak bridges refresh without changing enabled state; replacing while disabled waits for the later activation flip to publish the new provider.

## Strong And Weak Bridges

`StrongBridge<T>` is a direct `Arc<T>` wrapper with `Deref`, matching the strong-dependency hot path: after finish-time validation, calls are ordinary trait-object calls.

`WeakBridge<T>` stores an `InterfaceSlot`, a cloned frozen table, and a cached `(generation, Arc<T>)`. `call(...)` returns `BridgeError::Absent` when the interface was never installed in the frozen table and `BridgeError::NotEnabled` when the installed provider is disabled. When the generation matches the cached provider, the call path reuses the downcast provider; when the generation changes, the bridge refreshes from the table. `pin()` returns `BridgeGuard<T>` so a system body can resolve once and issue repeated calls through the same target.

`PluginFinishContext::resolve_strong::<T>()` and `resolve_weak::<T>()` are the lifecycle-facing entry points.

The current performance baseline lives in `extension_registry_bridge_performance_baseline.rs` and has two layers. Structural tests keep `StrongBridge<T>` layout equivalent to one `Arc<dyn Interface>` wrapper, guard the WeakBridge cached-generation hit path before table provider lookup, keep `BridgeGuard<T>` as a resolved-target wrapper without table/slot/generation fields, and verify a pinned batch records one bridge resolution in debug builds. `bridge_performance_baseline_samples_wall_clock_hot_paths` adds a wall-clock sampled baseline over direct `Arc`, `StrongBridge`, cached `WeakBridge`, and pinned `BridgeGuard` calls, emits stable `bridge.performance_sample` diagnostics, and keeps the bridge hot paths inside broad ratio budgets so regressions are visible without making normal machine-load variance a correctness failure. The same file now owns the outer native/VM bridge performance structure guards: native bridge calls must use interface slots resolved before ABI dispatch, VM bridge host callbacks must capture resolved bridge slots, `ScriptCallTable::call(...)` must dispatch by dense id, and real `zr_vm` host callbacks must capture `ScriptCallSite` rows before runtime invocation.

Linked Rust plugin registration now validates the export side of the bridge manifest contract. If a package declares `provides_interfaces`, at least one runtime module from that package must call `export_interface(...)` for that id during registration. If registration exports an interface id that the package manifest did not declare, the registration report records a diagnostic. This keeps plugin.toml from drifting away from the actual bridge table before catalog merging or future editor bridge matrices consume the data.

`RuntimePluginCatalog` now validates required bridge interface dependency closure when registration reports are merged or when plugins are registered incrementally. A dependency row with `required = true` and `interfaces = [...]` must point at a registered provider package whose manifest declares each requested interface. Optional rows remain non-blocking. Missing providers or missing interface declarations produce `bridge.strong_dependency_missing` diagnostics that include the dependency chain, for example `weather -> physics -> scene`.

The catalog also exposes `strong_bridge_dependents(provider_package_id)`. It returns the packages that declare required bridge interface dependencies on the provider, with the requested interface ids grouped per dependent. `strong_bridge_disable_blockers(provider_package_id)` projects the same data into explicit blocker rows so the planned M3 runtime path can reject disabling a strong dependency target while dependents are active. Each blocker can render a stable `bridge.strong_target_disable_blocked` diagnostic that names the provider, dependent, and required interfaces.

Catalog runtime extension merging now carries `InterfaceExport` rows into the final merged `RuntimeExtensionRegistry` instead of leaving them only in each registration report. The merge path re-interns the original owner module name into the target registry before calling `register_interface_export(...)`, so the frozen bridge table built from `RuntimeExtensionCatalogReport.registry` keeps the same owner semantics as resources, events, and systems. `RuntimeExtensionRegistry::interface_owners_for_runtime_modules(...)` provides the lifecycle-facing owner lookup over that merged table.

`RuntimePluginCatalog::activate_bridge_provider_at_frame_boundary(...)`, `disable_bridge_provider_at_frame_boundary(...)`, `deactivate_bridge_provider_at_frame_boundary(...)`, and `reload_bridge_provider_at_frame_boundary(...)` are the M3 catalog-level lifecycle surface. They resolve the provider package's runtime modules from `PluginPackageManifest.modules`, find matching interface owners in the merged registry, and call the owner-level bridge table transition APIs. Activation restores owner providers from the final registry before enabling rows, which closes the provider-clearing gap left by deactivation. Reload keeps the current owner slots from the active registry but reads replacement `InterfaceExport` rows from the replacement registry, so new provider objects can be published even if the reloaded registration produced different owner slot ids. Disable and deactivate first consult `strong_bridge_disable_blockers(...)`; strong dependents produce `RuntimePluginBridgeLifecycleError::StrongDependentsBlocked` with a `RuntimePluginBridgeLifecycleBlock` that keeps the provider id, transition mode, blocker rows, and stable diagnostic text.

`RuntimePluginBridgeLifecycleState` bundles a `RuntimePluginCatalog`, the final `RuntimeExtensionCatalogReport`, and one frozen bridge table built from that final registry. Frame-boundary callers can keep this state instead of passing catalog/registry/table triples around. Weak bridges resolved from `state.bridge_table()` observe the same generation changes produced by `state.disable_provider_at_frame_boundary(...)`, `state.activate_provider_at_frame_boundary(...)`, `state.deactivate_provider_at_frame_boundary(...)`, and `state.reload_provider_at_frame_boundary(...)`. `RuntimePluginBridgeLifecycleEvent` provides the event-shaped input for CoreRuntime/plugin wiring, including `reload_provider(...)` for replacement-registry reloads, and `state.apply_provider_lifecycle_event(...)` returns `RuntimePluginBridgeLifecycleOutcome::Applied(report)` or `Blocked(error)` with stable diagnostic text. `state.provider_package_id_for_runtime_module(...)` maps linked runtime module names back to provider package ids for `CoreRuntime` module lifecycle routing. `state.diagnostics_summary()` returns the current table aggregate for lifecycle logs.

`CoreRuntime` and `CoreHandle` now provide the M3 runtime-side state slot and provider lifecycle facade: `install_plugin_bridge_lifecycle_state(...)`, `plugin_bridge_lifecycle_state()`, `apply_plugin_bridge_lifecycle_event(...)`, `activate_plugin_bridge_provider_at_frame_boundary(...)`, `disable_plugin_bridge_provider_at_frame_boundary(...)`, `deactivate_plugin_bridge_provider_at_frame_boundary(...)`, and `clear_plugin_bridge_lifecycle_state()`. `zircon_app` registration-aware bootstrap installs a lifecycle state for linked runtime plugin registration reports before module activation, so startup-provided bridge exports are immediately available to the runtime event surface. `CoreHandle::activate_module(...)` / `deactivate_module(...)` now route linked runtime plugin modules through that lifecycle state: activation restores providers from the final registry, while deactivation applies provider deactivation before unloading services and returns `CoreError::PluginBridgeLifecycleBlocked(...)` without unloading when strong bridge dependents reject the transition.

`NativePluginLiveHost` now has runtime `*_with_bridge_lifecycle(...)` helpers for load, unload, and hot reload. These helpers apply `RuntimePluginBridgeLifecycleEvent` against a supplied `RuntimePluginBridgeLifecycleState` and retain the structured result in `NativePluginLiveHostBridgeLifecycleReport`. Runtime load publishes provider activation, runtime hot reload applies provider reload against the replacement registry, and runtime unload first attempts provider deactivation and returns the blocked diagnostic without dropping the native handle when a strong bridge dependent is present.

`NativePluginLiveHost::runtime_bridge_call_scope_from_loaded_manifest(...)` connects the M4 native bridge metadata path to the live-host loaded-plugin table. It reads the loaded runtime package manifest, pairs `provides_interfaces.methods` with caller-supplied `NativeBridgeMethodBinding` callbacks, resolves the descriptors through the active bridge lifecycle table, and returns a `NativeHostBridgeCallScope` ready for `ZrHostApiV3.bridge.call`.

`NativePluginLiveHost::install_runtime_bridge_method_bindings(...)` is the host-side binding registry for native bridge methods. The install step is allowed only for an already loaded runtime plugin with a package manifest, and it validates the manifest/binding pair before storing the callbacks. `runtime_bridge_call_scope_from_installed_bindings(...)` then rebuilds descriptors from the current loaded manifest and those installed callbacks, so a reloaded package can move method slots in `provides_interfaces.methods` without requiring callers to re-pass the callback list. ABI v3 runtime entry reports now expose `bridge_methods` as a DLL-level callback table; live-host runtime load and hot reload parse that table into `NativeBridgeMethodBinding` rows, validate them against the manifest, replace the installed binding registry, and emit discovery diagnostics. Runtime unload clears the installed set so stale DLL callback pointers are not retained. `reload_runtime_bridge_provider_and_scope_from_installed_bindings(...)` combines `RuntimePluginBridgeLifecycleEvent::reload_provider(...)` with current-loaded-manifest descriptor rebuild and returns `NativePluginLiveHostBridgeReloadReport`, carrying the bridge lifecycle report, rebuilt `NativeHostBridgeCallScope`, and stable diagnostics including the rebuilt method count. `clear_runtime_bridge_method_bindings(...)` remains the explicit teardown helper for embedders and now uses the same poison-recovering binding-table lock helper as install/reload paths.

In debug builds, each bridge entry also records lightweight weak-bridge diagnostics. `WeakBridge::call(...)` and `WeakBridge::pin()` increment enabled-call or not-enabled counters on the target slot, and `FrozenBridgeTable::diagnostics(slot)` returns a `BridgeDiagnosticsSnapshot`. `BridgeInterfaceSnapshot` embeds the same counter snapshot so editor and runtime diagnostic consumers can render the table without reading bridge internals. `BridgeInterfaceSnapshot::diagnostic()` gives each row stable text with slot, interface id, owner module slot, generation, provider-installed state, status, and call counters. Release builds keep the same public snapshot and matrix API but compile the counters to zero so the editor bridge matrix data plane has no release hot-path cost.

Editor play-mode snapshots now consume the bridge matrix data plane. `EditorRuntimePlayModeBackendReport` can carry an optional `BridgeDiagnosticsMatrix`, and the native plugin play-mode backend can be constructed with a `RuntimePluginBridgeLifecycleState` so project plugin load/exit operations publish the current bridge table diagnostics. Workbench enter/exit play-mode handling projects any supplied matrix into `EditorBridgeDiagnosticsSnapshot`, storing summary rows, owner module slots, status text, call counters, and stable diagnostic lines on `EditorDataSnapshot`; reports without a matrix and failed enter paths clear the snapshot to the default empty matrix.

## Native ABI Bridge Calls

`ZrHostBridgeApiV1::call` is the public Native ABI entry point for pre-resolved bridge calls. It receives a runtime plugin handle, dense interface slot, method slot, input byte slice, and borrowed output buffer. `NativeHostApiV3RegistrationScope` exposes the symbol but returns `UnsupportedVersion` because registration-time host tables should not execute bridge calls.

`NativeHostBridgeCallScope` is the runtime-call adapter. It stores a cloned `FrozenBridgeTable` plus a method dispatch map keyed by `(InterfaceSlot, method_slot)`, exposes `method_count()` for reload/report checks, then exposes the same `ZrHostApiV3.bridge.call` callback. The callback maps the bridge table status to stable ABI statuses: absent slots and missing methods return `NotFound`, installed but disabled or provider-missing rows return `BridgeNotEnabled`, and invalid non-empty null payloads return `InvalidArgument`. Enabled rows increment the bridge enabled-call counter before dispatching the registered native method; disabled rows increment the not-enabled counter before returning.

Native method metadata can now build that dispatch table without hand-writing dense interface slots. `NativeBridgeMethodDescriptor` carries an interface id, method slot, and method function. `NativeHostBridgeCallScope::from_method_descriptors(...)` resolves each interface id against the frozen bridge table, returns `MissingPluginInterface` for unknown metadata, and stores the resolved `(InterfaceSlot, method_slot)` entries for ABI calls. Package manifests now provide the shared reflection source through `provides_interfaces.methods`; `native_bridge_method_descriptors_from_manifest(...)` pairs those rows with native code bindings, rejects duplicate/missing/unknown bindings, and produces the native descriptors consumed by the call scope. `NativeBridgeMethodFn` wraps either an in-process Rust callback or a DLL ABI v3 callback plus `user_data`, so tests and dynamic packages use the same descriptor path. `bridge_method_bindings_from_abi_v3(...)` parses the DLL-exposed table into owned bindings before the live host validates them against the manifest.

## VM Host Bridge Calls

VM-side bridge access is wired through the current script host export system instead of a parallel lookup path. `register_bridge_host_module(...)` registers the `zr.zircon.bridge` host module with `bridge.call` capability and one host function per `ScriptBridgeMethodDescriptor`. Each descriptor carries a script-facing function name, interface id, method slot, return kind, optional parameters/capabilities/documentation, and a Rust dispatch callback. `script_bridge_method_descriptors_from_manifest(...)` and `register_bridge_host_module_from_manifest(...)` now use the same `provides_interfaces.methods` rows as native bridge descriptors, preserving return kind, parameters, method-specific capabilities, and documentation.

During registration, the builder resolves each interface id against the frozen bridge table and stores the dense `InterfaceSlot` in the callback. At call time, the callback checks the bridge row status before invoking the method. Disabled or provider-missing rows return a script host error containing "not enabled" and increment the bridge not-enabled diagnostic counter; enabled rows increment the enabled counter and invoke the registered method with `ScriptBridgeCall { interface_slot, method_slot, arguments }`.

`HostExportRegistry::script_call_table()` now snapshots registered host export callbacks into dense `ScriptCallSite` rows. The real `zr_vm` backend uses that table while registering host native functions, so VM callbacks for both built-in modules and `zr.zircon.bridge` dispatch through a pre-resolved call site instead of repeating module/function lookup at runtime.
