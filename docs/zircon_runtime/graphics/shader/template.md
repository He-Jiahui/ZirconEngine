# Shader Template Assembly

## Purpose

Shader template assembly foundation is the Plan 08 MS-M1 graphics-side bridge between the backend-neutral `GeometrySourceDescriptor` contract and future material pipeline compilation. It gives graphics code one folder-backed owner for composing material WGSL from geometry-source includes, material surface code, shared surface types, optional shading helpers, and pass templates.

This module deliberately stops before WGPU object creation. It does not create shader modules, bind group layouts, render pipelines, or cache entries. Those remain later slices under the mesh pipeline cache, shader prewarm, and runtime fallback-material cutover.

## Behavior Model

`MaterialShaderTemplateRequest` carries these inputs:

- `geometry_source`: a `GeometrySourceDescriptor` from `core/framework/render/shader/geometry_source.rs`.
- `pass_type`: the `ShaderPassType` to assemble.
- `features`: `ShaderFeatureBits`, currently used by pass specialization for alpha-test depth and shadow behavior.
- `shading_model_descriptor`: optional `ShadingModelDescriptor` metadata for passes that need a shading include.
- `material_surface_source` plus `material_surface_entry`: authored or generated WGSL surface code that will be renamed to `zr_material_surface`.

`assemble_material_shader_template(...)` emits `MaterialShaderTemplateAssembly`. The output includes the final WGSL source, ordered include tokens, include content hashes, and template revision `zr-material-template-v1`. The hash list is intentionally part of the output because later disk-cache and prewarm work need stable invalidation inputs before WGPU compilation runs.

The assembler imports `GeometrySourceDescriptor` and built-in geometry include tokens through the `core::framework::render` facade. The 2026-06-24 root GeometrySource facade restoration keeps that public path available by thinly forwarding descriptor and include-token constants from `render/shader`; it does not move include lookup, source assembly, or validation behavior out of this folder-backed graphics owner.

Standard material template surface foundation adds `standard_material_surface_source(...)` as the built-in StandardPBR material source input for this assembler. ## Design And Rationale

The owner mirrors the engine structure rule that root modules stay thin. Include token lookup, module import resolution, dependency ordering, and content hashing live in `module_registry.rs`; pass-specific policy lives in `pass_specialization.rs`; standard material source projection lives in `material_surface.rs`; WGSL parse/validation lives in `validation.rs`; source rewriting and assembly validation live in `assemble.rs`.

The assembler rejects material-declared functions that use reserved `zr_`, `fetch_`, or `shade_` prefixes. This prevents generated material code from shadowing engine-owned template symbols before later Naga validation is available. It also rejects missing or duplicate material surface entry declarations so the template path cannot silently choose the wrong function.

The module registry uses `include_str!` and `blake3::hash` for built-in template content and also accepts request-local asset include sources supplied by `ResourceStreamer`. Built-in template chunks and asset module chunks use the same token de-duplication and content-hash path, so an authored `#include <zr_surface_types.wgsl>` cannot duplicate the baseline surface-types chunk and a changed project module can invalidate the assembled source. Plugin manifest-level module registration, asset-root include revision propagation, and source-only project import dependency propagation are now covered by focused SH03-M2 follow-ups; broader product/RenderDoc gates remain tracked in the shader plans.

## Control Flow

`assemble_material_shader_template(...)` first asks `pass_specialization::pass_template_for(...)` whether the selected pass needs a material surface, pass support includes, and a Forward shading include. Forward now carries light-grid/shadow support through `support_includes`, then resolves the shading include from the optional `ShadingModelDescriptor.forward_include` and any request-local sources supplied through `with_shading_model_forward_include_source(...)`; DepthPrepass and Shadow include material surface code only when `ShaderFeatureBits::ALPHA_TEST` is present. In that case they also select `zr_template_depth_alpha.wgsl` or `zr_template_shadow_alpha.wgsl`, whose fragment entry evaluates `zr_material_surface(input)` only to call `zr_apply_alpha_clip(surface)`. Velocity uses geometry previous-position fetch; non-alpha Velocity does not include material surface code, while alpha-test Velocity selects `zr_template_velocity_alpha.wgsl` and includes material surface code only for alpha discard.

`assemble_deferred_gbuffer_shader_template(...)` follows the same scene/GPUScene/surface/geometry/material assembly path, but it resolves `ShadingModelDescriptor.gbuffer_encode_include` through `shading_model_gbuffer_include_for(...)` before the material surface and dedicated deferred GBuffer entry template are appended. The template entry calls `encode_gbuffer(surface, zr_build_shading_context(input))`, so the selected include owns packing policy while the entry template owns alpha discard and output entry points.

The module registry then resolves `GeometrySourceDescriptor::wgsl_include_token`. Unknown geometry tokens produce `ShaderTemplateAssemblyError::UnknownGeometryInclude` rather than falling back to static mesh behavior, and unknown authored module tokens produce `ShaderTemplateAssemblyError::UnknownModuleInclude`. This keeps new geometry sources and project modules explicit and avoids hidden compatibility paths.
