# Mesh Pipeline Cache

`MeshPipelineCache` owns built-in mesh WGPU pipeline state for the scene renderer. It keeps shader modules, forward base mesh pipelines, deferred GBuffer pipelines, depth-prepass normal-target pipelines, velocity pipelines, TAA auxiliary pipelines, shadow pipelines, and the pass/pipeline variant registry used by the MD-M1 mesh command layer.

Prewarm opt-in WGPU render-pipeline validation reuses these pass-specific mesh pipeline constructors without moving WGPU types into the framework contract layer. `prewarm_pipeline_validation.rs` builds a validation-only pipeline layout for scene, shadow receiver, material, and GPUScene bind groups, then maps each `ShaderVariantPrewarmRequest` pass to the same Forward/GBuffer/DepthPrepass/Shadow/Velocity/TAA reactive-mask creation functions used by runtime mesh cache paths. `zircon_shader_prewarm --validate-wgpu-pipelines` calls this helper before writing staged cache entries and records `wgpu_pipeline_validation` counts. The focused WGPU pass also fixed the offscreen device limit contract: full mesh forward validation needs `MESH_FORWARD_PIPELINE_REQUIRED_STORAGE_BUFFERS_PER_SHADER_STAGE = 12`, so render backend device requests now take the max of HZB and mesh-forward storage-buffer requirements when the adapter supports it. Status: `render_plan08_prewarm_wgpu_render_pipeline_validation_gate_focused_tests_passed_product_deferred`; guard: `runtime_15_shader_prewarm_wgpu_render_pipeline_validation_is_wired`; focused tool anchor: `test_build_command_forwards_wgpu_shader_pipeline_validation`. Product miss=0, no-proxy staged execution, and RenderDoc/product capture remain separate gates.

## Variant Registry

`MeshPipelineVariantRegistry` assigns stable `MeshPipelineVariantId` values for cache-backed pipeline variants. Its key is `MeshPassPipelineKind` plus the complete `PipelineKey`, so the same material pipeline used by the base pass and motion-vector pass resolves to different ids. Repeated requests for the same pass and pipeline shape reuse the same id.

Each `MeshPipelineVariantKey` also stores the Plan 08 neutral `ShaderVariantKey` derived from that `PipelineKey`. The registry maps base and TAA reactive passes to `ShaderPassType::Forward`, deferred GBuffer and current normal-target depth prepass variants to `ShaderPassType::GBuffer`, shadow variants to `Shadow`, and motion vectors to `Velocity`, using `wgpu-runtime` as the current platform token. DepthPrepass uses the GBuffer template today because the compiled graph pass still writes `GBUFFER_NORMAL` alongside `SCENE_DEPTH`; Deferred GBuffer uses a dedicated albedo/material template source because it writes `GBUFFER_ALBEDO` and `GBUFFER_MATERIAL`. The pure depth-only template is now covered by built-in standard-material staged prewarm source/hash tests, but it remains a future runtime/product graph contract until normal production is separated.

The registry also records a per-frame `ShaderVariantMissReport`. Variant id resolution counts requests and memory hits. Base mesh shader-module creation adds disk hits, compile misses, disk writes, and disk errors when it consults `ShaderVariantCacheDisk`. The report now carries `dimension_summary` rows keyed by pass type, geometry source id, shading model id, and quality tier, so runtime/product staged-prewarm evidence can be compared directly against build-time prewarm report dimensions.

The report also exposes cumulative pipeline-shape gauges for startup and permutation profiling. `registered_pipeline_variant_count` counts full mesh registry keys, `registered_shader_variant_count` counts their unique `ShaderVariantKey` values, and `texture_presence_normalized_pipeline_variant_count` counts full keys after clearing only base-color, metallic-roughness, occlusion, and emissive texture-presence booleans. Their difference is reported as `texture_presence_equivalent_pipeline_variant_count`; it is a targeted upper bound on registry expansion from those four runtime resource-presence values, not proof that every registered key created a WGPU object. `cached_render_pipeline_count` separately sums the eight live mesh pipeline maps and excludes asynchronous jobs that are still pending, while `cached_shader_module_count` reports the live mesh shader-module cache. Those two fields are current residency gauges. `render_pipeline_creation_count` and `shader_module_creation_count` separately count every actual WGPU mesh creation call across synchronous, background, and live-manifest prewarm paths, including calls whose later validation scope rejects the object. Their paired `*_creation_cpu_microseconds` fields accumulate only the CPU wall-clock interval of the WGPU creation call itself; they exclude source assembly, async queue wait, error-scope polling, and cache insertion. `async_base_pipeline_queue_wait_count` and `async_base_pipeline_queue_wait_microseconds` separately count jobs that actually start on the background Base worker and the cumulative wall-clock interval from successful queue admission until each job starts. Rejected, duplicate, full-queue, worker-unavailable, and synchronous paths do not create wait samples. A shared locked snapshot lets the background Base worker publish each rare count/time pair coherently without adding work to cache-hit draw paths. These gauges are published under `render.shader_variant.*` in `DiagnosticStore`, so cold-start tooling can correlate registration expansion, queue pressure, creation cost, and live residency without scanning logs or traversing registry storage each frame. The PBR viewer also snapshots the same report after its Ready render into evidence schema v12; the sidecar verifier requires nonzero registered and resident Base GPU objects and preserves v2-v11 only for explicit historical inspection.

Async WGSL validation has a separate cumulative measurement row under `render.shader_variant.source_validation.*`. It records `queued`, `already_pending`, `full`, and `worker_unavailable` admission outcomes; actual worker job, unique source-contract, duplicate-job, success, and failure counts; and cumulative queue-wait and Naga validation CPU microseconds. The worker body also emits the `render/shader_pipeline/source_validation_worker` profiler scope for distribution analysis. A source contract is the exact WGSL hash plus diagnostic-segment provenance, independent of the full material/PSO variant used by the current validation-state key. Duplicate detection occurs only when a job starts, allocates only for a newly observed source contract, and does not touch installed-pipeline draw/cache-hit/replay paths. These counters are evidence for a future compiler-result identity decision; they do not by themselves authorize source-only caching or change hot-reload and diagnostic behavior.

Mesh shader publication also validates fragment outputs against the actual pass color-target numeric contract. Base uses the renderer target format; GBuffer and HitProxy consume their existing format owners; Velocity and both TAA reactive targets use fixed Mesh-owned constants; DepthPrepass, Shadow, and OIT have no color targets. Compatibility mirrors locked wgpu-core behavior: only a shader output paired with a present target is checked, and the target scalar kind/width/component count must be covered by the shader output. Extra shader outputs and unwritten targets remain legal. The contracts are built once with the cache and are checked only for a new reflected source or cached module admission before disk publication and WGPU pipeline creation; installed draw and cache-hit paths do not consult them.

Variant id `0` is intentionally left outside the registry for any remaining fixed pass-owned pipelines. Base, Deferred GBuffer, DepthPrepass, Velocity, TAA reactive, and Shadow mesh command paths now use registry ids so command sorting and replay can distinguish cache-backed variants by stable `MeshPipelineVariantId` values instead of fixed sentinels.
