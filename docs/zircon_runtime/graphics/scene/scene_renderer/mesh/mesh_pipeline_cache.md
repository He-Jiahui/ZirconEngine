# Mesh Pipeline Cache

`MeshPipelineCache` owns built-in mesh WGPU pipeline state for the scene renderer. It keeps shader modules, forward base mesh pipelines, deferred GBuffer pipelines, depth-prepass normal-target pipelines, velocity pipelines, TAA auxiliary pipelines, shadow pipelines, and the pass/pipeline variant registry used by the MD-M1 mesh command layer.

Prewarm opt-in WGPU render-pipeline validation reuses these pass-specific mesh pipeline constructors without moving WGPU types into the framework contract layer. `prewarm_pipeline_validation.rs` builds a validation-only pipeline layout for scene, shadow receiver, material, and GPUScene bind groups, then maps each `ShaderVariantPrewarmRequest` pass to the same Forward/GBuffer/DepthPrepass/Shadow/Velocity/TAA reactive-mask creation functions used by runtime mesh cache paths. `zircon_shader_prewarm --validate-wgpu-pipelines` calls this helper before writing staged cache entries and records `wgpu_pipeline_validation` counts. The focused WGPU pass also fixed the offscreen device limit contract: full mesh forward validation needs `MESH_FORWARD_PIPELINE_REQUIRED_STORAGE_BUFFERS_PER_SHADER_STAGE = 12`, so render backend device requests now take the max of HZB and mesh-forward storage-buffer requirements when the adapter supports it. Status: `render_plan08_prewarm_wgpu_render_pipeline_validation_gate_focused_tests_passed_product_deferred`; guard: `runtime_15_shader_prewarm_wgpu_render_pipeline_validation_is_wired`; focused tool anchor: `test_build_command_forwards_wgpu_shader_pipeline_validation`. Product miss=0, no-proxy staged execution, and RenderDoc/product capture remain separate gates.

The 2026-07-05 scene-environment refresh keeps that validation layout aligned with the live renderer scene bind group. The validation scene group now mirrors `SceneRendererCore` binding 0 as the scene uniform buffer, binding 1 as the `texture_cube<f32>` source environment view, and binding 2 as the filtering environment sampler consumed by `zr_environment.wgsl`. The local DepthPrepass, GBuffer, Shadow, Velocity, and TAA test-support scene layouts follow the same contract, so project/plugin material-pass staged prewarm validates the same environment resource shape that runtime Forward/GBuffer/Shadow pipelines use instead of a stale scene group that only exposed binding 0. ## Variant Registry

`MeshPipelineVariantRegistry` assigns stable `MeshPipelineVariantId` values for cache-backed pipeline variants. Its key is `MeshPassPipelineKind` plus the complete `PipelineKey`, so the same material pipeline used by the base pass and motion-vector pass resolves to different ids. Repeated requests for the same pass and pipeline shape reuse the same id.

Each `MeshPipelineVariantKey` also stores the Plan 08 neutral `ShaderVariantKey` derived from that `PipelineKey`. The registry maps base and TAA reactive passes to `ShaderPassType::Forward`, deferred GBuffer and current normal-target depth prepass variants to `ShaderPassType::GBuffer`, shadow variants to `Shadow`, and motion vectors to `Velocity`, using `wgpu-runtime` as the current platform token. DepthPrepass uses the GBuffer template today because the compiled graph pass still writes `GBUFFER_NORMAL` alongside `SCENE_DEPTH`; Deferred GBuffer uses a dedicated albedo/material template source because it writes `GBUFFER_ALBEDO` and `GBUFFER_MATERIAL`. The pure depth-only template is now covered by built-in standard-material staged prewarm source/hash tests, but it remains a future runtime/product graph contract until normal production is separated.

The registry also records a per-frame `ShaderVariantMissReport`. Variant id resolution counts requests and memory hits. Base mesh shader-module creation adds disk hits, compile misses, disk writes, and disk errors when it consults `ShaderVariantCacheDisk`. The report now carries `dimension_summary` rows keyed by pass type, geometry source id, shading model id, and quality tier, so runtime/product staged-prewarm evidence can be compared directly against build-time prewarm report dimensions.

Variant id `0` is intentionally left outside the registry for any remaining fixed pass-owned pipelines. Base, Deferred GBuffer, DepthPrepass, Velocity, TAA reactive, and Shadow mesh command paths now use registry ids so command sorting and replay can distinguish cache-backed variants by stable `MeshPipelineVariantId` values instead of fixed sentinels.

`MeshPipelineCache` implements `MeshPipelineVariantResolver`. `SceneRendererCore::render_compiled_scene` and overlay mesh recording pass the live cache into `build_mesh_pass_command_buffers`, while unit tests pass a pure `MeshPipelineVariantRegistry`. `MeshPassBuildContext` forwards processor requests to that resolver when processors create `MeshDrawCommand` values. The context uses `MeshDrawQueueProfile::shader_geometry_source_id()` rather than the raw queue geometry source, which lets draw construction choose explicit production source metadata before the resolver requests a shader variant. Direct CPU-morphed draw-source metadata extends that bridge for CPU-baked morphs: active direct morph weights can still create `PendingMeshGeometry::CpuMorphed`, pending command cache extract/plan preserve `DynamicCpuMorphedSource`, `uses_cpu_morphed_source()` exposes the classification, and the shader variant dimension remains `GEOMETRY_SOURCE_ID_STATIC_MESH`. CPU-morphed GPU-skinning draw-source metadata extends the same bridge for fallback skinned morphs: `PendingSkinnedGpuSource::CpuMorphed` maps to `DynamicCpuMorphedGpuSkinningSource`, `uses_cpu_morphed_gpu_skinning_source()` preserves that draw classification, prepared queue stats keep it dynamic, and the queue profile resolves to `GEOMETRY_SOURCE_ID_SKINNED_MESH`. Morph payload projection and Morph payload slot indexing give direct morph draws a data handoff to GPUScene storage: `morph_payload_upload.rs` projects active position/normal/tangent/color rows into `GpuMorphDelta` / `GpuMorphWeight`, emits `GpuMorphPayload` headers, writes `PendingMeshDraw.morph_payload_slot`, and uploads/deduplicates those rows before GPUScene draw sync. Morph geometry-source selection now consumes that slot in `build_mesh_draws/build/geometry_source_selection.rs`: payload-backed direct non-skinned morphs use `PendingMeshGeometry::GpuMorphed` and `DynamicGpuMorphedSource` (`GEOMETRY_SOURCE_ID_MORPHED_MESH`), while payload-backed skinned morphs keep the original `PendingSkinnedGpuSource::Prepared` mesh and use `DynamicGpuSkinnedMorphedSource` (`GEOMETRY_SOURCE_ID_SKINNED_MORPHED_MESH`). CPU-baked fallbacks remain Static/Skinned to avoid double morph.
