# Runtime UI Surface Input

`zircon_runtime::ui::surface::input` applies the shared M5 input contract to retained runtime UI surfaces. The module is intentionally below `surface/` because `UiSurface` owns focus, capture, navigation, tree dirty state, and retained frame data; hosts only translate native input into shared DTOs and consume host requests returned by dispatch.

## Module Shape

`mod.rs` is structural. It exposes `UiSurfaceInputState` publicly through `zircon_runtime::ui::surface` and keeps `apply_dispatch_reply(...)` plus `dispatch_input_event(...)` crate-private implementation details called by `UiSurface` methods.

`window_pump.rs` is the runtime-local bridge from `zircon_runtime_interface::ui::window::UiWindowInputPumpEvent` into the existing surface input manager. `Input(...)` pump entries delegate directly to `dispatch_input_event(...)`, preserving the normal pointer, keyboard, text, IME, drag/drop, popup, tooltip, accessibility, and navigation reducers. `Window(...)` entries do not consume native window actions, close windows, or own app lifecycle policy. They do retain observable `UiSurface.window_state` facts for focus gain/loss, application activation/inactivation, occlusion, close request, closed, destroyed, metrics, position, and redraw requests so `UiSurfaceFrame.window_state` remains the single frame-level diagnostic source. A `CursorMoved` window event first projects through `UiWindowEvent::normalized_cursor_move_input()` and then delegates to the unified dispatcher, so hover hit-testing, route traces, component hover events, and pointer diagnostics stay identical to ordinary pointer `Move` input while preserving window metadata. Focus loss, application deactivation, and non-client-area window actions still ask the interface DTO for a `transient_dismissal_effect()`. When such an effect exists, the bridge synthesizes a `UiInputEvent::Popup` dismissal named `window.transient` from `UiWindowInputContext::from_window_metadata(...)` and applies a handled `DefaultAction` reply through `apply_dispatch_reply(...)`. This keeps window focus loss, application deactivation, and non-client-area menu dismissal on the same `UiDispatchReply` / `UiDispatchEffect` path as Escape, outside-pointer dismissal, and widget-originated popup replies. Mouse-like pointer input records a runtime-owned last cursor point; CursorLeft and close/destroy events reuse that point to dispatch pointer `Cancel`, clear retained hover, and clear the cursor point. If a hover-clearing window event arrives with no recorded mouse point, the bridge clears stale hover/pressed/capture state without inventing coordinates and records `window_pointer_cancel_missing_point`. Window lifecycle events that only update retained frame facts return handled `DefaultAction` results annotated with the specific lifecycle note; window events with no runtime input or retained-state effect still return an unhandled, unrouted result annotated with `window_event` and `window_input_pump` diagnostics. `UiSurface::dispatch_window_input_pump_event(...)` and `UiSurface::dispatch_window_input_pump_batch(...)` are thin facades over this child module.

`zircon_runtime_interface::ui::window::runtime_event_to_window_input_pump_event(...)` is the interface-owned adapter from `ZrRuntimeEventV1` ABI events into this same pump vocabulary. It sits upstream of `surface/input/window_pump.rs`: it decodes ABI event constants, payload bytes, and host context into `UiWindowInputPumpEvent` or ordered batches while returning typed errors for malformed events and ABI states that do not yet have a shared pump DTO. Full dynamic-session/app forwarding through the adapter is still a later runtime-boundary slice; the 2026-06-12 wheel-at-point work only keeps the existing app host and dynamic ABI reducer compatible with coordinate-present wheel events.

`RuntimeUiManager` now exposes platform-input, normalized-input, and window-pump facades at the runtime UI manager boundary. `dispatch_platform_input_event(...)` and `dispatch_platform_input_batch(...)` accept `UiWindowPlatformInputEvent` values from GenericApplication-style host callbacks, normalize them through the shared interface DTO, and then reuse the same manager-owned dispatch path as already-normalized input. `dispatch_input_event(...)` accepts an already-normalized `UiInputEvent`, forwards it to `UiSurface::dispatch_input_event(...)`, and then calls the existing dirty-surface rebuild helper. `dispatch_input_batch(...)` repeats that same normalized-input route in order for callers that already have a callback batch, so every event receives the same per-event router/focus/capture/rebuild treatment as the single-event facade. `dispatch_window_input_pump_event(...)` and `dispatch_window_input_pump_batch(...)` do the same for `UiWindowInputPumpEvent` / batch values. Window `Created`/`Resized` metrics also update the manager's current root viewport size after the surface accepts the event; the following dirty rebuild and `build_frame()` therefore use the latest logical window size instead of the constructor fallback. Window-pump batches are reduced through the single-event facade one event at a time, so a resize followed by pointer input in the same batch refreshes geometry and hit data before that pointer is routed. Manager-level normalized, platform, and window-pump batches now share the same host diagnostics contract: a later `UiTreeError` stops the remaining batch and reports `normalized input batch index N`, `platform input batch index N`, or `window input pump batch index N`, while earlier accepted events have already updated focus, retained window facts, dirty domains, root viewport, and frame output. `runtime_ui/input_router.rs` gives the manager its own retained pointer/navigation dispatcher set, so runtime host code registers node-bound handlers through `register_pointer_handler(...)`, phase-qualified pointer handlers through `register_pointer_phase_handler(...)`, and navigation handlers through `register_navigation_handler(...)`, then hands platform input, normalized input, window, or ABI events to the manager without threading dispatcher instances through every call. The pointer phase entry is the manager-facing form of the same Slate-style `OnPreviewMouseButtonDown` tunnel / target / bubble chain already implemented by `UiPointerDispatcher`; a PreviewTunnel handler can stop before target handlers while the result still records the hit target and route steps from the shared surface. The router is deliberately manager-owned, not a second routing implementation: it delegates to `UiPointerDispatcher` / `UiNavigationDispatcher`, while `UiSurface` still owns hit paths, focus paths, capture, hover, route traces, reply effects, and dirty-domain rebuilds. Loading a new builtin fixture resets the manager-owned router, covering ordinary pointer handlers, phase-qualified pointer handlers, and navigation handlers, so stale node ids from one surface cannot handle, capture, or navigate input on a rebuilt fixture. `runtime_ui/window_event.rs` adds the ABI-facing sibling methods `dispatch_runtime_event(...)` and `dispatch_runtime_event_batch(...)`: they call `zircon_runtime_interface::ui::window::runtime_event_to_window_input_pump_event(...)` for each ABI event, map adapter or tree failures into `RuntimeUiManagerError`, and reuse the same single-event pump facade. The manager-level ABI batch deliberately converts and dispatches one event at a time, matching GenericApplication/Slate callback order: a later malformed, no-equivalent, or successfully adapted but dispatch-failing ABI event stops the batch and reports the failing batch index with the underlying error, but earlier accepted events have already updated retained window facts, focus state, dirty domains, root viewport, and frame output. Because the runtime-event batch facade reuses the same event-ordered pump reducer, ABI viewport metrics followed by an ABI mouse button in the same batch also rebuild geometry before pointer hit testing. `RuntimeUiManager` and `RuntimeUiFixture` are now crate-private production re-exports from `zircon_runtime::ui`, not `#[cfg(test)]` helpers, so runtime-owned modules such as the dynamic session can consume the manager without making the demo/host surface public outside the crate. This keeps future host-editor input/window intake on the shared surface reducer while preserving the manager's existing retained-frame contract: lifecycle-only events update `surface.window_state`/`surface_frame().window_state`, layout-metric events update the manager root viewport and recompute only the dirty retained surface domains before `build_frame()`, and platform/pointer/navigation/ABI input can reach the manager-owned router before returning unified `UiDispatchReply` effects. Full dynamic runtime session/app forwarding through the adapter is still a later boundary slice; this wheel-at-point slice only updates app host emission and dynamic ABI wheel reduction so the current non-adapter session path stays compatible with the shared ABI contract.

`state/mod.rs` stores the aggregate transient per-surface input ownership that does not belong on individual widgets, while child modules own each retained-state family. The root keeps the captured pointer id, high-precision owner, pointer-lock owner/policy, input-method owner, latest input-method request, last mouse-like cursor point, and the `UiSurfaceInputState` field layout. `state/popup_tooltip.rs` owns popup stack and tooltip candidate state; `state/drag_drop.rs` owns the active drag/drop session and pointer/session owner checks; `state/pointer_drag.rs` owns widget pointer-drag start/current metrics; `state/pointer_position.rs` owns the last cursor point used by window cancel projection; and `state/analog.rs` owns analog control values plus analog navigation repeat gates. Pointer-capture cleanup is owner-aware: the shared captured pointer id is cleared for capture loss, and high-precision ownership is cleared only when it belongs to the released or replaced captor. Pointer-drag state is keyed by the runtime owner and survives the early pointer-up capture clear long enough for TextInput, Range, and ScrollbarThumb release reducers to emit `End` metrics, then is explicitly removed by the reducer or release cleanup path.

`component_state.rs` stores retained per-node component interaction flags such as hovered, focused, pressed, dragging, drop-hovered, active drag target, and loading. It is surface-owned rather than TOML-owned: v2 assets describe initial props/state, then runtime input reduces transient interaction state into the heap-resident `UiSurfaceComponentStateStore`. A real transition in those flags marks the owning node render-dirty only; it does not request layout, hit-test, text, input, or visible-range work. Repeated pointer movement over the same target therefore stays idle after the first hover repaint, while hover enter/leave, focus gain/loss, press/release, drag/drop source-target transitions, and semantic loading transitions remain visible to style/render consumers without reloading prototype assets or mutating authored TOML. Tree metadata seeding and accepted runtime property mutations use the same mapper for `hovered`, `focused`, `pressed`, `checked`, `selected`, `popup_open`, `dragging`, `drop_hovered`, `active_drag_target`, and `loading`, so render-facing pseudo-state has one retained source regardless of whether it came from authored metadata, widget behavior, runtime property mutation, or a shared input effect.

`surface/interaction_state.rs` is the shared effective-interaction gate for retained nodes. Pointer press/release events, generic click fallback, and default widget reducers all consult the same inputs before mutating or emitting component events: retained `state_flags.enabled`, runtime component-state `disabled`/`enabled` values and disabled flags, retained `disabled` attributes, and `UiWidgetContract.disabled`. This mirrors Bevy's standard widget pattern where `InteractionDisabled` is checked inside button, checkbox, and slider pointer/keyboard reducers before `Activate` or `ValueChange` is triggered.

`validation.rs` centralizes input-owner checks used by effect application and owner-routed dispatch. A valid owner must exist, be enabled, be render-visible itself, and have an enabled plus render-visible ancestor chain. This keeps text/IME/high-precision ownership aligned with the same visibility semantics used by arranged hit/render paths and prevents disabled containers from leaving focused descendants active.

`effect.rs` consumes `UiDispatchReply` values. It applies ordered `UiDispatchEffect` entries, records applied and rejected effects with their source `effect_index`, validates target nodes before mutating surface state, and marks dirty flags for dirty/redraw requests. Child modules own coherent reply-effect families: `effect/component_event.rs` owns `EmitComponentEvent` target validation, emission policy acceptance, and delivered component-event report projection; `effect/drag_drop.rs` owns `UiDispatchEffect::DragDrop` application plus source/target component-state synchronization; `effect/focus_pointer.rs` owns focus, pointer capture, pointer lock, high-precision pointer ownership, and focus-visible reason mapping; high-precision pointer enablement now uses `has_pointer_capture_or_unindexed_fallback_for_owner` from `state/pointer_capture.rs`, recorded by `runtime_09_m1_2_pointer_capture_fallback_renamed_static_passed_cargo_pending` and guarded by `runtime_09_pointer_capture_fallback_rename_reduces_ui_input_debt`; `effect/navigation.rs` owns `RequestNavigation` route lookup, next-focus resolution, and navigation focus application; `effect/redraw.rs` owns `DirtyRedraw` target validation and structured dirty-domain merge without widening render-only redraws into legacy dirty state; `effect/popup_tooltip.rs` owns popup and tooltip retained-state mutation; `effect/text_services.rs` owns input-method and clipboard request validation/state application; `effect/host_request.rs` owns the pure effect-to-host-request mapping for platform side effects; `effect/target.rs` owns pure applied-target projection for route diagnostics and host-request reasons; and `effect/node.rs` owns the shared missing-node validation used by target-addressed child reducers. Reply processing therefore stays as the root coordinator while each Slate-style state family has a folder-backed reducer instead of growing inside the root file.

`effect/redraw.rs` applies `DirtyRedraw` while preserving the supplied structured dirty domains: render-only redraws do not set the legacy `state_flags.dirty` bit, because that bit still widens to hit-test/input/render in `UiSurface::dirty_flags()`. Text-edit visual metadata mutations for caret, selection, and composition ranges also stay render-only; the edited `value` property is the only text-edit mutation that drives text layout and measurement. Input-method enable requests can establish a valid owner; reset/update/disable requests require the current IME owner and are rejected before host requests when stale. Optional `UiInputMethodSurroundingText` is validated before a host request is emitted so cursor and anchor byte offsets must stay inside the UTF-8 excerpt and on character boundaries. Owner-sensitive effects now carry their owner target in the shared DTO: `ClearFocus { target, .. }`, `ReleasePointerCapture { target, pointer_id, .. }`, and `UnlockPointer { target, .. }`. Runtime application rejects stale targets before clearing focus/IME, capture/high-precision, or pointer-lock state. The drag/drop effect child keeps `Begin`, `Update`, and `Accept` target validation on the same input-owner gate before mutating the active session and reducing source/target visual flags into `UiSurfaceComponentStateStore`; `Reject` keeps the session owner facts but clears drop-hover target flags, while `Complete` and `Cancel` remain cleanup operations keyed by the active pointer/session so a source can be released even after the hover target disappeared. Rejected drag/drop effects do not rewrite component-state flags, matching Slate's separation between a live drag operation and the current valid drop target path. `SetFocus` and navigation clear a previous IME owner only after focus successfully changes, direct capture clears stale pointer ids, and `UseHighPrecisionPointer { enabled: true }` requires live capture for the same owner. After reply effects are applied, both direct replies and merged reply-step routes are annotated with the same route policy and `UiInputRouteTrace` used by `dispatch_input_event(...)`, so Slate-style `FReply`-equivalent paths expose target, preview tunnel, bubble path, focus path, capture target, and popup stack diagnostics instead of only mutating surface state. Direct replies synthesize `route_steps` from the final trace and terminal disposition, while merged reply-step dispatch preserves caller-supplied step traces with each routed phase, target, handler, disposition, effect range, and propagation-stop flag. In merged routes, Zircon deliberately makes effect-carrying continuation explicit: `Unhandled` steps are trace-only and do not contribute effects to the merged reply, `Passthrough` steps may contribute effects while routing continues, and `Handled` or `Blocked` steps contribute their effects and stop propagation. This differs from Slate's permissive `FReply` object shape, but follows the same router intent from `FSlateApplication`: unhandled replies keep routing, while a claimed reply owns the lasting route operations.

`route_policy.rs` owns the stable policy and trace projection used by both unified input dispatch and direct reply application. It chooses bubble, direct, focus-path, pointer-capture, or default-action routing from the normalized `UiInputEvent`, then records target, preview tunnel, bubble path, focus path, capture owner, root fallbacks, and popup stack after reply effects have mutated transient input state. Pointer `Up`, `Move`, and `Cancel` consult the retained per-pointer capture map rather than only the currently active pointer id, so a touch/pen pointer can route to its own captor even when another pointer is active. Direct `FReply`-equivalent pointer `Up`/`Cancel` replies that apply `ReleasePointerCapture` keep a capture-route override from the applied effect, preserving `PointerCapture`, `capture_target`, and the direct captured step after the reducer clears live capture state. Drag/drop follows the Slate `FWidgetPath` shape: `Begin` remains direct to the detected drag source, `Enter`/`Over`/`Leave`/`Drop` trace the current drop target bubble path while retaining the drag source as `capture_target`, and `End` remains a capture cleanup path. `route_steps.rs` converts that trace into phase-level diagnostics when a route did not already provide explicit step traces. It treats an unspecified terminal reply phase as `Target`, still marks the terminal target step when the final disposition is `Unhandled`, and only stops propagation for `Handled` or `Blocked` terminal steps. This keeps preview tunnels observational unless a reply explicitly claims Preview. Direct replies, pointer dispatch, focused keyboard/text/IME routes, captured pointer movement, captured pointer release/cancellation, drag/drop target updates, and default popup/tooltip/accessibility actions all expose comparable Slate-style phase evidence. Text and IME adapters now invoke this shared policy after owner validation, stale IME cleanup, and editable-state mutation, so accepted and rejected focused text routes expose the same focus-path diagnostics before returning to `dispatch.rs`. Unified `UiInputEvent::Popup` close/dismiss events are `DefaultAction` routes only when they still match a retained popup stack entry; stale close/dismiss events are ignored before host requests or state mutation and report `popup.stale`. Unified `UiInputEvent::TooltipTimer` elapsed events are locked as `DefaultAction` routes when they still match the retained tooltip candidate: the explicit or retained tooltip owner becomes the direct route target, the tooltip host request is tied back to the applied effect, and the visible tooltip state is recorded beside the same route-step diagnostics used by popup default actions. Stale delayed tooltip timers that no longer match the retained tooltip id/owner are ignored before host requests or state mutation, preserving the current tooltip candidate while reporting `tooltip.stale`. Popup and tooltip adapters now invoke this shared policy after their retained-state checks, so stale and applied delayed/default-action results carry route traces before returning to `dispatch.rs`. Unified `UiInputEvent::Accessibility` actions are also default-action routes: the request target becomes the direct owner target, the owner bubble path and preview tunnel remain visible for diagnostics, and the synthesized `DefaultAction` step records the accessibility handler/disposition without pretending the action bubbled through pointer routing. The accessibility input adapter now invokes this shared policy after `ui/accessibility/action.rs` validates snapshot targets and resolves the action, so accepted, rejected, unsupported, and stale accessibility results carry route traces before returning to the multiplexer. Drag/drop `End` correction now lives in `drag_drop.rs`: the adapter captures the drag source before `apply_dispatch_reply(...)` clears retained capture, then clears generic direct steps and rebuilds from the source-preserving capture trace so the direct step target stays on the drag source while the route target can still show the last drop target.

`dispatch.rs` is the shared entry point adapter and now stays close to the normalized input-event multiplexer. Pointer, navigation, keyboard, analog, text/IME, drag/drop, popup, tooltip, and accessibility families delegate to child adapters. `navigation.rs` owns the shared navigation adapter used by direct `Navigation` events plus keyboard and analog navigation handoffs: it calls the legacy navigation dispatcher, projects `SetFocus` reply effects, records focused-input diagnostics, annotates navigation route traces, and synthesizes route steps before returning to the multiplexer. Handled navigation replies keep the legacy handler/route target on `UiDispatchReply::handler` and mark `UiDispatchPhase::Target`, so focus-path diagnostics do not misreport ordinary target-handled navigation as a preview-tunnel stop. `accessibility.rs` is the input-side accessibility adapter: it delegates action semantics to `ui/accessibility/action.rs`, then annotates accessibility default-action route policy and route steps before returning to the shared multiplexer. `analog.rs` owns the focused analog adapter: it updates retained analog control state, asks `analog_navigation.rs` for Slate-style threshold/repeat decisions, routes navigation through the shared navigation dispatcher, and falls back to owner-routed analog results with repeat-suppression diagnostics plus route-policy/route-step annotation. `pointer.rs` owns unified pointer orchestration below that multiplexer: it calls the legacy pointer dispatcher, applies pointer dirty requests, updates pointer-id capture state, releases stale capture, projects the routed result into `UiInputDispatchResult`, merges TextInput pointer edits, then annotates pointer route traces and route steps. Runtime 09 M1.2 records `runtime_09_m1_2_pointer_legacy_reply_renamed_static_passed_cargo_pending`: `pointer.rs` and `pointer_reply.rs` now use `routed_result` for the local route result while preserving route order, diagnostics, focus/capture side effects, and returned dispatch data. `runtime_09_pointer_legacy_reply_rename_reduces_ui_input_debt` keeps this local pointer naming from regressing. The adapter also owns pointer-id semantics above the legacy mouse-like dispatcher: when a Move/Up/Cancel event carries a pointer id that differs from the active captured pointer id, dispatch temporarily bypasses the current captor, routes by hit target, and then restores the original captor. This preserves the single-pointer legacy API while giving touch/pen input the per-pointer capture behavior expected from Slate-style `GetOrCreateUser(...)->HasCapture(pointer_index)` routing. Pointer scroll results keep the original shared pointer input event, including optional precise x/y/unit wheel metadata, even while legacy dispatch consumes the scalar fallback. Handler-less pointer replies with no component/effect handler default their synthesized phase to `Target`, so an unhandled hit target remains visible before bubble ancestors continue as passthrough diagnostics. This follows Unreal Slate's `FSlateApplication` pointer ownership split: the application locates the widget path, routes pointer down/up/move/wheel/double-click or touch-derived pointer events, and then processes reply effects, while lower helpers project reply operations and widget-specific text behavior. `keyboard.rs` owns the focused keyboard adapter: it validates the focused owner, records focused-route diagnostics, delegates TextInput mutation to `editable_text.rs`, maps keyboard navigation through the shared navigation dispatcher, applies Escape popup dismissal and Enter/Space default activation, then annotates non-navigation keyboard results with route policy and route steps. Keyboard-synthesized default activation and popup-dismissal replies mark `UiDispatchPhase::Target`, keeping the preview tunnel trace observational while the terminal handled step remains the focused target. Stale disabled or hidden focus therefore reports `owner route rejected` instead of mutating retained widget state. This follows Unreal Slate's `FSlateApplication::ProcessKeyDownEvent` ownership split where the application-level dispatcher gets the focused widget path, routes preview and bubble key handlers, then processes the routed reply, while widget-specific text/editing helpers stay below the dispatcher. `editable_text.rs` owns top-level Text and IME input adaptation as well as focused keyboard text editing: Text input uses a valid IME owner when present, clears stale IME ownership, then falls back to the focused node; IME input clears stale or cancelled IME ownership and reports an `owner route rejected` diagnostic when an invalid stored owner was present. The adapter annotates Text/IME route policy and route steps after owner checks and mutation, while keyboard text edits remain annotated by `keyboard.rs` and pointer selection remains annotated by `pointer.rs`. `editable_text/mutation.rs` owns the shared editable-state application path: runtime property mutations for value/caret/selection/composition metadata, accepted binding-report capture, focused-input logging, and Change/Submit component-event report projection. The helper remains re-exported through `editable_text.rs` so keyboard clipboard and pointer text selection keep using the same mutation route instead of duplicating state projection. `editable_text/state_transition.rs` owns committed text and IME preedit state construction before mutation: it chooses the replacement range from active composition, selection, or caret, applies retained text constraints to the exact replacement, commits composition when needed, and maps IME cursor byte ranges back into caret or selection updates on valid UTF-8 boundaries. `drag_drop.rs` owns the unified drag/drop input adapter: `Begin` can establish a retained session, while `Enter`/`Over`/`Leave`/`Drop`/`End` apply only when the incoming pointer id and optional session id still match the active retained drag state. Stale drag/drop platform events are ignored before reply/effect application so they do not produce rejected effects or mutate source/target component state, and the adapter annotates drag/drop route policy and route steps itself so source-preserving `End` traces stay tied to the family-specific retained state. `popup.rs` owns the unified popup event adapter: `OpenRequested` can create or replace a stack entry, while `CloseRequested` and `Dismissed` apply only when their popup id and explicit owner still match a retained stack entry in `UiSurfaceInputState`; it also annotates popup default-action route policy and route steps before returning to the shared multiplexer. `tooltip_timer.rs` owns the unified tooltip timer adapter: `Armed` replaces the retained tooltip candidate, while delayed `Elapsed` and `Canceled` only apply when their id and explicit owner still match that candidate; it also annotates tooltip default-action route policy and route steps after stale-candidate validation. Other owner-routed families validate that the stored owner still exists, is enabled, and has render-visible ancestors before reporting a handled route.

`text_constraints.rs` is the TextInput-specific constraint parser used by `editable_text.rs` before committed text and IME preedit/commit enter `UiTextEditAction`. It reads retained node attributes, not editor authoring state: `max_graphemes`, `max_chars`, or `max_length` bound the replacement by Unicode grapheme count; `input_filter` or `text_filter` can restrict inserted text to `digits`, `number`, `ascii`, or `alphanumeric`; and explicit `multiline = false` strips CR/LF from inserted or preedit text. The same retained multiline flag gates focused Enter handling: multiline fields insert `"\n"` through the committed-text path, while single-line fields leave Enter unhandled for submit/default behavior. Existing text is not rewritten, so constraints only govern the replacement payload currently entering the runtime-owned field. The constraint function is crate-visible through `surface/mod.rs` so accessibility `SetValue` can sanitize whole-field replacements and `ReplaceSelectedText` can sanitize selected-range replacements with the same runtime rules instead of bypassing TextInput filters, multiline policy, or max length.

M2 focus routing now records focused input through the runtime-owned `UiFocusState::focused_inputs` log. Keyboard, navigation, text, and IME dispatch paths record the focused node, the bubble route from focused node to root, the handler or owner that accepted the focused-input route, and whether the focused route was accepted. Focused keyboard route diagnostics now assert the same focused node and route across `UiInputRouteTrace`, synthesized `UiDispatchReplyStepTrace` phases, and the `focused_inputs` log, keeping the host-observable diagnostics and runtime-owned focus log converged. Focused text/IME route diagnostics now assert the same route evidence while also proving committed text and IME commit mutate the retained TextInput value and emit the expected change/commit component events. Navigation route diagnostics intentionally preserve the old focused route in `UiInputRouteTrace` while recording the new focused node in `focused_inputs` after the default traversal emits `SetFocus`; this keeps route evidence and focus-state mutation evidence distinct. This mirrors Bevy's focused-input bubbling concept while keeping the route serializable in `zircon_runtime_interface::ui::focus::UiFocusedInput`.

Focus mutation lives in `surface/focus.rs` instead of growing `surface.rs` further. Programmatic focus uses `UiFocusChangeReason::Programmatic`; pointer focus uses `Input` and hides focus-visible by default unless a pointer handler explicitly requests a visible focus ring; keyboard/navigation focus uses `Navigation` and `KeyboardNavigation`. Autofocus resolves from `pending_autofocus` or the first authored `UiFocusContract::autofocus` node and records an `Autofocus` focus-change event. Re-focusing the already focused node updates the visible policy but does not append a duplicate focus-change event.

Open overlay focus scopes are no longer limited to hard-coded Material component names. `Dialog`, `ConfirmDialog`, `Modal`, `Popover`, `Menu`, and any node whose resolved `UiWidgetContract::behavior` is `Popup` participate in the same focus scope when `open` or `popup_open` is true. Opening the scope records the previous focus, autofocuses the first focusable descendant unless `disable_auto_focus` / `disableAutoFocus` is set, and tab traversal loops inside that overlay. Programmatic focus requests that target an outside node are redirected back into the open overlay unless `disable_enforce_focus` / `disableEnforceFocus` is set. Closing the overlay removes the restore entry, restores the previous valid focus unless `disable_restore_focus` / `disableRestoreFocus` is set, and clears focus when the closed overlay still owns it. This keeps `.zui` Popup/MenuPopup/Dialog/ConfirmDialog widgets on the same focus-loop contract as MUI modal components while preserving authored opt-out flags.

Focus reconciliation is driven by accepted tree changes only. Runtime property mutation clears focus when an accepted `disabled`, `enabled`, `visible`, `visibility`, or `focusable` mutation makes the focused node invalid, and records `Disabled` or `Hidden` according to the property that invalidated focus. The `disabled` path matters for authored/runtime attribute gates because `disabled = true` is not the inverse `enabled` state flag; it is mirrored into component state and then checked by the shared input-owner validator. Unchanged and rejected mutations do not emit focus changes. Detaching a subtree to the surface node pool clears focus, capture, press, hover, high-precision, IME, pointer-lock, and active drag/drop state for detached owners with `Despawned` focus-change reason.

The focus cleanup path rebuilds the hover-owner list from valid owners instead of retaining with a closure that also borrows the surface for validation. Editable text dispatch captures the focused-input kind before moving the shared input event into `UiInputDispatchResult`, and keyboard focused-input records an accepted focused route whenever a focused owner exists even if the current low-level keyboard reply remains unhandled pending a widget reducer. These are compile-level invariants for the runtime-owned focus/input state and do not change navigation ordering.

M3 navigation behavior consumes the M1 `UiNavigationContract` stored on `UiTreeNode`. `next_navigation_target(...)` applies tab indices, group order, modal group traps, manual directional node/group overrides, blocked edges, and spatial fallback from arranged node centers. Non-modal groups contribute ordering rather than trapping traversal; modal groups filter both tab traversal and manual directional overrides so a dialog cannot escape through an authored neighbor. Existing tree-order helpers remain available for older tests and narrow callers, but surface navigation dispatch uses the contract-aware traversal.

## Widget Behavior Contract

Headless widget behavior is now authored through `UiWidgetContract::behavior` instead of being inferred only from a component name at each runtime call site. `UiWidgetBehavior::Auto` preserves existing templates by mapping known components such as `Button`, `Checkbox`, `Slider`, `TextField`, and `MenuItem` onto behavior families. Popup-like shell components resolve to `Popup`, so accepted `open`/`popup_open` mutations share popup-stack synchronization and modal focus-loop handling. Dialog-like shells join the same popup stack and modal focus scope through the retained overlay shell classifier instead of gaining the generic Popup default toggle behavior. Explicit values such as `Toggle`, `Range`, or `TextInput` override that fallback, and `Passive` prevents a known component name from gaining default behavior accidentally.

Default pointer and focused-keyboard behavior read the resolved widget behavior once and then apply the behavior family. Buttons and menu items emit the same activated commit through click bindings for pointer release and focused `Enter`/`Space`; pointer double-click keeps the existing `double_activated` binding event while still being owned by the button behavior reducer. Menu item popup close is owned by the MenuItem reducer even when the menu item itself has no activation binding, so pointer, keyboard, and accessibility activation all close the nearest open popup through the same popup mutation path. Toggle widgets use `checked_property` with `checked` as the legacy fallback. Disclosure and popup widgets use `open_property` with `expanded` or `popup_open` as the current family default. Range widgets use `value_property`, `min_property`, `max_property`, and `step_property`, so custom TOML components can participate in drag, step, and value-change events without adopting the built-in `Slider` or `RangeField` component names.

Typed widget ownership remains in effect even when a widget is disabled: a disabled button, menu item, toggle, disclosure, popup, or range does not fall through to the generic click fallback. Instead, the typed reducer owns the route and no-ops because the shared interaction gate rejects it. That keeps runtime pointer, focused keyboard, and accessibility disabled semantics aligned with Bevy's `InteractionDisabled` checks in `button.rs`, `checkbox.rs`, and `slider.rs`.

Range navigation now follows the same Bevy slider keyboard contract for incremental and endpoint changes. Focused `Left`/`Down` and `Right`/`Up` navigation step through the authored `step_property`; focused `Home` and `End` navigation mutate the authored `value_property` to the current `min_property` or `max_property`. The endpoint path still goes through `UiSurface::mutate_property`, so render-only dirty behavior and runtime component-state value mirroring stay consistent with pointer drag and accessibility increment/decrement.

The Range default reducer now lives in `surface/default_interactions/range.rs`. The parent `default_interactions.rs` remains the common widget-action dispatcher for Button/MenuItem, Toggle, Disclosure, and Popup behavior, while the child module owns Range pointer drag, numeric alias lookup, clamp/step math, and navigation endpoint mutation. This keeps the Bevy slider-aligned behavior family isolated before adding further standard widgets.

Radio behavior follows the Bevy `RadioGroup`/`RadioButton` split in `dev/bevy/crates/bevy_ui_widgets/src/radio.rs`: a selected radio does not emit another change, a disabled radio or disabled nearest group is rejected by the shared interaction gate, and a radio can expose an app-specific value through `UiWidgetContract::value`. Zircon intentionally applies the group selection through `UiSurface::mutate_property` because retained templates and runtime component state are the current data-binding layer. `surface/default_interactions/radio.rs` sets the target radio checked, clears checked sibling radios in the nearest `RadioGroup`, and mutates the group's `value_property` to the selected radio's `widget.value` or stable node identity fallback. Godot's `ButtonGroup` documentation corroborates the mutual-exclusion expectation, while Slint's Material `RadioButton` documentation confirms the author-facing `checked`/`enabled` surface.

Scrollbar behavior follows Bevy `dev/bevy/crates/bevy_ui_widgets/src/scrollbar.rs`: scrollbar track and thumb are headless controls for a scrollable container, not slider-like value widgets. `UiWidgetBehavior::Scrollbar` carries `scroll_target`, optional `scroll_axis`, and `min_thumb_extent`; `ScrollbarThumb` is a passive child marker. The runtime reducer in `surface/default_interactions/scrollbar.rs` resolves a target node by `#node_id`, `control_id`, or node path, then a primary track click pages the target `ScrollableBox` by its viewport extent through `UiRuntimeTreeScrollExt::set_scroll_offset`. Thumb press captures the pointer, starts runtime pointer-drag metrics, and emits `BeginDrag`; captured move updates the target scroll offset and emits `DragDelta` with `UiDragPhase::Update`, start/current points, axis delta, and distance; release emits `EndDrag` with `UiDragPhase::End` before clearing the drag state. A thumb click still does not page the scroll container because paging belongs to the track, not the thumb.

MenuItem activation now owns the first headless menu close behavior. Bevy `dev/bevy/crates/bevy_ui_widgets/src/menu.rs` activates menu items and then sends menu close/focus-root events for the popup stack; the same file also treats Escape as a popup close request. Zircon does not yet have a full neutral menu-stack contract, so `default_interactions.rs` applies the conservative retained equivalent: after a `MenuItem` pointer click or focused Enter/Space activation, or after Escape is pressed while focus is inside a popup, the nearest `Popup` ancestor with an open `open_property` is mutated to `false` only when it passes the ancestor-aware widget interaction gate, and matching popup bindings receive `ClosePopup`. The close path no longer depends on the MenuItem itself having an activation binding; that keeps menu closing in the same runtime behavior path for pointer, keyboard, and accessibility activation without inventing editor-owned popup state.

The keyboard path handles the same default activation keys used by Bevy's headless widgets: `Enter` and `Space` on the focused control. Buttons and menu items emit an activated commit through click bindings; toggles, disclosures, and popups mutate the same properties used by pointer activation. Popup keyboard activation synchronizes the shared popup stack through the same accepted `open`/`popup_open` mutation path used by pointer activation and tree metadata seeding, but the widget does not need to become a self-hit-test target just to receive an already-focused keyboard route. Repeated keyboard events do not trigger this default activation path.

Focused TextInput keyboard editing now uses the same retained editable text state as text and IME input. `surface/input/text_keyboard/edit_actions.rs` maps Bevy-style focused edit keys from local `dev/bevy/crates/bevy_ui_widgets/src/editable_text.rs` into `UiTextEditAction`: Backspace, Delete, Escape collapse/cancel, ArrowLeft/ArrowRight, ArrowUp/ArrowDown, Home, End, and select-all. `surface/input/text_keyboard/payload.rs` owns plain Enter newline detection and printable `UiKeyboardInputEvent.text` payload filtering. `surface/input/text_keyboard/clipboard.rs` owns the explicit clipboard command classifier for Ctrl/Super+C/X/V, dedicated Copy/Cut/Paste logical keys, and Shift+Delete cut; the structural root re-exports those focused TextInput keyboard entry points so `editable_text.rs` and `keyboard_clipboard.rs` can keep their dispatch ownership. Arrow/Home/End actions read `UiInputEventMetadata.modifiers.shift` so Shift+movement extends the retained `selection_anchor`/`selection_focus`, while plain movement clears the selection and only moves `caret_offset`. Home and End now use shared line-boundary helpers for multiline text: plain Home/End moves to the current line start/end, while Ctrl/Super+Home/End moves to the document start/end; CRLF line endings are treated as one separator and End stops before the carriage return. Bevy also exposes hard-line shortcuts through Super+ArrowLeft/Right and Alt+Home/End; Zircon maps those to the same current hard-line start/end helpers until visual-line shaping geometry exists. Plain ArrowUp/ArrowDown use shared grapheme-column line helpers, so vertical movement targets the same logical grapheme column, clamps to shorter lines, treats CRLF as one line break, and stays on valid UTF-8 boundaries until the later shaping backend can supply visual caret x positions. Up on the first line collapses to document start and Down on the last line collapses to document end. Ctrl/Super+ArrowUp/ArrowDown follows Bevy's `TextStart`/`TextEnd` mapping and moves to the document start/end through the same retained selection path. ArrowLeft/ArrowRight also read `UiInputEventMetadata.modifiers.control` for word navigation: Ctrl+Left moves to a word start and Ctrl+Right moves to a word end, with Ctrl+Shift extending selection through the same retained selection properties. Ctrl+Backspace and Ctrl+Delete use the same word-boundary helper to select the previous or next word range and then reuse the existing Backspace/Delete selection-removal path, so word deletion reports the same value/caret/selection mutations as normal deletion. Ctrl+A and Super+A map to the existing `SetSelection` action and select the full retained text without emitting a value-change component event. Escape follows Bevy's `CollapseSelection` intent when no composition is active: it clears the retained selection by moving the caret to the current focus without changing value. If composition metadata is active, Escape keeps Zircon's IME safety behavior and cancels composition first, restoring the saved text through `CancelComposition`. Read-only TextInput still permits caret movement, selection updates, Escape collapse, and Copy, but blocks content mutation, composition writes, Cut, and Paste. Disabled or hidden focused owners are rejected before this edit path, so stale focus cannot use keyboard text payloads, editing keys, Escape collapse, popup dismissal, or default activation to mutate retained state. A plain focused Enter matches Bevy's `allow_newlines` branch: when retained `multiline` allows it, Enter inserts `"\n"` through the same committed-text path used by `UiInputEvent::Text`; when `multiline = false`, Enter is not consumed by text editing and can propagate to submit/default behavior. Printable `UiKeyboardInputEvent.text` payloads with no Control/Alt/Super modifier now also use that committed-text path, so hosts that combine key and text data do not need a second `UiInputEvent::Text`; Tab and newline payloads remain unhandled for navigation and submit/default behavior. All clipboard commands emit `UiDispatchEffect::RequestClipboard` with a typed `UiDispatchHostRequestKind::Clipboard`; Copy and Paste do not invent runtime clipboard state or binding reports, while Cut removes the active selection through the same value/caret/selection mutation route before requesting the host clipboard write. ## Surface Integration

`UiSurface` now stores `input: UiSurfaceInputState` with serde defaults so old retained surface snapshots can deserialize without input-state fields. Public methods `UiSurface::apply_dispatch_reply(...)` and `UiSurface::dispatch_input_event(...)` keep the shared runtime seam explicit while the implementation remains in the child module.

Pointer capture release paths clear the matching per-pointer capture in addition to updating the active pointer id and `UiFocusState::captured`. When the released owner also owns high precision, `clear_pointer_capture_for(owner)` clears both states; otherwise high precision is left alone so a stale release cannot clear another owner's raw-input state. Captured pointer `Up` and `Cancel` now follow the same retained-surface termination contract as Slate-style pointer capture release: they route to the current pointer's captor, clear capture, high precision, owner drag metrics, focused pressed ownership, and retained pressed state as applicable, and project a `ReleasePointerCapture { reason: Cancel }` effect into the unified input result while preserving capture-route diagnostics after cleanup. Direct reply application uses the applied release effect as the pre-cleanup capture snapshot, so external pointer replies retain the captured route even after state mutation.

Pointer dispatch dirty requests are now first-class retained-surface input invalidation. `UiSurface::apply_pointer_dispatch_dirty(...)` maps each `UiPointerDispatchEffect::RequestDirty(...)` invocation back to the invoking node and preserves the supplied `UiDirtyFlags` without widening render-only requests through the legacy `state_flags.dirty` bit. `RuntimeUiManager` consumes that method after pointer dispatch and only calls `rebuild_dirty(root_size)` when the surface actually has dirty domains. Pointer-derived component state follows the same narrow domain: `apply_pointer_component_state(...)`, `set_node_pressed_dirty(...)`, and `surface/focus.rs` mark render dirty only when the retained hover/focus/press state actually changes. This means runtime v2 fixtures can redraw a pressed/hovered/focused visual through the render domain, or run incremental layout for real geometry changes, without reloading v2 TOML or rebuilding the entire surface tree.

Pointer primary press/release now also reduces the retained pressed state into `UiTreeNode::state_flags.pressed`. The update is intentionally render-only: it changes the accessibility/render-facing state, adds a render dirty flag to the affected node, and does not set the legacy `state_flags.dirty` bit. A second primary press on another target clears the previous pressed node and marks both nodes render-dirty, matching retained widget behavior without forcing layout or hit-grid rebuilds.

Runtime property mutation synchronizes accepted tree property changes into `UiSurfaceComponentStateStore`, including generic typed values and canonical boolean flags such as disabled, pressed, checked, expanded, popup-open, and selected. Unchanged or rejected mutations do not initialize or rewrite component state and do not mark render dirty. This preserves the public `UiPropertyMutationStatus::Unchanged` contract while still letting real accepted mutations feed runtime pseudo-state styling and accessibility state extraction through the component-state path.

Pointer hover, focus, and press also reduce into `UiSurfaceComponentStateStore`. Hover/focus state is retained for component/style consumers but does not yet widen dirty domains by itself; press still marks render dirty through the tree state path because current render and accessibility extraction already read `state_flags.pressed`. Detaching a subtree to the retained node pool clears component states for those nodes before reuse, so recycled controls cannot inherit stale hover/focus/press flags.

Focused input owner validation now rejects disabled ancestors through the shared `ui_surface_node_disabled(...)` helper used by widget interaction and accessibility extraction: `state_flags.enabled`, component-state `disabled`/inverse `enabled`, canonical runtime disabled flags, `UiWidgetContract.disabled`, and retained `disabled = true`. Accepted `disabled = true` runtime property mutations now immediately run the same reconcile path as `enabled = false`, so stale focus, capture, high-precision pointer, IME, pointer-lock, pressed, hover, and active drag/drop owners are cleared before a later input event can observe them. That means a node under a disabled popup cannot regain keyboard, IME, pointer-capture, drag/drop, or popup-close ownership merely because the child itself is enabled. Escape and outside-click popup dismissal consume the same ancestor-aware widget gate, so disabled popup owners are not closed by stale focus or pointer paths.

The 2026-05-27 M5 runtime gate also filters pointer-derived focus acquisition through the same input-owner gate. Pointer hit testing may still identify a disabled node so diagnostics and suppression remain precise, but `UiSurface` no longer tries to move focus to that disabled route target. Disabled Button and TextInput hits therefore suppress pointer/keyboard mutation without producing a stale focus owner or a `MissingNode` focus error.

Popup and tooltip input/effect DTOs now carry an optional `owner: UiNodeId`. Runtime dispatch copies that owner from `UiPopupInputEvent` and `UiTooltipTimerInputEvent` into the corresponding `UiDispatchEffect`, and `apply_dispatch_reply(...)` validates the owner with the same input-owner gate before mutating `popup_stack` or tooltip state or before emitting host requests. A missing owner remains the legacy host-only path for old serialized events and tests; an explicit stale, hidden, or disabled owner rejects the effect and leaves shared popup/tooltip state unchanged. Delayed tooltip timer events also validate against the retained tooltip candidate before effect application, so a late `Elapsed` from a previous hover cannot overwrite the tooltip currently armed for another owner.

Default Popup widget behavior now feeds the same shared popup stack used by explicit `UiDispatchEffect::Popup` replies. `UiSurface` seeds open Popup widgets from tree metadata/rebuild state by node path, then accepted `open`/`popup_open` property mutations for Popup widgets update or remove that stack entry. This keeps Escape dismissal, outside-click dismissal, keyboard popup toggles, and route diagnostics aligned with the Slate-style menu stack while preserving the host-only path for explicit popup effects with arbitrary ids.

Keyboard default activation now has focused unified route evidence for Button-style widgets.
