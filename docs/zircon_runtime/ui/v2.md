# UI v2 Foundation

UI v2 moves authored UI assets away from recursive runtime `UiTemplateNode` documents and into flat arena data. The stable DTOs live in `zircon_runtime_interface::ui::v2`; runtime loading, heap prototype storage, arena compilation, style resolution, and surface construction live in `zircon_runtime::ui::v2`.

## Runtime Contract

`UiV2AssetDocument` has four top-level asset kinds: `view`, `component`, `style`, and `theme_tokens`. Nodes are stored in a flat `nodes` table and use fixed fields: `component`, `classes`, `props`, `state`, `layout`, `slots`, `events`, and `children`. V2 style declarations are owned by `UiV2StyleSheet`, `UiV2StyleRule`, and `UiV2StyleDeclarationBlock` instead of reusing the legacy template asset style DTOs, while bindings and import lists still reuse existing shared UI contract types.

`theme_tokens` is style-like for editor/runtime routing. It remains a distinct v2 asset kind for serialization and governance, but legacy bridge points that need a `UiAssetKind` classify it as `Style`: runtime UI asset parsing accepts theme-token documents where style assets are expected, UI Asset Editor host sessions route them through the style editor path, and the v2 authoring preview treats them as non-visual style sources rather than attempting to build a view preview.

The UI v2 document importer boundary now reserves `.zui` as the production suffix while still decoding TOML into the existing `UiV2AssetDocument` DTO. `UiZuiAssetLoader::load_zui_str` and `load_zui_file` first parse through the v2 TOML loader, then enforce the `.zui` profile by `asset.kind`: component documents keep the strict component profile (`kind = "component"`, no top-level `[root]`, exactly one component, non-empty component root, and a root that resolves into `nodes`), while view/style documents may use the root/document profile needed by UI roots and style assets. Production `AssetImporter::default()` routes `.zui` through `import_ui_zui_asset`, then the shared v2 document importer materializes `UiV2ComponentAsset`, `UiV2ViewAsset`, or `UiV2StyleAsset` / `ResourceKind::UiWidget`, `UiLayout`, or `UiStyle`. `.v2.ui.toml` and `.ui.toml` importers are rejected outside explicit migration fixtures. The split `ui_document_importer` plugin mirrors that production path with `ui_document_importer.zui_document`, `full_suffixes = [".zui"]`, and component/view/style output kinds.

Editor extension registration enforces the same boundary for authoring descriptors: `EditorUiTemplateDescriptor` and `ComponentDrawerDescriptor` UI document paths must point to `.zui`. This catches stale plugin registrations before workbench projection tries to load a missing prototype and keeps component drawer metadata on the v2-backed cache/surface path.

Runtime plugin UI component descriptors now enforce the same document boundary. `RuntimeExtensionRegistry::register_ui_component(...)` still validates the plugin-owned component id prefix, then rejects any `ui_document` that does not end in `.zui`. The runtime registry projection keeps the `plugin-ui-component` descriptor role and `ui_document` prop, but stale recursive `.ui.toml` and broad `.v2.ui.toml` documents cannot enter the runtime component catalog through plugin manifests.

The v2 payloads intentionally keep the existing resource categories for now: v2 `view` maps to `ResourceKind::UiLayout`, `component` maps to `ResourceKind::UiWidget`, and `style` maps to `ResourceKind::UiStyle`. New `.zui` project scans select the matching branch from `asset.kind`, so component prototypes keep the v2 document payload while view/style roots can migrate off `.v2.ui.toml` without reopening a second production importer.

`UiV2DocumentCompiler` validates missing references, empty components, multiple parents, and cycles with an explicit stack before building `UiV2NodeArena`. The compiled artifact is now the interface-owned `UiV2CompiledDocument`, which carries the arena, source-id handle map, and `UiV2ComponentGraph`. The graph records each arena node's stable handle, source id, component name, parent handle, and child handles so editor/runtime consumers can inspect the component graph without depending on a runtime-local compiled type.

`UiV2SurfaceBuilder` consumes the arena directly through `ui::v2::surface_tree` and inserts one flat arena node at a time into the retained runtime tree. The folder-backed `surface_tree` owner splits node insertion, layout parsing, slot projection, interaction inference, and shared parsing helpers so the v2 runtime surface path can evolve without growing the root builder. It does not build a recursive `UiTemplateNode` tree and no longer routes through the legacy `UiTemplateTreeBuilder` or `UiTemplateSurfaceBuilder` path. Node paths are stable flat source paths (`v2/<source_id>`) so very deep UI documents do not allocate path strings proportional to depth squared. The `ui_v2_surface_projection_does_not_call_template_tree_builder` guard scans the v2 surface projection sources and fails if that main path regains old template-builder dependencies.

`surface_tree::interaction` now derives default input capabilities from the formal `UiComponentDescriptorRegistry::editor_showcase()` catalog. Authored `input_*` metadata remains the override path, authored bindings still mark event-specific nodes as interactive, and catalog descriptors fill the default for components that do not repeat those flags in every v2 asset. Runtime input, numeric, selection, reference, and collection components receive click/hover/focus defaults; container and feedback components become interactive only when their descriptor events imply interaction, so `MessageBox`, `Popup`, and `Foldout` can receive input while passive `ProgressBar` stays non-interactive.

`UiV2ComponentInstancer` expands local and imported composite components through an explicit stack. It validates source graph cycles before expansion so a cyclic flat graph fails fast instead of spinning before compiler validation. Component slot fills are grouped by authored `slot.name` / `slot_name`, then checked against `UiV2ComponentDefinition.slots`: required slots must be present, unknown slots are rejected once a component declares slot schema, and non-`multiple` slots reject multiple fills. Components with no declared slot schema continue to accept the default slot as the simple no-schema path.

The instancer treats source children as traversal input, not as output children. Every output node starts with an empty child list and receives children only when the arena instancing pass mounts a child into the output parent. This avoids duplicating child edges when a flat authored view is compiled and prevents the component graph from growing into an invalid or runaway tree. Original v2 node IDs are preserved for non-expanded source nodes so style resolution and diagnostics keep stable source IDs; generated `v2n*` IDs are used only for component-expanded nodes.

Declared default slots now forward ordinary un-slotted instance children. A component can declare `slots = { default = { multiple = true } }`, place a `Slot` placeholder with `props = { name = "default" }` inside its root subtree, and receive every child mount whose `slot` table omits a name. This is the path used by Workbench `WorkbenchTabStrip`: the reusable tab strip owns the outer `Tabs` node while each shell instance supplies concrete `WorkbenchTab` children. The guard `ui_v2_composite_component_forwards_default_slot_children` verifies that `RuntimeTabA` and `RuntimeTabB` become direct children of the expanded runtime tab strip instead of being collected and dropped.

Instance-level root style patches also apply after imported component expansion. Authored instance style such as `style = { self = { foreground_color = "#ef493f", text_tone = "error" } }` is preserved as final root `style_overrides` even when an imported component root and a stylesheet rule already provide default values. The guard `ui_v2_imported_component_instance_style_patches_expanded_root` locks the precedence used by Workbench viewport gizmo labels: component defaults and stylesheet aliases can supply neutral colors, while the viewport instance can still mark X/Y/Z labels with semantic foreground colors.

UI Asset Editor v2 component authoring uses a layout-document projection only as the editing adapter. Selected-node props/state literal patching is exposed through the session API and then serialized back through the schema-aware v2 save path, so v2 component assets keep `kind = "component"` plus flat `[nodes.*].props/state` instead of downgrading to recursive widget TOML. The same values are flattened as `prop` and `state` rows into both the inspector summary stream and the dedicated retained-host `UiAssetInspectorWidgetData.prop_state_rows` model, where each row carries `kind`, `path`, `value`, and `display`. Retained conversion now has a dedicated `ui_asset_detail_fields/` owner tree that turns Widget, Slot, Layout, and Binding inspector data into dynamic `InputField` nodes. It emits basic widget fields, generic props/state rows, slot mount/padding/layout fields, layout semantic/container fields, and binding id/event/route fields, then grows each inspector section frame before shifting later sections. These generated fields use `dispatch_kind = "commit_only"`: text input mutates the native focus buffer and repaints only the input damage region, while Enter/commit dispatches `ui_asset_detail|<instance>|<detail>|<action>|<index>` through the pane surface dispatcher. Draft edit ids stay under `ui_asset_detail_draft|...`, so keypresses do not trigger UI asset document patches or full presentation rebuilds. The `asset_editor` component adapter accepts the resulting `widget.prop.<path>` / `widget.state.<path>` commit targets, so retained/v2 controls can display and author generic component parameters without parsing generic inspector text or adding one hard-coded editor action per key.

## Style Resolver

`UiV2StyleResolver` compiles v2 style rules into ordered selector rules and applies them by specificity plus declaration order. It supports component selectors, `.class`, `#control_id`, and pseudo states such as `:hover`, `:pressed`, `:focused`, `:disabled`, `:checked`, and `:selected`. Pseudo states are derived from true values in `props` and `state`; `hovered` also aliases to `hover`.

The static resolver intentionally leaves authored inline `style.self` out of the selector cascade. Static non-pseudo rules populate `UiTemplateNodeMetadata.attributes`; authored inline style and final override values populate `UiTemplateNodeMetadata.style_overrides`. Runtime render extraction reads `style_overrides` first and falls back to `attributes`, preserving the highest-priority inline authored value without letting it become a stale pseudo-state baseline. The guard `ui_v2_inline_style_overrides_cascade_values_in_style_overrides` freezes this split with a Button whose selector cascade resolves `button_variant = "contained"` while inline style keeps `button_variant = "outlined"` in `style_overrides`.

Typed style consumers sit on top of the same v2 value maps. `zircon_runtime::ui::style` defines the generic `StyleProperty` / `StyleField<P>` resolver and weak `StyleSheetScope` list used by `ButtonStyleFields`; `resolve_button_style_from_values(...)` is the narrow bridge from runtime/editor TOML value maps to shared `ResolvedButtonStyle`. The first shipped consumer is Material Button/IconButton styling: enum fields such as `button_variant`, `button_color`, `button_size`, `icon_placement`, and `button_interaction_state` are parsed into `zircon_runtime_interface::ui::style` enums instead of being passed through as host-local strings. When no explicit interaction-state string is authored, the bool fallback resolves loading/disabled first, then pressed before focused, then hovered. This keeps runtime Material buttons aligned with the retained painter's state-layer priority so a pointer-down control that also has keyboard focus keeps the stronger pressed visual feedback. This layer is deliberately separate from the v2 selector engine so future typed style properties can reuse the same cascade/override mechanics without changing the `.ui.toml` schema.

Token values can be referenced as `$token.name` or `var(token.name)` and are resolved from the document token map before styles are projected into runtime metadata. Resolution walks nested arrays and tables, so Material declarations such as `background = { color = "$material_surface" }` and pseudo-state table declarations are normalized before render extraction reads them.

Theme token resolution is now available as an explicit v2 parsing/building mode. `UiV2StyleResolver::resolve_with_theme(...)` and `UiV2SurfaceBuilder::build_surface_from_compiled_document_with_theme(...)` accept a `UiThemeRegistry` and resolve theme role strings such as `$theme.palette.accent`, `theme.palette.surface.1`, or `var(theme.palette.text.primary)` into concrete color values before the retained tree and runtime pseudo-state index capture their baselines. The default resolver and builder entry points intentionally keep the old document-token-only behavior so existing assets are not silently rebound to the active editor theme.

Resolved v2 style now carries token provenance beside resolved values. `UiV2ResolvedStyle::style_tokens` stores a stable property-path to source map such as `background = theme.palette.accent`, `foreground = token.editor.text -> theme.palette.text.primary`, or nested paths such as `background.color`. The surface tree builder copies this map into `UiTemplateNodeMetadata.style_tokens`, and the runtime pseudo-state style index captures the same map in its per-node baseline. When a runtime rule overlays `background`, the metadata source changes from the static rule's token to the active pseudo-state token; when a property mutation replaces an authored style value, the old token source for that property is removed from the baseline. This keeps final retained UI colors and sizes traceable back to authored document tokens or normalized theme roles without changing the concrete values consumed by render extraction.

Retained-host v2 assets must author the same runtime projection metadata on the hot path instead of relying on editor-only expansion. `inspector_surface_controls.zui` now projects an `InspectorSurfaceControls` root with direct retained control children, keeps field labels as metadata, authors explicit `placeholder` / `value` / `value_text` on input fields, authors `layout_min_height` and `input_*` flags on interactive roots, and uses direct `NumberField` / `Button` nodes for the inspector transform and action controls. `RetainedUiHostAdapter` projects visible text from non-empty `text`, then falls back to `label` only when the node does not also carry field/value metadata such as `placeholder`, `value`, `value_text`, `options`, `items`, or `entries`; this preserves action labels while preventing input labels from becoming typed text.

## Taffy Bridge

`zircon_runtime::ui::layout::taffy_bridge` imports Taffy into runtime and converts the Taffy-owned subset of Zircon layout contracts into `taffy::style::Style`. Flex, Grid, Wrap, and Size-style layout roles are routed toward Taffy. Overlay, Canvas, Popup, VirtualList, and editor docking remain Zircon-owned. Runtime 09 M2.1 records this as `runtime_09_m2_1_taffy_bridge_pass_order_static_passed_cargo_pending`: `taffy_bridge/compute.rs` owns `compute_taffy_child_frames(...)`, Taffy tree construction, rounding policy, and `compute_layout`; `layout/pass/taffy_arrange.rs` only performs eligibility/fallback/reporting and delegates computation to the bridge.

`layout/pass/pipeline.rs` exposes `UI_LAYOUT_PASS_ORDER`: responsive style resolution, measurement, backend selection, Taffy bridge arrangement, Zircon fallback arrangement, clip and virtual-window propagation, and selection report. Full layout and incremental layout consume that same order. `runtime_09_m2_1_style_mapping_remains_taffy_dto_adapter` keeps `layout/style_mapping.rs` as the Taffy DTO adapter; it is not a backend executor.

`layout/pass/taffy_arrange.rs` is called from the global arrange pass for safe Flex, Wrap, and Grid subtrees. The current integration stage allows v2-authored nodes with template metadata to use Taffy because metadata is render/event data, not a layout placement contract. Authored slot frame policies, canvas/grid placement overrides, or non-default anchor/pivot/position still fall back to Zircon arrangement so absolute placement, Overlay, Canvas, Popup, VirtualList, and editor docking semantics remain Zircon-owned. The guard tests prove Overlay and Scrollable/VirtualList semantics stay outside the Taffy path, while `taffy_layout_pass_accepts_template_metadata_from_v2_assets` covers the v2 template cutover.
