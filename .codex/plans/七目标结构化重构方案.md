# 七目标结构化重构方案

## Summary

- 本方案按 7 个目标收敛，不把仓库再次拉回“大文件拆一点点”的局部修补，而是直接改成可持续扩张的目录树和职责边界。
- 总体策略固定为：先拆低层编译与运行时支撑，再拆 editor 业务链路，最后收敛顶层 `entry` 与 `script` 组合边界。不要先动 `zircon_entry`，否则只会把下层不稳定接口再硬编码一遍。
- 跨目标硬约束：
  - `zircon_manager` 只保留 manager 调度、resolver、handle、稳定命名和公共契约，不再容纳任何具体功能 manager 实现。
  - `mod.rs`、`lib.rs`、`entry_runner.rs` 一类根文件只做结构接线，不再承载真实业务实现。
  - `IManager/IDriver/IPlugin` 的概念边界继续遵守当前收敛方案：具体能力留在 owning crate，公共语义留在 `zircon_module`/`zircon_manager`/`zircon_entry`。

- `compile.rs` 只负责管线编排，不再内嵌节点展开、组件实例化、样式解析和值归一化。

- `UiDocumentCompiler` 保留为外部入口类型，但只做 façade，不再成为“整条编译管线的实现文件”。

## 接口与边界约束

- `UiDocumentCompiler`、`UiAssetEditorSession`、`DefaultEditorAssetManager`、`ScriptModule`、`EngineEntry` 这些现有主入口类型继续存在，但降格为 façade 或 owner，不再承担全实现。
- `zircon_manager` 的公开职责固定为 manager contracts、resolver、scheduler、stable names、handle/facade；所有具体业务 manager 一律回到 owning crate。
- `zircon_script` 在本轮后应当是“目录与角色已收敛，但 plugin 生命周期仍显式未完成”的状态；不要在这轮同时引入伪完整 plugin API。
- `zircon_entry` 在本轮后应当是“入口契约和模块集合装配隔离清楚”的状态；不要把去静态依赖和运行模式拆分混成一次大手术。

## 建议落地顺序

1. 先拆 `zircon_ui/src/template/asset/compiler.rs`，把模板编译管线切成稳定下游依赖面。
2. 再拆 `zircon_editor/src/host/template_runtime`，先把 runtime 逻辑和 builtin 模板注册数据分家。
3. 接着拆 `zircon_asset/src/editor/manager.rs`，把 project sync、preview refresh、folder projection、reference analysis 变成独立能力面。
4. 然后拆 `zircon_editor/src/editing/ui_asset`，让 session、preview、style、tree、source 各自回到独立子树。
5. 再把 `zircon_editor/src/host/manager/ui_asset_sessions.rs` 变成目录树，此时它只编排稳定的下游接口，不再自己吸收实现细节。
6. 然后收敛 `zircon_script/src/vm`，先把 backend、host、plugin、runtime、module 分域，为后续真实 plugin 生命周期接线腾出空间。
7. 最后处理 `zircon_entry/src/entry`，把 profile module set 和 run mode dispatch 固定下来，避免 entry 继续充当“全模块静态组合器”。

## Test Plan

- `zircon_ui`：
  - 模板编译、节点展开、组件实例化、样式应用、值归一化、结构校验的现有行为保持一致。
- `zircon_editor/host/template_runtime`：
  - builtin template documents、bindings、component descriptors 能被稳定加载；runtime projection 不依赖 builtin 数据文件布局。
- `zircon_asset`：
  - `sync_from_project`、preview dirty/refresh、folder tree projection、direct references 提取都有独立单测或回归测试入口。
- `zircon_editor/editing/ui_asset`：
  - session 打开、编辑、preview compile、style inspector、hierarchy projection、palette drop 各自有独立测试面，不再只能靠 session 全量集成测试覆盖。
- `zircon_editor/host/manager/ui_asset_sessions`：
  - open/save/session lifecycle/import hydration/sync 各自可验证，且 manager 层不再直接实现 import 递归细节。
- `zircon_script`：
  - unavailable/mock backend、manifest/package/instance/state blob、hot reload coordinator 都能独立测试；测试结果必须明确标识 plugin runtime 仍未完全接入 core plugin lifecycle。
- `zircon_entry`：
  - editor/runtime/headless 三条路径都能映射到明确 `EngineEntry` 责任边界；module set 组装测试与 run mode dispatch 测试分离。
- 全局验收：
  - 不再存在新的根文件继续膨胀为实现大文件。
  - `zircon_manager` 不再承载任何具体功能 manager。
  - 7 个目标的根层路径一眼可看出子域，不需要打开文件才能知道职责。

## Assumptions

- 本方案的“7 个目标”固定为：
  - `zircon_editor/editing/ui_asset`
  - `zircon_editor/host/manager/ui_asset_sessions`
  - `zircon_entry`
  - `zircon_script`
  - `zircon_editor/host/template_runtime`
  - `zircon_asset/src/editor/manager.rs`
  - `zircon_ui/src/template/asset/compiler.rs`
- `zircon_scene/src/components.rs` 不纳入本轮，作为下一阶段 backlog；等 editor/runtime/interface 收敛后再处理 world/ECS 声明仓库问题。
- `zircon_render_server` 与路线图中的 `zircon_server` 命名收敛不在这 7 目标内，本轮只为后续收敛清出边界。
- 本轮目标是目录树和职责收敛，不同时追求功能升级、生命周期全贯通、或全面去除 `zircon_entry` 的静态依赖。
