# 全对象接口家族与结构化审计技能方案

## Summary

- 本轮采用“全对象体系”方案，但只把真正需要跨层统一的部分做成代码级抽象；`IEntry/IModule/IService/IDriver/IManager/IPlugin` 形成主接口家族，`IObject/ISystem/IEntity/IComponent` 形成运行时语义家族。
- skill 做成仓库内技能，路径固定为 `.codex/skills/zircon-project-skills/zr-runtime-interface-convergence/`，直接绑定 `基本路线图.md` 和 `.codex/plans/全系统重构方案.md`。
- 当前项目是“部分结构化、未完成收敛”，不是推倒重来。`zircon_core` 的 descriptor 主干可保留，必须补的是统一接口词汇、模块拥有者抽象、入口收敛、插件边界、以及编辑器热点模块拆分。
- 结论是“需要重构”，但应做收敛式重构，不做无差别全仓重写。

## Key Changes

### 1. 接口家族定义

- 概念层统一使用 `I*` 命名，代码层统一使用 Rust 风格命名。
- `IEntry -> EngineEntry`：负责 profile 选择、内建模块集合、bootstrap 和 host run mode；不直接拥有具体子系统对象。
- `IModule -> EngineModule`：作为模块拥有者抽象，负责产出模块描述符；现有 `EngineModule` 直接升级为权威接口，不再只是备用 trait。
- `IService`：定义 Core 管理对象的共性语义，包含注册名、所属模块、生命周期、启动模式、依赖声明来源。
- `IDriver`：低层能力角色，只允许依赖 Driver，不允许反向依赖 Manager 语义。
- `IManager`：高层能力角色，依赖通过声明式依赖和 resolver/facade 取得，不持有跨生命周期强耦合对象。
- `IPlugin`：保留在同一家族中，但只作为 VM/plugin 路线的专用角色，不与普通 Module/Manager 混同。
- `IObject/ISystem/IEntity/IComponent` 只定义运行时语义边界，不强行全部 trait 化。
- `IEntity/IComponent` 明确按 ECS 语义处理：`Entity` 是身份与层级入口，`Component` 是数据单元，不设计成全局 OO 基类。
- `ISystem` 定义为调度单元或 manager-owned runtime system，不回退成旧式 scene-node 对象模型。

### 2. 代码收敛方向

- 保留 `zircon_core` 的 `ModuleDescriptor/DriverDescriptor/ManagerDescriptor/PluginDescriptor` 作为注册元数据层，不先推翻 descriptor 模式。
- 把各 crate 目前散落的 `module_descriptor()` 自由函数收敛为真实模块拥有者类型，实现 `EngineModule`；自由函数仅作为过渡适配层。
- 把 `zircon_entry` 的 editor/runtime/headless 运行路径收敛为 `EngineEntry` 实现，而不是继续靠薄 `EntryRunner` + 静态分支拼接。
- 不在第一步强行统一 `zircon_manager` 与 `zircon_render_server` 的命名，但把它与路线图中的 `zircon_server` 偏差列为独立收敛任务。
- 维持 `zircon_script` 的 VM/plugin 方向，但把它标记为“框架未贯通”，在 Core 的 plugin 生命周期真正成型前，不扩散 `IPlugin` 到其他层。
- 编辑器先做热点拆分，优先处理 `editing/ui_asset/session`、`host/manager/ui_asset_sessions` 一类边界过重区域；`zircon_core` 这类已较聚焦的 crate 不做无关拆分。
- 继续允许 skeleton module 存在，但 skill 和审计结果必须把它们明确标注为 `skeleton`，防止误判为已完成架构。

## Public Interfaces

- `EngineEntry`：定义 profile、模块集合、bootstrap、run mode 的统一入口契约，归属 `zircon_entry`。
- `EngineModule`：定义模块拥有者契约，归属 `zircon_module`，每个真实模块 crate 都应导出一个模块类型实现它。
- `IService/IDriver/IManager/IPlugin`：作为架构契约写入 skill 和参考文档，代码侧继续通过 descriptor + capability trait + facade handle 三层表达，不强行做成一个大而空的统一 trait。
- `IObject/ISystem/IEntity/IComponent`：作为世界层语义契约，归属 `zircon_scene` 的 ECS/world 模型，不进入 `zircon_core` 全局抽象。
- skill 内必须提供一张概念名到 Rust 名的映射表，固定采用“文档 `I*`，代码 Rust 风格”的命名规则。

## Skill Design

- skill 名称固定为 `zr-runtime-interface-convergence`。
- `SKILL.md` 负责三件事：先读路线图与总重构方案，再把需求归类到接口家族，再做结构化/模块化审计后才给出实现建议。
- `references/interface-family.md` 固定记录接口家族、允许依赖方向、生命周期语义、crate 归属、ECS 例外规则。
- `references/structural-audit.md` 固定记录当前仓库的真实诊断结论：descriptor 主干已存在、`EngineModule` 未成为主入口、plugin 路线未贯通、entry 静态耦合重、editor 局部边界过载。
- 增加一个审计脚本，输出至少这些结果：自由 `module_descriptor()` 分布、`stub_module_descriptor` 使用点、缺失模块拥有者类型的 crate、plugin 运行时空洞、entry 对模块的静态依赖、超大文件热点。
- 生成 `agents/openai.yaml`，让 skill 可被稳定发现和触发。

## Test Plan

- skill 结构验证通过 `quick_validate.py`。
- 审计脚本能稳定输出模块类型缺失、skeleton module、plugin 缺口、entry 耦合和文件热点。
- 每个 runtime crate 都能被归类为 `converged`、`skeleton` 或 `needs-refactor`。
- `zircon_entry` 的 editor/runtime/headless 路径都能映射到明确的 `EngineEntry` 责任边界。
- `EngineModule` 能覆盖当前真实模块 crate，旧自由函数仅作为过渡层存在。
- `IEntity/IComponent` 的定义不破坏当前 ECS 方向，不把世界层重新退回 OO 基类体系。
- 后续进入实现阶段时，再补 `cargo check --workspace` 作为架构收敛后的验证门。

## Assumptions

- 以 `.codex/plans/全系统重构方案.md` 作为当前架构权威，不另起一套平行主干。
- 本轮目标是“接口家族设计 + skill 设计 + 结构诊断 + 重构路线”，不是立即改代码。
- 代码命名固定采用 Rust 风格，概念命名固定保留 `I*`。
- 当前结构判断基于静态仓库勘察；本次规划中 `cargo check --workspace` 未在时限内完成，因此编译健康不作为本轮结论前提。
