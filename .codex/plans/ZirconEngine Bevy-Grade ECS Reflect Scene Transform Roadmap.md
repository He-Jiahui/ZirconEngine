# ZirconEngine Bevy-Grade ECS / Reflect / Scene / Transform Roadmap

## Summary
- Target: full Bevy-grade parity, per your choice, not only developer-facing API parity. This includes typed ECS, resources, queries, schedules, change detection, lifecycle/observers, reflection/type registry/derive, scene serialization, transform propagation, editor integration, and performance-oriented storage/execution.
- Constraint: do not import `bevy_ecs` as the runtime dependency. Use Bevy as source/reference, keep Zircon’s authority in `zircon_runtime::scene::World`, and preserve stable external `EntityId = u64` for editor, serialization, and asset compatibility.

## Public Interfaces And Architecture
- Add `zircon_runtime::scene::ecs` as the internal ECS kernel, while keeping `zircon_runtime::scene::World` as the public world authority.
- Add typed contracts: `Component`, `Resource`, `Bundle`, `ComponentId`, `ResourceId`, `ArchetypeId`, `StorageType::{Table,SparseSet}`, `QueryState`, `QueryData`, `QueryFilter`, `Commands`, `Events<T>`, `Messages<T>`, `Observer`, `LifecycleEvent`, and `ChangeTick`.
- Add reflection contracts under `zircon_runtime_interface::reflect` plus runtime integration in `zircon_runtime::scene::reflect`: `Reflect`, `FromReflect`, `TypePath`, `TypeInfo`, `TypeRegistration`, `TypeRegistry`, `ReflectComponent`, `ReflectResource`.
- Add a build-time proc-macro crate `zircon_reflect_derive` for `#[derive(Reflect)]`, `#[derive(Component)]`, `#[derive(Resource)]`, and later `#[derive(Bundle)]`; runtime crates consume generated impls, not macro internals.
- Hard-cut `SystemStage::LateUpdate` to `PostUpdate`; target order is `First -> PreUpdate -> FixedUpdate -> Update -> PostUpdate -> Last -> RenderExtract`, matching Bevy’s schedule shape while retaining Zircon’s render extract stage.

## Milestones
- M0 Evidence And Baseline: freeze current tests, document Bevy/Zircon mapping, and record the current dirty workspace as unrelated. Testing stage: `cargo test -p zircon_runtime --lib scene::tests --locked`, `cargo test --workspace --locked --no-run`.
- M1 ECS Identity And Storage: introduce generational internal entity slots, table/sparse-set storage, `ComponentId`, `ResourceId`, and a compatibility map from stable `EntityId` to internal entity location. Testing stage: spawn/despawn/stale ID, storage move/remove, existing scene roundtrip unchanged.
- M2 Typed Component / Resource / Bundle API: implement `Component`, `Resource`, `Bundle`, typed `World::{spawn, insert, remove, get, get_mut, insert_resource, resource}`; keep existing fixed component setters as wrappers. Testing stage: fixed components and dynamic plugin components both attach through the same registry path.
- M3 Query And Borrow Safety: implement `QueryState`, `With`, `Without`, `Added`, `Changed`, `Option<&T>`, entity access, and runtime access conflict detection before systems run. Testing stage: query parity cases from Bevy query tests plus Zircon transform/light/physics component queries.
- M4 Schedule / Systems / Commands: replace stage-only hook loops with a schedule graph, system descriptors, sets, ordering, command queue, `apply_deferred`, and deterministic single-thread executor first. Testing stage: order, ambiguity diagnostics, deferred spawn/insert/remove, plugin hook ordering.
- M5 Change Detection And Lifecycle: add per-component/resource ticks, `is_added`, `is_changed`, removed-component tracking, and lifecycle events `Add/Insert/Replace/Remove/Despawn`. Testing stage: Bevy-style `Changed<T>` propagation, stale tick wrap, lifecycle order, despawn cleanup.
- M6 Observers And Messages: implement immediate observer triggers for lifecycle and entity events, plus scheduled `Messages<T>` for frame-bound communication; keep existing `EventBus` for topic JSON events as outer integration. Testing stage: observer targeting, propagation, observer removal, message reader cursor behavior.
- M7 Transform / Hierarchy Cutover: convert `LocalTransform`, `WorldMatrix/GlobalTransform`, active hierarchy, and node cache rebuild into PostUpdate systems; setters only mark dirty. Testing stage: parent cycles, reparent, inactive parent, static mobility, large hierarchy, one-frame lag rules documented.
- M8 Reflection And Type Registry: replace ad hoc `ComponentTypeDescriptor` property metadata with `TypeRegistry`-backed component/resource metadata; preserve plugin JSON components through `ReflectComponent` adapters. Testing stage: reflected field read/write, editor-visible schema, unknown type errors, serialize/deserialize reflected values.
- M9 Dynamic Scene Serialization: introduce `DynamicEntity`, `DynamicScene`, entity-map remapping, reflected resource serialization, scene patch/apply, and versioned migration from current `NodeRecord` scene files. Testing stage: save/load old scenes, save/load reflected scenes, missing type diagnostics, resource/entity remap.
- M10 Editor Integration: make hierarchy, inspector, undo/redo, selection, viewport overlays, and plugin component editing consume typed ECS/reflection projections; no editor state returns to runtime world storage. Testing stage: inspector editing for fixed and reflected components, undo/redo component mutation, viewport render extract remains clean.
- M11 Performance Parity Stage: replace compatibility-heavy maps on hot paths with archetype/table iteration, sparse-set opt-in, cached query state, parallel executor using `JobScheduler`, and schedule conflict graph. Testing stage: microbenchmarks for spawn/query/change/transform; correctness must pass before accepting speedups.
- M12 Hard Cutover And Docs: remove duplicate fixed-storage paths that no longer own behavior, update module docs under `docs/zircon_runtime/scene` and `docs/engine-architecture`, and add Bevy-parity examples. Testing stage: full CI shape from [.github/workflows/ci.yml](E:/Git/ZirconEngine/.github/workflows/ci.yml:1): workspace build/test plus plugin workspace check/build/test.

## Test And Acceptance Criteria
- Core scenarios: typed spawn/despawn, stale entity rejection, fixed and dynamic components, resources, queries, deferred commands, change detection, lifecycle events, observer triggers, scene serialization, transform propagation, render extract, and editor inspector projection.
- Boundary scenarios: empty world, duplicate component insert, component remove while observed, recursive despawn, missing reflected type, malformed scene file, query conflicts, large hierarchy, repeated plugin load/unload, and tick wrap.
- Acceptance: all milestone testing stages pass, `cargo build --workspace --locked --verbose`, `cargo test --workspace --locked --verbose`, and plugin workspace `check/build/test` pass or unrelated pre-existing failures are explicitly recorded with evidence.

## Assumptions
- Bevy parity means behavior and capability parity, not source copying or API name cloning.
- Public `EntityId = u64` remains stable; internal generational identity is added beneath it.
- `zircon_runtime::scene::World` remains the authority; editor consumes projections and command surfaces.
- Existing unrelated dirty files are not part of this plan.
