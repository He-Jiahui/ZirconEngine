# Hybrid GI / Lumen-Style 分层混合光照计划

## 1. 计划定位与当前基线

- 计划主参考固定为仓库内 `dev/LumenInUE5.5.4WithComputeShader` 与可核对的 Unreal Lumen 源码结构，职责对齐 `scene representation -> surface cache -> screen probe gather -> radiance cache -> trace composite`。微信“计算机图形学”合集只用于补充使用场景、风险清单和研究方向，不作为算法正确性或性能数据的权威证据。
- 截至 2026-07-12，历史状态记录已经证明 M1 场景表示、Surface Cache、HZB、Voxel fallback，M2 动态方向光/点光/聚光/Emissive 的 Deferred/Forward+ 产品矩阵，以及 M3 motion/depth/source/support/normal-aware temporal、空间降噪和 multi-ray quality 已有实现证据。旧版 Summary 中“仍缺少 scene representation / surface cache / voxel fallback”的描述已经失效，本次校准不重复申领这些完成项。
- 后续目标从“只做全动态 Lumen-style GI”提升为可交付的分层混合光照：静态几何优先消费 Plan 11 EL-M3 的 lightmap/probe baked baseline，动态物体、动态灯和 Emissive 变化由 Hybrid GI 增量补光；每个表面、每个间接光 lobe 在任一帧只能有一个权威来源，禁止 baked 与 dynamic 对同一能量重复累计。
- Deferred 与 Forward+ 必须继续共享同一 `HybridGiInputSet`、同一追踪层级和同一 composite 规则。WGPU V1 不依赖硬件 RT；硬件 RT 只能作为未来可选加速层，不能成为 WebGPU/WGPU 产品路径的成立条件。

## 2. 目标、非目标与依赖边界

### 2.1 目标

- 保持现有 Dynamic Only 路径可用并完成编辑器默认接入、RenderDoc 证据和完整 CI 收口。
- 增加 `Baked Static + Dynamic HGI` 模式，覆盖室内静态场景、开放世界和高质量离线/电影预览三类使用方式。
- 将追踪组织为 capability graph，而不是把所有机制写成一条伪线性 fallback：先选择 `Screen / World` trace domain，再在 `Mesh SDF / Global SDF / Voxel / Optional Hardware RT` 求交后端间按能力与预算路由，命中后再从 `Surface Cache / Radiance Cache / baked probe` 选择权威 lighting source。能力不足时跳过不可用节点，最终仍由 Voxel 或关闭 GI 提供确定性降级。
- 提供可观测的来源、失效、驻留、预算和时序诊断，用户能够判断一个像素来自 baked、screen、surface cache、SDF、voxel 或 history。

### 2.2 非目标

- 不在本计划重新实现 lightmap UV、lightmap baker、静态 probe grid 或 baked asset 格式；这些由 `docs/plans/zircon_runtime/render/11-environment-lighting.md` 的 EL-M3 和 `rendering.baked_lighting` 插件拥有。
- 不把 NeRF、神经材质、神经降噪或文章中的 DLSS 版本宣传并入 V1/V1.1 验收；它们只进入 Plan 16 研究队列，必须以官方论文、SDK 和许可证复核后才能立项。
- 不承诺文章中的帧率、显存或百分比数据；Zircon 只接受本仓库场景、固定硬件、固定 preset 的测量结果。

## 3. 分层混合光照架构

### 3.1 间接光模式

- `DynamicOnly`：现有全动态 Hybrid GI，适合可破坏场景、昼夜变化和无 baked 数据项目。
- `BakedStaticDynamic`：静态表面从 Plan 11 baked lightmap/probe 读取稳定基线；动态物体和变化光源由 HGI 计算动态增量。
- `Disabled`：能力不足、服务器或显式关闭时不建立 HGI 资源。
- 最终 Rust API 名称必须在 M4 先写失败测试再落地；本节名称是语义合同，不视为已实现接口。

### 3.2 表面参与规则

- 静态接收面默认 `BakedStatic`：静态间接光只来自 lightmap；动态灯/Emissive 变化只叠加明确标记的 dynamic delta。
- 动态接收面默认 `DynamicReceiver`：近场由 HGI 追踪，远场可采样 Plan 11 probe grid 作为低频环境基线，但 composite 必须扣除或禁止重复的静态 bounce。
- `HybridReceiver` 只用于经过测试的过渡材质或跨区物体；必须记录 baked weight、dynamic weight、source mask 和 invalidation epoch。
- `Disabled` 表面不进入 card、SDF、voxel 或 baked 间接光采样，但仍可参与直接光和阴影。
- 物体由 static 改为 movable、材质/Emissive 改变、lightmap asset 变化、transform 越出 baked cell 或灯光 mobility 变化时，必须失效相应 Surface Cache page、trace history 与 baked/dynamic 混合权重。

### 3.3 数据所有权

- Plan 11 EL-M3 拥有 baked asset、lightmap sampling ABI、probe SH grid、烘焙 DTO 与 baker 插件。
- Hybrid GI 拥有参与策略、source mask、dynamic delta、Surface Cache、Screen Probe、Radiance Cache、SDF/Voxel trace、history 和 composite。
- Scene renderer 只从通用 scene extract 派生内部 cards/pages/clipmaps；`RenderHybridGiExtract` 保持 settings/budget/debug payload，不恢复 authored probes/trace regions 作为场景真源。
- `FrameHistorySlot::GlobalIllumination` 继续表示最终 GI composite history；历史元数据必须包含来源、support、normal/depth、participation epoch 和 baked asset generation。

### 3.4 Trace capability graph

- `trace domain`：Screen HZB 先处理可见近场；未解决样本进入 World trace。Screen trace 只回答屏幕空间求交，不能把 Surface Cache 当作同级求交后端。
- `intersection backend`：World trace 根据平台能力、场景资产和预算选择软件 Mesh SDF、Global SDF、Voxel 或未来 Optional Hardware RT。Hardware RT 是替代后端，不是必须排在所有软件路径后的最后一级。
- `hit-lighting source`：求交完成后，命中点从 Surface Cache、Radiance Cache 或 Plan 11 baked probe/lightmap 中选择一个权威间接光来源；来源选择与几何求交分离。
- 每个样本必须写入 domain、backend、lighting source、distance、confidence 和 fallback reason。M5 scheduler 只能消费这张 graph，不能重新硬编码文章中的单一顺序。

### 3.5 Dynamic delta 能量账本

- 最终间接光按 `surface + lobe + baked_light_set_generation + participation_epoch` 记账：`final_indirect = authoritative_baked_baseline + validated_dynamic_delta`。任一 ledger key 不得同时接受未扣重的 baked bounce 与完整 HGI bounce。
- 静态接收面只对未进入当前 baked light set 的动态灯、移动 Emissive 或显式变化遮挡计算 delta；静态灯 mobility 改变时必须换代 generation、清除旧 delta，并在重烘焙前进入可诊断降级，禁止继续叠加旧基线。
- 动态物体可消费 probe 的低频静态环境，但 HGI trace 必须携带 source mask，排除已经由 probe 表达的静态 bounce。无法证明可扣重时，产品策略必须在 baked baseline 与完整 dynamic HGI 中二选一。
- 遮挡或 shadow 状态使“减去旧光”不可可靠重建时，不允许产生负补偿；必须失效受影响区域并使用 zero-delta、DynamicOnly 或等待重烘焙的确定性路径。

### HGI-M5-RC：Radiance Cache 生命周期

1. `RC-S1 demand marking`：Screen Probe 放置后标记所需 Radiance Probe；Radiance Cache 使用独立 clipmap，不能复用或冒充 Global SDF Clipmap。
2. `RC-S2 persistent state`：维护上一帧 indirection/cache 传播、camera scroll、history reprojection、clear 与 invalidation；元数据包含 last-used、last-traced、generation 和 participation epoch。
3. `RC-S3 allocation`：建立 probe free-list、分配/回收、预算淘汰与耗尽降级；预算截断必须确定且可诊断。
4. `RC-S4 update pipeline`：按 mark -> allocate trace tiles -> trace -> filter -> border fixup -> mip -> Screen Probe consume 执行，不允许在未过滤或未完成边界修复时暴露新 generation。
5. `RC-S5 validation`：覆盖 camera scroll、history clear 后黑 probe、free-list 耗尽、预算截断、indirection 失效和跨帧 generation 不匹配。

HGI-M5-RC 完成门：Radiance Cache 与 Global SDF 各自拥有独立资源、滚动和统计；所有 probe 在未驻留、被淘汰或 generation 不匹配时返回确定 fallback，不能读未初始化 radiance。

### HGI-M5：SDF 与分层追踪后端

1. `M5-S1 mesh bounds and flags`：建立 Mesh SDF object bounds、visible/movable/shadow/emissive/indirect-while-hidden flags 与 clipmap influence culling。
2. `M5-S2 mesh SDF assets`：由 asset/import 路径生成或导入 Mesh SDF；runtime 只消费版本化资产，不在首帧同步烘焙。
3. `M5-S3 global SDF clipmap`：相机中心按 cell/page 稳定取整，支持 dirty region、page residency、streaming 和确定性预算。
4. `M5-S4 trace scheduler`：实现 3.4 的 capability graph，分别调度 Screen/World domain、软件 SDF/Voxel 或可选 HWRT 求交后端，以及 Surface/Radiance/Baked lighting source；每个节点写 source、distance、confidence、fallback reason 和 cost counters。
5. `M5-S5 optional hardware RT`：统一消费 Render Plan 20 的 `Capabilities + Policy + CapabilityPlan -> Selection`、共享 RayTracingScene 与 RHI；只有 wgpu adapter 实际启用 AS + InlineQuery 或完整 pipeline、项目策略允许且 selection 选中时才接入。缺失、实验开关关闭或预算不足时继续 SDF/Voxel,不得改变结果语义。

M5 完成门：关闭任意可选层仍有确定性结果；camera clipmap 滚动无页抖动和明显漏光；SDF/Voxel miss 不返回未初始化 radiance；WebGPU 平台无需硬件 RT 即可通过核心场景。

### HGI-M6：可用性、诊断与性能治理

- 质量档位必须约束 ray count、trace distance、Surface/Radiance Cache 更新量、clipmap page、history length 和显存预算，禁止只换枚举名称不改变工作量。
- Debug views 至少包含 participation、baked weight、dynamic weight、trace source、card/page residency、SDF/voxel occupancy、radiance cache、history confidence、invalidation reason。
- Stats 至少包含各追踪层 hit/miss、更新页数、eviction、失效数量、GPU pass 时间、资源字节数和 capability fallback reason。
- 为 WebGPU 建立 format/filter/renderability/storage/readback/mip capability 矩阵；硬件光追能力、项目策略与 execution candidate 统一引用 Render Plan 20,不允许把桌面 Vulkan/DX12/Metal 的隐含能力带入 WGPU 合同。
- RenderDoc 验收固定检查资源命名、pass 顺序、绑定尺寸、未初始化读取、history ping-pong 和 composite source mask。

## 5. 产品使用方式

当前可运行路径和编辑器/运行时配置见 [`docs/zircon_plugins/hybrid_gi/usage.md`](../../docs/zircon_plugins/hybrid_gi/usage.md)。截至 2026-07-14，五种 Profile 的解析、预算和结构化回退已进入产品路径：`FullyDynamic`/`Custom DynamicOnly` 可直接使用；含 baked baseline 的 Profile 只有在同帧存在有效 Plan 11 合同时才生效，缺失时确定性降级为 `DynamicOnly/BakedLightingUnavailable`。broad/full 验证仍开放，因此不能把整个 HGI-M4 宣称为最终交付。

| Profile | 主要场景 | 静态间接光 | 动态间接光 | 默认追踪策略 | 关键风险 |
| --- | --- | --- | --- | --- | --- |
| Fully Dynamic | 可破坏关卡、昼夜变化 | 无 | 全量 HGI | Screen/Surface Cache/Voxel，SDF 可选 | 更新预算与时序残影 |
| Indoor Static | 室内、固定结构 | Lightmap 为权威 | 动态物体/灯/Emissive delta | Baked baseline + 近场动态 trace | 双重计能量、漏光 |
| Open World | 大场景、streaming | 远场/静态区 baked | 玩家附近与变化区 HGI | Probe/lightmap + clipmap 分层 | 页抖动、跨区 generation |
| Cinematic | 高质量预览/确定性采集 | 可选高质量 baked | 高 ray count HGI | 全分层、固定 warmup 与采集帧 | 显存峰值、可重复性 |

Profile 只提供工程默认值，不替代项目显式配置。运行时必须能查询最终解析后的模式、预算和 fallback，编辑器不得仅显示用户请求值。

## 6. 测试与验收矩阵

- 能量边界：纯 baked、纯 dynamic、baked + dynamic light、baked + moving emissive、dynamic object on baked floor；验证无 double count、负能量、NaN 或突变。
- 失效边界：static/movable 往返、材质与 Emissive 修改、lightmap/probe 换代、场景分区装卸、相机跨 clipmap cell/page。
- 追踪边界：screen hit、screen miss/surface hit、mesh SDF hit、global SDF hit、voxel fallback、全层 miss 和 capability-disabled。
- 时序边界：静止收敛、平移/旋转、遮挡显隐、薄墙、封闭房间、快速灯光变化和动态物体交叉。
- Radiance Cache 边界：camera scroll、history clear、indirection generation 变化、free-list 耗尽、预算截断、probe 淘汰后重分配、filter/border/mip 未完成不可见。
- 管线一致性：Deferred/Forward+ 使用相同输入语义；允许数值容差，不允许来源层级和失效策略分叉。
- 平台边界：Windows native WGPU 为主验收；WebGPU 严格验证 format/usage/readback；WSL 只在明确 Linux-only 需求下使用。
- 产品证据：每个里程碑至少包含 focused unit/contract、真实 WGPU readback、真实产品场景 PNG、stats 快照；M3/M4/M5/M6 必须有 RenderDoc `.rdc`。
- 所有 Cargo 验证必须通过 session coordinator 分配，并把 target 放在 D/E/F 盘根目录 cargo-targets 下；禁止写入仓库 `target/`。

## 7. 公共接口约束

- `RenderSceneGeometryExtract` 继续显式区分 directional、point、spot；Emissive 从 material/capture 链进入。
- `RenderHybridGiExtract` 只承载 feature、mode、quality、budget、profile 和 debug 请求；cards/pages/SDF/voxel/probes/history 均为 renderer/runtime 内部状态。
- baked sampling ABI 不上移到 HGI 插件；HGI 通过 Plan 11 稳定 DTO/资源句柄消费 baked 数据。
- 外部 API 只暴露稳定设置、解析后状态、统计和诊断，不暴露底层 atlas/page/trace buffer 的可变所有权。
- 任何新 public enum/DTO 先以序列化 round-trip、默认值、能力降级和旧资产迁移测试锁定，再进入实现。

## 8. 假设与硬约束

- “全部动态灯型”在当前范围内固定为 directional + point + spot + Emissive；area/rect/IES 另立里程碑。
- V1/V1.1 的必备 miss fallback 仍是软件 Voxel Clipmap；Mesh/Global SDF 属于 M5 质量升级，不反向阻塞现有产品闭环。
- Deferred 与 Forward+ 必须共用 GI 数据合同；Forward+ 可补 GBuffer-lite，但不得拥有独立 Hybrid GI 算法。
- 旧 `RenderHybridGiProbe / RenderHybridGiTraceRegion` 只允许 fixture/debug；不得恢复为长期 authoring 或主场景真源。
- 文章中的未来 API、SIGGRAPH 2026、DLSS、NeRF 或神经渲染内容，在官方来源与许可证复核前均不得写成完成条件。
