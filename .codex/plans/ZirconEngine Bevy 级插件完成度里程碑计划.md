# ZirconEngine Bevy 级插件完成度里程碑计划

## Summary
目标不是复制 Bevy API，而是把 Zircon 的插件体系补到 Bevy 同级的“可选择、可诊断、可裁剪、可验证”完成度：默认 profile 不再依赖隐式 externalized 警告，插件能力有成熟度分类，项目/export 可以按 profile 选择 animation/audio/sprite/particles/navigation/net 等能力。

当前源码显示：Zircon 已有较广的 `RuntimePluginId` 和 catalog，且 `animation`、`sound`、`navigation`、`net`、`particles` 都有真实 runtime crate；核心缺口在 [builtin resolver](<E:/Git/ZirconEngine/zircon_runtime/src/builtin/runtime_modules.rs:644>) 对多数插件仍只返回 externalized，profile 仍停留在 [minimal capability list](<E:/Git/ZirconEngine/zircon_runtime/src/plugin/core_profiles.rs:4>)，缺少成熟度和 profile 级选择。

## Public API / Interface Changes
- 新增 `PluginMaturity::{Core, Stable, Beta, Experimental, Externalized, Stub, Deprecated}`，写入 `RuntimePluginDescriptor`、`PluginPackageManifest` 和 first-party `plugin.toml`。
- 新增 `CapabilityStatus::{Complete, Partial, Stub, Externalized, Unsupported}`，用于标注每个 capability/optional feature 的真实实现状态、目标平台限制和 Bevy 参考来源。
- 新增 `RuntimeProfileId::{Minimal, Client2d, Client3d, Editor, Dev, Server}` 与 `RuntimeProfileDescriptor`：包含 target mode、默认插件、可选插件、必需 capability、允许的最低 maturity、是否允许 externalized required plugin。
- 新增结构化 `RuntimePluginAvailabilityReport`，替代散落 warning 字符串：区分 `available`、`linked`、`native_dynamic`、`externalized_missing`、`stub`、`blocked_by_target`、`blocked_by_maturity`、`missing_required`。
- `ExportBuildPlan` 序列化 `runtime_plugin_availability`，由 export profile 推导 `RuntimeProfileDescriptor`，并结合 linked/native provider registration 生成结构化可用性报告；这让项目导出和 editor tooling 可以直接读取 linked/native/externalized/maturity 分类。
- `ExportProfile.runtime_profile_id` 可显式绑定 `minimal/client_2d/client_3d/editor/dev/server`，旧 manifest 仍可通过 target/name 推断；source template 会序列化该字段，避免 2D/3D profile 选择依赖导出名字符串。
- `zircon_runtime` 仍不得依赖 `zircon_plugins`；first-party 静态注册放在 app/editor-support 层，通过现有 `bootstrap_with_runtime_plugin_and_feature_registrations` 传入。

## Milestones
1. **M0: Bevy/Zircon Capability Audit**
   建立 capability matrix：对齐 Bevy default/minimal/features 与 Zircon catalog、plugin workspace、runtime registrations。明确 `animation/sound/navigation/net/particles` 是“有 runtime 但 resolver 未闭环”，`sprite` 需要新增 first-party `sprite_2d` 插件而不是塞进 `texture` 或 `tilemap_2d`。

2. **M1: Profile + Maturity Foundation**
   扩展 descriptor/manifest/catalog，补齐 `minimal/client_2d/client_3d/editor/dev/server` profile。默认 `client_2d/client_3d` 按 Bevy default 思路启用 asset/scene/render/ui/audio/sprite 基线；`server` 不启用 UI/render/audio listener；`dev/editor` 可启用 diagnostics/remote。Stable profile 中 required 插件不得是 `Externalized` 或 `Stub`。

3. **M2: Resolver and Registration Closure**
   重构 resolver 为 provider chain：core builtin、linked first-party runtime、native dynamic package、external missing。`module_for_plugin` 不再对真实 first-party 插件直接吐 externalized warning；required 缺失变 fatal，optional 缺失变结构化 diagnostic。把 `animation/sound/navigation/net/particles` 的 runtime registrations 接入 profile bootstrap 测试。

4. **M3: Animation Completion**
   以 Bevy `AnimationClip`、`AnimationGraph`、`AnimationPlayer`、事件 track 和 PostUpdate 调度为参考，补齐 Zircon animation 的 clip asset、graph/blending、transition、target path、timeline event、gltf animation import、editor authoring。验收包含曲线采样、循环/反向事件、缺失 target 诊断、transform propagation 顺序、gltf fixture。

5. **M4: Audio/Sound Completion**
   以 Bevy `AudioPlugin` 的 `AudioPlayer`、`PlaybackSettings`、`GlobalVolume`、spatial listener/source 和 cleanup 为参考，把 `sound` 补到 profile 可用：音频 asset/importer、实体播放组件、mixer/global volume、spatial update、sink cleanup、无音频设备降级诊断。timeline animation track 和 ray-traced reverb 保持 optional feature gated。

6. **M5: Sprite2D First-Party Plugin**
   新增 `RuntimePluginId::Sprite2d` 与 `zircon_plugins/sprite_2d/runtime`。实现 `SpriteRenderer`、texture atlas、custom rect/size、9-slice/slicing、sorting layer/order、2D bounds/culling、render extract/queue integration；可选 picking 只在 input/picking capability 存在时启用。

7. **M6: Navigation Split**
   拆分语义：`ui_navigation` 作为 Bevy parity 能力，覆盖 focus、tab、directional navigation、manual override；现有 `navigation` navmesh/pathfinding 标为 first-party beta/advanced optional。强化 navmesh asset/bake、agents、dynamic obstacles、offmesh links、editor debug gizmos 和 invalid settings diagnostics。

8. **M7: Net / Remote**
   以 Bevy Remote Protocol 为 first-party 对标目标：新增或收敛 `net.remote_protocol`，支持 JSON-RPC/world query/diagnostics，默认只在 `dev/editor` profile 可显式启用，不在 client/server 默认监听端口。`replication/reliable_udp/rpc/websocket/content_download` 继续作为 experimental optional feature，受 maturity/profile gate 控制。

9. **M8: Particles / VFX**
   因 Bevy core 无 first-party particles，Zircon particles 不作为 Bevy default parity 阻塞项，先标 `Experimental`。补齐 CPU deterministic simulation、GPU fallback、sprite/material integration、render extract order、透明排序、stats diagnostics；`physics`、`animation_control`、`gpu_simulation`、`vfx_graph` 均通过 feature dependency 验证。

10. **M9: Export and Editor UX**
   Project manifest/export profile 使用 `RuntimeProfileDescriptor` 生成插件选择和 packaging plan。Editor plugin manager 展示 maturity、profile membership、target support、缺失依赖、blocked reason、Bevy parity note；不再展示笼统 externalized warning。

11. **M10: Docs and CI Gates**

## Execution Order and Promotion Rules

这条路线必须按层推进，而不是按“哪个插件看起来快”推进。Bevy 的完成度来自默认 feature/profile、真实插件实现、可裁剪组合、文档和 CI 一起闭环；Zircon 的对应规则是先证明 profile/provider 基础，再逐步提升插件能力，最后才提升 editor/export/Hub 体验。

| Layer | Milestones | May advance only when | Evidence bundle |
| --- | --- | --- | --- |
| Foundation | M0 capability audit, M1 profile/maturity, M2 resolver/provider closure | 每个 `RuntimePluginId`、first-party `plugin.toml`、profile required/optional membership、availability bucket 都有 owner 文档和测试候选；stable/default profile 没有 required `Externalized` 或 `Stub`。 | `profile_maturity`、`manifest_contributions`、`export_build_plan`、app `profile_bootstrap`、`profile-selection.md` 和 parity matrix rows。 |
| Default-facing runtime features | M3 animation, M4 sound, M5 sprite2d | M2 provider-chain 已经能区分 linked/native/externalized/missing；功能测试从 asset/import/runtime/scene/render/profile 下层向上通过。 | 每个插件至少有 runtime tests、profile/provider tests、Bevy source evidence、advanced-feature divergence note。 |
| Split optional lanes | M6 navigation, M7 net/remote, M8 particles | 先明确 Bevy parity lane 和 Zircon advanced lane 的边界，再验证各自 target/profile/maturity gate。不能用 gameplay navmesh 代替 UI navigation，不能用 gameplay networking 代替 developer remote，不能把 particles 变成 Bevy default blocker。 | UI navigation focused tests、remote protocol tests、net feature tests、particles runtime/editor tests、explicit profile optionality evidence。 |
| Productization | M9 export/editor UX | Runtime profile、project manifest、export profile、availability report、editor status、Hub summary 都读同一份结构化状态。任何 UI 展示不得解析 warning 字符串或维护第二套 plugin availability model。 | `ExportBuildPlan` tests、editor manager/plugin status tests、pane presentation tests、Hub catalog/view-model tests、native dynamic export diagnostics。 |
| Regression guard | M10 docs/CI gates | 每个已提升能力都有 owner doc、candidate commands、debug order、validation notes；CI/local validation ladder 与 `.github/workflows/ci.yml` 和 `validate-matrix.ps1` 对齐。 | scoped docs checks、placeholder scan、focused tests、plugin workspace checks、export-platform matrix、workspace build/test、validator or CI evidence。 |

Promotion rules:
- A milestone may be documented ahead of implementation, but it is not implementation-complete until its testing stage has run or the docs explicitly say the pass was docs-only.
- Upper layers cannot patch around lower-layer failures. For example, editor/export UX must not hide a bad `RuntimePluginAvailabilityReport`, and app bootstrap must not accept a missing required plugin unless the profile itself makes it optional.
- Feature breadth is not parity by itself. A wider Zircon subsystem, such as sound or particles, still needs the Bevy baseline behavior pinned before advanced lanes count.
- `zircon_runtime` remains descriptor/report owner and must not depend on `zircon_plugins`; concrete first-party providers stay in `zircon_app`, generated export hosts, plugin crates, or native package paths.
- Active-session or Cargo target contention can justify a docs-only continuation, but final promotion must record exact commands, platform, package/workspace scope, `--locked` usage, and remaining gaps.

## Critical Path and Parallel Lanes

The critical path is `M0 -> M1 -> M2 -> first default-facing plugin proof -> M9 -> M10`. ## Executable Handoff and Promotion Submission

Future implementation workers should treat each M0-M10 slice as a work order, not as a broad theme. A work order is valid only when it carries the fields below. If one field cannot be supplied from current source, the worker must keep the slice in analysis/docs-only mode.

| Field | Required content | Rejection rule |
| --- | --- | --- |
| Work order identity | Milestone id, lane name, owner crate/module, target profile, and whether the slice is foundation, default-facing, optional advanced, productization, or regression guard. | Reject vague names such as "finish audio" or "improve plugins" because they cannot be mapped to a promotion gate. |
| Bevy source anchors | Local Bevy files and line anchors for the behavior being matched, plus public docs link when the user-facing API or feature vocabulary matters. | Reject references that only say "Bevy does this" without pointing to source behavior. |
| Zircon owner paths | Exact Zircon files or docs that own descriptors, provider registration, runtime behavior, export/editor/Hub projection, and tests. | Reject a slice that crosses active owner boundaries without a coordination note. |
| Lower gates | The M0-M10 gates that must already be accepted, plus any active-session blockers. | Reject promotion when the lower gate is still V0/V1 docs-only and the current slice needs runtime evidence. |
| Implementation package | The concrete behavior to change or verify: descriptors, provider chain, runtime plugin, profile membership, export report, editor projection, docs-sync, or CI gate. | Reject UI/demo-only work that does not update the source-of-truth owner. |
| Validation package | Validation rung from V0-V6, exact command or static check, platform, `--locked`/offline/target-dir details, expected scope, and debug order. | Reject claims that use stale logs or omit command scope. |
| Docs package | Owning docs, matrix rows, validation note, accepted divergence, and related-code/doc owner updates. | Reject code-changing slices that leave docs for a later pass. |
| Stop condition | The first failed condition that prevents promotion and the lower layer that owns the fix. | Reject work that hides lower-layer failure in an upper presentation layer. |

Promotion submission flow:
1. Coordination preflight: run the recent plan/session scan, read any active session touching the same owner path, and record whether the slice is implementation or docs-only.
2. Source evidence preflight: cite Bevy source anchors and current Zircon owner paths before editing.
3. Lower-gate check: confirm M0-M2 foundation status before any default-facing or productization promotion.
4. Implementation or docs-only slice: keep edits inside the declared owner paths and update docs in the same pass.
5. Validation stage: run the declared V-rung evidence when the milestone stage allows it; if Cargo is intentionally skipped, record V0/V1 and keep the row unpromoted.
6. Matrix update: update `bevy-parity-matrix.md`, `profile-selection.md`, or the owning module doc with validation notes and accepted gaps.
7. Promotion decision: promote only when evidence reaches the required rung and no stop condition remains; otherwise record the next lower-layer fix.

The submission is intentionally strict. Bevy's own engineering model separates plugin composition, feature profiles, docs generation, example checks, compile checks, and tests; Zircon needs the same separation to avoid a green UI or a working demo being mistaken for engine-level completion.
