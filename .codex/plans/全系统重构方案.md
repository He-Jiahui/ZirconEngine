# Zircon 全系统重构方案

## Summary

- 本次按你的选择采用一次性大重构，不保留旧主链路作为长期兼容层；最终状态以路线图为准，而不是以当前最小编辑器实现为准。
- 新内核以 `zircon_app -> zircon_core -> zircon_module/zircon_server -> 各功能模块` 为主干，`CoreRuntime` 作为进程级唯一核心实例，统一管理模块、驱动器、管理器、事件、配置、调度和插件生命周期。
- `zircon_scene` 立即改为 `Archetype ECS + Hierarchy`，`Entity` 成为唯一对象身份；现有 Scene 树退化为 ECS 层级视图与序列化视图，不再是权威运行时模型。
- 所有 `zircon_*` crate 都要同步接入新架构并具备真实模块骨架，不再保留只返回 `engine_name()` 的占位 crate。
- 插件不再走 Rust 动态库，改为 VM 插件架构；`zircon_script` 负责宿主侧插件协议、稳定句柄、热替换状态迁移和 VM 后端适配槽位。`E:\Git\zr_vm` 是后续真实 VM 后端来源，本仓库本轮只把集成边界设计好并留空实现。

## Key Changes

### 1. 内核与生命周期

- `zircon_core` 重构为真正的核心层，提供：
  - `CoreRuntime`
  - `CoreHandle/CoreWeak`
  - `RegistryName`
  - `StartupMode::{Immediate, Lazy}`
  - `LifecycleState::{Registered, Initializing, Running, Stopping, Unloaded}`
  - `DependencySpec`
  - `EventBus`
  - `ConfigStore`
  - `JobScheduler/ClockDriver`
- 依赖解析严格按路线图执行：
  - Driver 只能依赖 Driver，不能依赖 Manager。
  - Manager 可以依赖 Driver 和 Manager。
  - 所有依赖在 descriptor 中声明，由 Core 生成按需解析闭包；业务对象不缓存跨生命周期的直接强引用。
- 保留字符串命名访问，同时增加类型化 façade 访问。
  - 命名格式固定为 `ModuleName.ServiceKind.ServiceName`
  - 例如 `GraphicsModule.Driver.WgpuDriver`、`SceneModule.Manager.WorldManager`
- 卸载规则固定：
  - 任何 Driver 只有在所有依赖它的 Manager/System/Plugin 已卸载后才能卸载。
  - Lazy 服务首次解析时初始化。
  - Immediate 服务在所属 Module/Plugin 激活时初始化。

### 2. 模块、管理器、服务器 façade

- `zircon_module` 改为模块与插件元数据中心，公开：
  - `ModuleDescriptor`
  - `DriverDescriptor`
  - `ManagerDescriptor`
  - `PluginDescriptor`
  - `ModuleContext`
  - `PluginContext`
- `zircon_server` 不再空置，改为跨模块公共 façade crate。
  - 所有 VM 插件和上层应用只依赖 `zircon_server` 暴露的稳定句柄与服务接口，不直接持有底层 Rust 实现对象。
  - 这里放置 `RenderingServer`、`AssetServer`、`InputServer`、`SceneServer`、`ConfigServer`、`EventServer` 等 façade trait 与 handle type。
- 每个功能 crate 都要变成真正的 `*Module`：
  - `zircon_platform`
  - `zircon_input`
  - `zircon_asset`
  - `zircon_graphics`
  - `zircon_scene`
  - `zircon_editor`
  - `zircon_physics`
  - `zircon_sound`
  - `zircon_texture`
  - `zircon_ui`
  - `zircon_net`
  - `zircon_navigation`
  - `zircon_particles`
  - `zircon_animation`
  - `zircon_server`
  - `zircon_script`
- 其中首轮功能完整迁移的是当前主链路相关模块：
  - app/core/module/server/platform/input/asset/graphics/scene/editor/script
- 其余模块本轮必须同步具备：
  - Module descriptor
  - Driver/Manager descriptor
  - config 对象
  - 生命周期接入
  - no-op 或 stub 实现
  - 可被 Core 正确注册、初始化、关闭

### 3. ECS 立即接管运行时世界

- `zircon_scene` 改为 ECS World crate，不再以当前 `Scene { nodes: Vec<SceneNode> }` 为核心。
- 首版运行时对象模型固定为：
  - `EntityId`
  - `Name`
  - `Hierarchy`
  - `LocalTransform`
  - `WorldTransform`
  - `Camera`
  - `MeshRenderer`
  - `DirectionalLight`
  - `Active`
- Scene 树规则固定：
  - 父子关系由 `Hierarchy` 组件表达。
  - 编辑器场景树只是 ECS 层级查询结果。
  - `WorldTransform` 由系统计算，不允许 UI 直接写。
- 调度阶段固定为：
  - `PreUpdate`
  - `Update`
  - `LateUpdate`
  - `FixedUpdate`
  - `RenderExtract`
- `System` 是调度单元，不再是当前场景节点式对象。
- `zircon_editor` 不再直接拥有 `Scene`；它只维护编辑器状态、选择集、命令栈和 inspector 草稿，并通过 `SceneServer/WorldManager` 修改 ECS World。
- 现有项目保存/加载、外部 mesh 导入、undo/redo 都迁移到 ECS 世界与命令系统之上。
- 原先 `RenderSceneSnapshot` 保留，但它改为 `RenderExtract` 阶段从 ECS 生成的渲染抽取结果，而不是从旧 Scene 图生成。

### 4. 图形、应用入口与编辑器宿主

- `zircon_graphics` 保持独立渲染内核，但它不再直接依赖旧 Scene 数据结构；只接受 `RenderExtract` 结果。
- `zircon_app` 只做 Entry：
  - 创建 `CoreRuntime`
  - 注册全部内建 Module
  - 选择 Editor 或 Runtime 启动模式
  - 驱动主循环
- `zircon_editor` 改为 EditorModule + EditorApp 宿主：
  - `EditorState`
  - `EditorCommand`
  - `UndoableStack`
  - `EditorChrome`
  - `ViewportHost`
- editor/runtime 都必须通过 Core 查询 façade，不允许继续直接 new `Scene`、`ViewportController`、`RenderService` 拼主链路。
- 当前已经存在的 viewport GPU 桥接保留，但其调用入口迁移到 `RenderingServer + WorldManager + EditorViewportManager` 模型之下。

### 5. VM 插件与热替换

- 插件统一改为 VM 插件，不再使用 Rust 原生动态库。
- `zircon_script` 负责：
  - `VmBackend`
  - `VmPluginPackage`
  - `VmPluginInstance`
  - `VmStateBlob`
  - `HostHandle`
  - `CapabilitySet`
  - `HotReloadCoordinator`
- 插件热替换语义固定为“宿主句柄稳定，实例可替换”：
  - VM 插件只能通过 `HostHandle` 访问宿主服务。
  - 热替换时宿主保留稳定句柄表。
  - 旧实例执行 `save_state -> deactivate`
  - 新实例执行 `activate -> restore_state`
  - 外部模块感知到的是同一个 plugin slot，而不是同一个 Rust 对象地址
- 这满足你要求的“无感热替换”，但保证层级限定在 VM 插件 API 语义层，不追求 Rust 内部对象地址连续。
- 因为 `E:\Git\zr_vm` 当前不在本仓库且 Rust 绑定暂时留空，本轮必须实现：
  - 完整 VM 宿主协议
  - 插件包 manifest
  - 状态迁移协议
  - backend trait
  - `UnavailableVmBackend` / `MockVmBackend`
- 本轮不实现 `zr_vm` 真正执行器，但后续只需要替换 `VmBackend` 适配层，不再改 Core/Module/Server 架构。

  - Driver/Manager 注册、Lazy/Immediate 初始化、依赖排序、卸载阻塞、字符串查找与类型查找一致。
- ECS：
  - 实体创建/删除、层级变换传播、系统阶段顺序、渲染抽取、项目保存/加载、undo/redo 后世界一致。
- 图形与宿主：
  - editor 和 runtime 都通过 `zircon_app` 启动并成功走 Core 主链路。
  - viewport 仍能显示同一 ECS 世界的 3D 内容。
  - editor 对世界修改后，inspector、层级树、渲染结果一致。
- VM 插件协议：
  - manifest 解析
  - capability 协商
  - host handle 有效性校验
  - `save_state/restore_state` 契约
  - plugin slot 热替换不导致宿主引用失效
  - backend unavailable 路径有明确错误而不是 panic
- Workspace 验收：
  - `cargo check --workspace`
  - editor/runtime 宿主编译通过
  - 全部 `zircon_*` crate 已接入 Module/Driver/Manager 生命周期
  - 不再存在仅靠 `engine_name()` 占位的系统 crate

## Assumptions

- `E:\Git\zr_vm` 是外部 VM 工程；本仓库本轮只做宿主协议和适配槽位，不直接实现 VM 执行器。
- “全 workspace 同步落地”解释为：所有 crate 都完成架构接入和生命周期化，不解释为所有领域功能在本轮全部做完。
- “无感热替换”保证的是 VM 插件对宿主 API 的连续性和状态迁移语义，不保证 Rust 内部具体对象地址或 trait object 连续。
- Core 仍然按路线图保持全局唯一实例，但实现使用 Rust 安全方式管理，而不是裸全局可变单例。
