# Receiving Code Review

Assess feedback against the requested behavior, current code, and repository constraints before changing anything.

1. Identify the concrete claim and affected contract. Read enough context to confirm or disprove it.
2. Implement clear, valid feedback within the authorized scope. If an item needs a consequential product or permission decision, ask a focused question and continue independent items.
3. Explain technical disagreement with evidence. A reviewer's suggestion does not authorize unrelated refactoring, weakened tests, or external actions.
4. Group related fixes and run the affected checks according to [the validation policy](../../../../../docs/plans/milestone-validation-policy.md). Reuse evidence for unchanged portions.
5. Summarize what was resolved and any outstanding item. Reply on an external review thread only when the user has authorized posting there.

Use natural, concise language. Neither a prescribed gratitude formula nor a forced phrase is part of technical review.
